# 24. 판 게임 개인 시간 (2026-10-29)

바둑처럼 사람마다 기본 시간과 초읽기가 있다. 오목·장기에 넣었고, 앞으로의 판 게임(바둑·체스)도 같은 틀을 쓴다.
2026-10-28 사용자 질문 "오목은 개인별 시간 이런 거 없나?"에서 시작했다(docs/20 1절).

## 1. 규칙

| 고르는 것 | 기본 시간 | 초읽기 |
|---|---|---|
| 시간 없음(기본) | — | — |
| 빠른 3분 | 3분 | 30초 × 3번 |
| 보통 10분 | 10분 | 30초 × 3번 |

- 내 차례에만 내 시계가 준다. 기본 시간을 다 쓰면 초읽기로 넘어간다.
- 초읽기는 한 수를 30초 안에 두면 횟수가 줄지 않는다. 30초를 넘길 때마다 한 번씩 준다. 다 쓰면 시간패다.
- 판마다 시계를 새로 준다. 장기는 상차림 때 시계가 가지 않는다.
- 옵션 화면에서 고르고, 다함께도 고른 규칙으로 방을 연다.

## 2. 구조

- `@mighty/engine`의 `time-control`
  - 시간 규칙 `TimePreset`과 남은 시간 `PlayerClock`을 둔다.
  - `spendTime(clock, spent, control)`이 한 수에 쓴 시간을 깎는다. 기본 시간 → 초읽기 → 시간패 순서다.
- 엔진(오목·장기)
  - 시계를 상태(`clocks`)에 둔다.
  - 두기·쉬기 행동에 `spent`(그 수에 쓴 ms)가 실린다. 엔진은 그만큼 깎는다.
  - 시간을 넘겨 둔 수는 두지 않고 시간패로 끝낸다.
  - `timeout` 행동은 정말 시간이 다 됐을 때만 받는다.
  - 엔진은 지금 시각을 모른다(순수 함수 그대로).
- 대국 진행(`LocalMatch`, 혼자 하기와 방장)
  - `Clock`으로 차례가 시작된 뒤 지난 시간을 잰다.
  - `GameKit.timing.stamp`로 그 시간을 행동에 싣는다. 참가자가 보낸 값은 덮어쓴다.
  - 남은 시간이 다 되면 그 자리로 `timeout`을 기록한다.
  - 참가자는 `timeout`을 보낼 수 없다(`guestMayAct`).
- 화면: `GameClock`이 엔진 상태의 남은 시간을 받은 때부터 거꾸로 센다. 고르기는 `TimePresetPicker`다.

### 차례를 끝내지 않는 행동(2026-10-29)

- LocalMatch는 행동이 들어올 때마다 시계를 다시 걸고 생각 시간을 새로 잰다. 그런데 체스 무승부 제안·거절처럼 두는 사람의 차례를 끝내지 않는 행동 뒤에 새로 재면, 거절만으로 시계가 처음부터 다시 걸려 시간을 벌 수 있다.
- 그래서 키트가 `timing.keepsTurn(action)`으로 그런 행동을 알리면, 같은 사람의 시계가 계속 갈 때 그 차례에 이미 쓴 시간을 이어 잰다. 다음 수에 실리는 `spent`도 차례가 시작된 때부터다.
- 시험: `apps/web/src/game/local-match-time.test.ts`의 "차례를 끝내지 않는 행동".

## 3. 설계 다섯 질문

1. **데이터의 뜻·연결·책임**
   - 규칙의 `time`(없으면 시간 없음)을 둔다.
   - 상태의 `clocks[자리] = { main, periods }`를 둔다.
   - 행동에 `spent`를 싣고, `timeout` 행동을 더했다.
   - 시각을 재는 책임은 대국을 돌리는 기기 하나(혼자 하기·방장)에만 있다.
2. **꼭 지킬 규칙을 어떻게 보장하나**
   - 시간 계산은 `spendTime` 한 곳에서만 한다.
   - 기록에 `spent`와 `timeout`이 남아, 다시 두면 시계까지 같은 판이 나온다. 판 끝 검증이 시계도 확인한다.
   - 시험은 `ManualClock`(단위)과 Playwright `page.clock`(화면)으로 정확한 순간에 시간패를 일으킨다.
3. **사람과 AI가 데이터를 어떻게 찾아 쓰나**
   - 규칙 문자열 꼬리가 시간 규칙이다: `-t1`이 빠른, `-t2`가 보통이다. 예: `o1-s1-t1`, `j1-s1-t2`
   - 기록의 `spent`는 ms다.
4. **요구사항이 바뀌면 어디까지 고치나**
   - 시간 규칙을 더하는 것은 `TIME_PRESETS`와 꼬리 글자 한 줄이다.
   - 피셔(수마다 시간 더하기) 같은 다른 방식은 `spendTime`과 `TimeControl`만 넓히면 된다.
5. **다른 대안과 고른 근거**
   - 시계를 엔진 밖(방장 메모리)에 두고 화면 정보로만 보내는 방법을 견줬다.
     - 그러면 판 끝 검증이 시간패를 확인할 수 없다.
     - 새로고침하면 시계가 사라진다.
     - 게임마다 온라인 메시지를 바꿔야 한다.
   - 그래서 시계를 상태에 두고 "쓴 시간"을 행동에 싣는 방법을 골랐다.
   - 방장이 쓴 시간을 부풀릴 수는 있다. 방장이 엔진을 돌리는 다른 결정과 같은 수준의 믿음이다(docs/07).

## 4. 남은 것

- 온라인에서 방장과 참가자 사이 지연만큼 참가자 화면의 시계가 조금 늦게 보일 수 있다. 시간패 판정은 방장 시계 하나로 한다.
- 시간이 얼마 안 남았을 때 소리(초읽기 "삑")를 낼지 정한다.
