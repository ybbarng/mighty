# 18. 게임 센터 확장 기획 (2026-10-27)

마이티·하트를 담은 지금 구조를 넓혀, 지인끼리 여러 캐주얼 게임을 하는 "게임 센터"로 키울 가능성에 대비한 기획이다.
당장 만들자는 문서가 아니다. 새 게임을 넣거나 공통 모듈을 고칠 때 방향이 어긋나지 않게 하려고 쓴다.

- 대상: 지인끼리. 유료화하지 않는다.
- 저작권·상표는 이 문서에서는 따지지 않는다. 다만 저장소와 사이트가 공개라서, 실제로 만들 때는 이름과 그림을 다시 본다(맨 끝 "남은 결정").

---

## 1. 지금 가진 것

| 층 | 지금 있는 것 | 위치 |
|---|---|---|
| 연결 | WebRTC로 기기끼리 바로 잇기(Nostr 릴레이로 서로 찾기), 같은 브라우저 탭끼리(시험용), 메모리(단위 시험). TURN 중계는 준비 중 | `apps/web/src/net/p2p-transport.ts`, `transport.ts` |
| 방 | 방 만들기, 초대 링크·QR, 대기실, 빈자리 컴퓨터, 채팅, 끊기면 다시 잇기, 기다리다 투표로 끝내기 | `HostRoom`, `GuestRoom`, `LocalMatch` |
| 진행 | 방장 기기가 순수 함수 엔진을 돌리고 참가자는 행동만 보낸다. 여러 자리가 동시에 결정하는 것도 된다(`pendingSeats`, 하트 카드 넘기기) | `GameKit` (`apps/web/src/game/kit.ts`) |
| 공정성 | 멘탈 포커: 함께 섞기(SRA), 자기 자리만 열기, 공개, 열쇠 증명, 섞기 증명, 판 끝에 모두가 다시 계산 | `packages/fair-play` |
| 컴퓨터 | 입문·중수·고수(규칙 + 추측 탐색) | `packages/ai`, `packages/hearts-ai` |
| 공통 화면 | 내 기록, 복기, 배우기(설명·퀴즈·미션), 소리, 설정, 무늬 표기 | `src/stats`, `src/review`, `src/components/learn` |

이 구조는 "차례가 정해진, 숨은 정보가 카드인 게임"에 맞춰져 있다. 아래에서 다른 종류의 게임에 무엇이 더 필요한지 정리한다.

## 3. 나누는 기준

게임을 만드는 데 드는 인프라는 두 가지 축으로 거의 정해진다.

### 3-1. 시간: 누가 언제 행동하는가

| 부류 | 뜻 | 예 | 정할 것 |
|---|---|---|---|
| A. 차례 | 정해진 사람이 행동하고 기다린다 | 마이티, 원카드, 오목 | 지금 구조 그대로 |
| B. 동시 공개 | 모두가 몰래 고르고 한꺼번에 공개한다 | 가위바위보, 젝스님트, 경매 | 먼저 공개한 사람이 손해 보지 않게(남의 것을 보고 바꾸지 못하게) |
| C. 실시간 경쟁, 공유 판 | 같은 판을 보고 먼저 하는 사람이 이긴다 | SET, 할리갈리 | 누가 먼저였는지 누가 정하나 |
| D. 실시간, 각자 판 | 각자 자기 판을 두고 가끔 영향을 주고받는다 | 블록 대결, 뿌요뿌요 | 지연을 견디는 동기화, 결과 검증 |
| E. 실시간 공유 세계 | 하나의 움직이는 세계를 함께 조종한다 | 퐁, 봄버맨 | 수십 ms 지연도 느껴진다. 되감아 다시 계산하는 동기화 |

### 3-2. 정보: 무엇을 숨기고, 무엇이 운인가

| 부류 | 예 | 공정성 도구 |
|---|---|---|
| 완전 공개 | 오목, 퐁 | 필요 없음(엔진 검증만) |
| 섞은 카드 | 마이티, 원카드, SET | 함께 섞기·자기 자리만 열기·공개(있음). 원카드는 "판 도중 덱에서 뽑기", 도둑잡기는 "남의 자리 카드를 내가 열기"가 더 필요 |
| 동시에 고른 값 | 가위바위보, 경매 | 약속 뒤 공개(값의 해시를 먼저 보내고, 모두 모이면 공개) |
| 처음에 숨긴 배치 | 배틀십 | 칸마다 약속해 두고, 맞았는지 물을 때 그 칸만 공개(속이면 판 끝에 드러남) |
| 숨은 역할 | 라이어 게임, 마피아 | 역할 카드를 섞어 나누기(카드와 같다) |
| 함께 정하는 운 | 주사위, 블록 순서 | 모두가 씨앗을 약속한 뒤 공개해 합친다 |

정보 쪽 도구는 거의 모두 `fair-play`의 "약속 뒤 공개"와 "함께 섞기"를 조합하면 된다. 정말 다른 인프라가 필요한 쪽은 **시간 축의 C·D·E**다.

---

## 4. 부류별 설계

### 부류 A·B: 지금 구조를 넓힌다 (차례·동시 공개)

- A는 지금 `GameKit` 그대로다. 원카드·스페이드·오목은 엔진과 화면만 새로 만들면 된다.
- B도 `GameKit`이 이미 여러 자리의 동시 결정을 받는다. 다만 지금은 방장이 먼저 받은 결정을 볼 수 있다. 방장도 남의 선택을 못 보게 하려면 `fair-play`에 **약속 뒤 공개** 단계를 둔다.
  1. 각자 "선택 + 임의 값"의 해시를 보낸다.
  2. 모두의 해시가 모이면 각자 원래 값을 공개한다.
  3. 해시와 맞지 않으면 그 자리를 짚는다(지금 열쇠 증명처럼).
- 추가할 `fair-play` 도구: 약속 뒤 공개, 함께 정하는 난수, 판 도중 덱에서 뽑기, 숨긴 배치 칸별 공개.
- 방장이 엔진을 돌리고 판 끝에 모두가 다시 계산하는 지금 방식이 그대로 통한다.

### 부류 C: 순서 심판 (실시간 경쟁, 공유 판)

"동시에 눌렀을 때 누가 먼저인가"만 문제다. 세 가지 방법이 있다.

| 방법 | 공정성 | 인프라 |
|---|---|---|
| C1. 방장 기기가 심판 | 방장이 지연 면에서 유리하고, 마음먹으면 순서를 속일 수 있다 | 추가 없음 |
| C2. 방장 심판 + 누른 시각 | 짧은 시간 안의 다툼은 각자 보낸 시각으로 가른다. 시각을 속일 수 있어 완전하지 않다 | 추가 없음 |
| C3. 중립 순서 서버 | 게임 내용은 모르고, 방 안 메시지가 도착한 순서에 번호만 붙여 모두에게 돌린다. 모두가 같은 순서를 보므로 방장도 끼어들 수 없다 | 작은 웹소켓 서버 하나 |

- 지인끼리라면 C1로 시작하고, 필요해지면 C3를 붙인다.
- **C3 "순서 서버"는 게임마다 만들지 않는다.** 방 번호별로 메시지에 번호를 붙여 돌려주기만 하는, 게임을 모르는 공용 서버로 둔다. 메시지는 방 열쇠로 암호화해 서버도 내용을 모르게 한다.
- 이 서버는 WebRTC가 막힌 망에서 **대신 쓰는 연결 통로**도 된다(TURN의 대안). 그래서 만들면 쓸모가 두 가지다.
- 엔진 쪽에서는 `GameKit`에 "아무 때나 누구든 낼 수 있는 결정"을 받아들이게 한다. 순서는 위 심판이 정한다.

### 부류 D: 각자 판 실시간 (블록 대결)

방장이 모두의 판을 계산하면 조작감이 나빠진다. 각자 기기가 자기 판을 돌린다.

- **결정적 엔진**: 정해진 간격(틱)으로 진행하고 정수 계산만 쓴다. 같은 입력이면 어느 기기에서나 같은 결과가 나온다.
- **블록 순서**: 모두가 씨앗을 약속한 뒤 공개해 합친다(부류 B 도구 재사용). 아무도 순서를 미리 고를 수 없다.
- **주고받는 것**: 결과가 아니라 "몇 번째 틱에 어느 키" 입력과, 공격("방해 줄 n개, 틱 t부터")을 보낸다. 상대 판은 가끔 오는 요약으로 그려도 된다.
- **검증**: 받은 입력으로 상대 판을 다시 돌려 보면, 그 입력으로 나올 수 없는 공격은 바로 드러난다. 블록 게임은 계산이 가벼워 판 도중에도 검증할 수 있다. 지금 "판 끝에 모두가 다시 계산"을 실시간으로 옮긴 것이다.
- **시간**: 입력을 일부러 늦게 보내 상대를 보고 움직이는 것은 입력마다 마감을 두어 줄인다. 느린 네트워크와 완전히 구별하지는 못한다.
- 새 틀이 필요하다: `RealtimeKit`(틱, 입력 흐름, 공격 이벤트, 다시 돌려 보기). 방·연결·채팅은 그대로 쓴다.

### 부류 E: 공유 세계 실시간 (퐁, 봄버맨)

- 수십 ms 지연도 느껴진다. 2인이면 "결정적 엔진 + 입력만 주고받기 + 늦게 온 입력은 되감아 다시 계산"(격투 게임에서 쓰는 방식)이 맞다.
- 3인 이상이면 한 기기(또는 서버)가 기준을 잡고 나머지는 예측해서 그린다.
- 일이 가장 크고 휴대폰 성능과 망 상태를 많이 탄다. **마지막에 하거나 하지 않는다.**

### 어디서든 못 막는 것

자동으로 두는 프로그램, 옆에 계산 프로그램을 띄워 놓고 수 묻기는 규칙에 맞는 입력만 보내므로 증명으로 잡을 수 없다. 서버가 있는 큰 게임도 완전히 막지 못한다. 이 문서의 공정성 목표는 "규칙과 운을 속이지 못한다"까지다.

## 5. 전체 구조

```
게임 센터 화면 (첫 화면: 게임 목록, 내 기록, 설정)
 └ 게임 등록부: 게임마다 id, 이름, 인원, 진행 모델, 화면, 컴퓨터, 배우기
진행 모델
 ├ TurnKit      (= 지금 GameKit. 차례, 동시 결정)              부류 A·B
 ├ + 순서 심판   (TurnKit + "아무나 결정" + 심판 C1/C3)         부류 C
 └ RealtimeKit  (틱, 입력 흐름, 다시 돌려 보기)                 부류 D (E는 나중)
공정성 도구 (packages/fair-play)
 ├ 함께 섞기·나누기·공개·증명 (있음)
 ├ 약속 뒤 공개, 함께 정하는 난수, 덱에서 뽑기, 숨긴 배치 칸별 공개 (추가)
 └ 판 끝·판 도중 다시 계산 (있음, 일반화)
방 (HostRoom·GuestRoom: 자리, 초대, 채팅, 다시 잇기, 투표, 빈자리 컴퓨터)
연결 (Transport)
 ├ WebRTC + TURN (준비 중)
 └ 순서 서버 웹소켓 (선택. 부류 C의 심판 겸 막힌 망의 대체 통로)
```

정할 원칙:

- **게임은 진행 모델 하나를 고른다.** 화면과 엔진은 게임마다, 방·연결·공정성·기록은 공용이다. 지금 "마이티·하트 모두에 넣는다"는 규칙을 "모든 게임에 넣는다"로 넓힌다.
- **엔진은 계속 순수 함수**로 둔다. 시험·복기·검증이 모두 여기에 기대고 있다.
- **서버는 게임을 모르게** 둔다. TURN과 순서 서버 모두 내용을 모르는 중계로만 쓴다. "서버 없이, 방장도 속이지 못한다"는 지금 정체성을 지키는 선이다.
- 지금 `GameKit`의 필수 항목(`retireAction`, `stats`, `review` 등)은 그대로 모든 게임의 필수 항목이 된다.

## 6. 단계

| 단계 | 할 일 | 새로 생기는 인프라 | 게임 |

| 0 | TURN 마무리 | TURN | — |
| 1 | 게임 센터 첫 화면, 게임 등록부, 주소 정리(`/mighty`, `/hearts`, …, 옛 주소는 넘겨주기) | 등록부 | — |
| 2 | 차례 게임 늘리기 | 덱에서 뽑기 | 원카드, 오목, 스페이드 |
| 3 | 동시 공개 | 약속 뒤 공개, 함께 정하는 난수 | 가위바위보, 젝스님트 |
| 4 | 숨긴 배치·역할 | 칸별 공개 | 배틀십, 라이어 게임 |
| 5 | 실시간 경쟁 | 아무나 결정 + 심판(C1, 필요하면 C3 순서 서버) | SET, 할리갈리 |
| 6 | 각자 판 실시간 | RealtimeKit | 블록 대결, 뿌요뿌요류 |
| 7 | (선택) 공유 세계 | 되감아 다시 계산하는 동기화 | 퐁 |

각 단계는 "작은 게임 하나로 새 인프라를 검증한 뒤 다음 게임"으로 간다. 예: 3단계는 가위바위보로 약속 뒤 공개를 검증하고 젝스님트로 넓힌다.

## 7. 남은 결정

- 이름과 주소: `mighty.byb.kr`을 그대로 쓰고 첫 화면만 바꿀지, 게임 센터용 새 이름을 둘지. 하트처럼 숨긴 게임을 계속 둘지.
- 순서 서버(C3)를 서버에 둘지. TURN처럼 게임을 모르는 중계이고, 막힌 망의 대체 통로도 겸한다.
- 공개 저장소·공개 사이트라서, 실제 상표 이름(테트리스, 뿌요뿌요, SET 등)과 원작 그림은 만들 때 다른 이름·직접 그린 그림으로 바꿀지.
- 우선순위: 위 단계 순서는 인프라를 쌓는 순서다. 실제로 하고 싶은 게임이 따로 있으면 그 게임에 필요한 단계부터 당긴다.
