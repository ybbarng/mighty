# 36. 하늘의 별 따기(Stardraw): 운영자도 믿을 필요 없는 정시 로또 (2026-10-29)

docs/35의 둘째 안(정시 추첨)을 사용자와 나눈 이야기(응모 비용, 공개 장부, 검증 도구)를 바탕으로 다시 설계한 것이다. 아직 만들지 않았다. 9절의 갈림길을 정하면 10절 순서로 만든다.

## 0. 한 줄 요약

매시 한 회차, 누구나 브라우저에서 패스키로 응모권 한 장을 낸다. 응모권마다 몇 초짜리 계산(작업 증명)과 서명이 들어간다. 마감 때 응모권 목록을 머클 루트로 묶어 공개하고, 그 뒤에 나올 공개 난수(drand)로 당첨 번호를 만든다. 모든 회차 기록은 해시로 이어진 공개 장부에 쌓이고, 장부 끝 해시는 GitHub에도 남긴다. 누구든 공개된 규칙과 독립 검사 도구로 처음부터 다시 계산해 볼 수 있다. 당첨되면 응모권의 비밀 열쇠로 서명해 당첨자 본인임을 확인하고, 상품(커피)은 사람끼리 앱 밖에서 주고받는다.

## 1. 원칙과 막을 것

**원칙**
1. **운영자도 믿을 필요 없게.** 서버(운영자)가 결과를 고르거나, 결과를 보고 장부를 고치거나, 당첨을 가로챌 수 없게 한다. 할 수 있는 나쁜 일은 남기되 반드시 드러나게 한다.
2. **한 명만 확인해도 드러나게.** 모두가 검사할 필요는 없다. 누구든 마음먹으면 독립적으로 검사할 수 있고, 한 사람만 검사해도 조작이 드러난다.
3. **정직한 사람은 불편하지 않게.** 응모는 몇 초, 검사는 단추 하나.
4. **상품이 작다는 것도 방어다.** 커피 한 잔이라 속여서 얻는 기댓값이 작다. 그 크기에 맞는 만큼만 막는다. 상품이 커지면 다시 본다.

**막을 것(위협)**
| 위협 | 누가 | 이 설계에서 |
|---|---|---|
| 당첨 번호를 고르거나 미리 알기 | 운영자 | 불가능(drand, 3절) |
| 결과를 보고 응모권 끼워 넣기·빼기 | 운영자 | 드러남(머클 루트를 drand 전에 공개) |
| 지난 회차 고치기 | 운영자 | 드러남(체인 + GitHub 앵커) |
| 사람마다 다른 장부 보여 주기 | 운영자 | 드러남(GitHub 앵커, 기기가 기억한 해시) |
| 당첨 가로채기, 남의 이름으로 응모 | 운영자·누구나 | 불가능(서명) |
| 한 사람이 응모권 대량으로 내기 | 누구나 | 비용으로 억제(작업 증명, 상한), 완전히는 못 막음(5절) |
| 응모권 받지 않기(검열) | 운영자 | 막지 못하지만 드러남(내 응모권 포함 증명이 안 나옴) |
| 검사 도구가 거짓말하기 | 운영자 | 독립 검사로 드러남(7절) |

## 2. 구성

```
[터미널 검사기]   [게임 센터 화면]        ← 검사 / 응모·결과·검사
       \            /
        [회차 서버]  ── 장부 파일(정적) ── 누구나 내려받기
            |
     [drand 공개 난수]   [공개 시각 인증 기관(TSA)]   [GitHub 앵커 저장소]
```
- **회차 서버**: 응모권을 받고, 마감·추첨·장부 쓰기를 한다. 개인 서버에 Node + SQLite. 신호 서버처럼 Traefik 요청 한도를 건다.
- **장부**: 회차 기록과 응모권 목록을 정적 파일(JSON)로 낸다. nginx가 내주고 캐시한다.
- **drand**: League of Entropy가 운영하는 공개 난수. quicknet 체인(3초마다, BLS 서명)을 쓴다.
- **공개 시각 인증 기관(RFC 3161 TSA)**: 마감 직후 봉인 값의 시각 인증 토큰을 준다. 기본 DigiCert·Sectigo(11-7).
- **GitHub 앵커 저장소**: 회차마다 기록 해시를 커밋한다(`ybbarng/stardraw-ledger`, 11-7).
- **터미널 검사기**: 공개 저장소에서 빌드한 실행 파일 하나. 장부 검사(`stardraw-verify`) 전용이다. 응모·당첨 증명은 하지 않는다(2026-10-30, 11-10).
- **화면**: 게임 센터 로또 페이지. 응모(직접 누를 때만), 남은 시간, 결과 연출, 콘솔 검사 함수.

## 3. 회차 흐름 (회차 k, 마감 시각 `closesAt` 기준)

회차 시각은 일정표로 계산한다(11-1). 아래는 구현(`packages/stardraw-core`) 기준이다.

**매시 정각 추첨, 55분 마감**(2026-10-29 사용자: "추첨 5분 전 마감"이 명확하다). 마감 `closesAt`은 x:55:00이고 drand 회차는 그 5분 뒤 첫 회차라 정각(x:00:00) 직후에 추첨한다. 이렇게 되도록 일정표 epoch를 맞춘다: `(epoch + 5분) % 회차 길이 = 0`(`isAlignedEpoch`, `alignedEpoch`). 1시간 회차는 x:55 시작 → 다음 x:55 마감 → 정각 추첨, 시험용 10분 회차는 x:05·x:15… 마감, x:10·x:20… 추첨이다. 다음 회차 응모는 앞 회차 추첨(정각) 뒤에 열리므로 응모 창은 회차마다 x:00~x:55다. 화면은 "매시 정각 추첨 · 55분 마감"과 함께 마감까지·추첨까지를 따로 센다.

| 시각 | 일 |
|---|---|
| 앞 회차 확정 직후 | 이번 회차의 **문제 값** = 앞 회차 기록 해시(1회차는 처음 일정표의 genesis 해시). 앞 회차가 drand로 확정돼야 알 수 있어서 미리 계산해 둘 수 없다 |
| ~ `closesAt` (x:55) | 응모권을 받는다(5절 비용·상한). 서버가 받은 시각으로 마감하고 영수증을 준다. 화면은 `closesAt - closeMargin`(5초)부터 막는다. 마감 뒤 도착한 응모는 "마감됐어요(서버 시각 hh:mm:ss)"로 돌려준다 |
| `closesAt` | 마감. 응모권을 응모권 id 순으로 정렬해 **머클 루트**를 만든다. 응모권 목록 파일과 루트를 공개하고 처리 기한(기본 3분) 안에 봉인 값의 시각 인증 토큰을 공개 기관 여러 곳에서 받는다 |
| `closesAt` + 5분 이후 첫 drand 회차 (정각 직후) | 미리 정해 둔 drand 회차의 값이 나온다(`drandRoundForClose`) |
| 직후 | 당첨 번호를 만들고(4절) 등수를 정해 **회차 기록**을 쓰고 장부 체인에 붙인다. 기록 해시를 GitHub 앵커 저장소에 남긴다 |

- 머클 루트(봉인 값)가 drand 값보다 먼저 시각 인증을 받으므로, 운영자도 결과를 알기 전에 응모권 목록이 고정된다. 봉인 시각이 drand 시각보다 늦으면 그 회차는 무효다(11-1).
- drand 회차 번호는 마감 시각에서 계산식으로 정해져 있어 운영자가 고를 수 없다.
- drand가 멈추면 그 회차는 기다렸다가 정해진 회차의 값이 나오면 확정한다(값을 바꾸지 않는다).

## 4. 데이터와 계산 규칙 (검사기가 따라 할 공개 규칙)

구현은 `packages/stardraw-core`이고, 시험 파일에 시험 값(입력 → 바이트 → 해시)이 있다.

**직렬화와 해시**
- 해시·서명 대상은 모두 **고정 바이너리 형식**이다(8-1 S1). 정수는 빅엔디언, 가변 길이 값(글자, drand 서명)은 앞에 u16 길이를 붙인다. 글자는 UTF-8.
- 해시는 SHA-256. 용도마다 이름을 앞에 붙인다: `taggedHash(이름, …) = SHA-256(이름 ‖ 0x00 ‖ …)`. 이름은 `stardraw/ticket/v1`, `stardraw/record/v1`처럼 판을 담는다.

**열쇠**: ECDSA P-256. 공개 열쇠는 압축하지 않은 65바이트, 공개 열쇠 SHA-256의 앞 16바이트가 **응모자 id**다. 응모는 브라우저 패스키로만 한다(11-2). 원시 열쇠(직접 만든 열쇠 쌍, 등록 kind 1·서명 kind 1)는 규칙에서 받지 않는다(2026-10-30, 11-11). 연습 장부·데모·배우기·시험은 기기 안 열쇠로 패스키 모양 서명을 흉내 낸다(core `softPasskeySigner`).

**응모자 서명**(응모권·당첨 증명·별명·확인 링크): 패스키 서명 하나뿐이다.
```
2 ‖ authenticatorData ‖ clientDataJSON ‖ DER 서명(각 u16 길이 + 바이트)   패스키(WebAuthn ES256)
```
- 첫 바이트(kind)가 1(원시 P-256 서명 `1 ‖ r‖s(64)`)이면 읽는 단계에서 거절한다(11-11). kind 바이트는 이미 장부에 실린 서명과 맞추려고 남겼다.
- 패스키 서명은 `authenticatorData ‖ SHA-256(clientDataJSON)`에 대한 서명이다. 검사기는 clientDataJSON의 `type = "webauthn.get"`, `challenge = base64url(SHA-256(서명할 내용))`, `origin`이 허용 목록(`https://game.byb.kr`)에 있는지, `crossOrigin`이 true가 아닌지, authenticatorData의 rpIdHash = `SHA-256("game.byb.kr")`인지, flags에 UP(0x01, 사람이 있었다)와 UV(0x04, 지문·얼굴·PIN으로 본인 확인을 했다)가 모두 켜졌는지(다른 비트는 보지 않는다, 2026-10-30 UV 추가, 11-10)를 본 뒤 서명을 확인한다.
- 서버 영수증은 서버 열쇠의 원시 서명(64바이트)이다.

**열쇠 등록**: 응모하려면 공개 열쇠를 먼저 장부에 등록한다(그 회차 기록에 들어간다).
```
v(u8 = 1) ‖ kind(u8 = 2, 패스키) ‖ credentialId(u16 길이 + 바이트) ‖ pub(65) ‖ nonce(u32)
```
- 패스키 번호는 1~1023바이트. kind 1(원시 열쇠, 패스키 번호 없음)은 받지 않는다(11-11). 같은 열쇠·같은 패스키 번호는 장부에 한 번만 들어간다(먼저 들어간 것이 이긴다).
- 작업 증명 대상은 `"stardraw/register/v1" ‖ 0x00 ‖ nonce를 뺀 앞부분`, 목표값은 일정표의 `registerPowTarget`(응모권보다 훨씬 무겁게). 문제 값은 응모권과 같다.
- 등록에는 서명이 없다. 남의 공개 열쇠를 먼저 등록해 봐야 서명할 수 없어 쓸모가 없고, 열쇠를 가졌다는 것은 응모권 서명이 증명한다.
- 등록 id = `taggedHash("stardraw/registration/v1", 등록)`. 응모권의 열쇠는 그 회차까지 등록돼 있어야 한다.

**응모권**(앞부분 80바이트 + 응모자 서명)
```
v(u8 = 1) ‖ round(u32, 회차 차례 번호) ‖ numbers(6바이트) ‖ pub(65) ‖ nonce(u32) ‖ 응모자 서명
```
- 번호는 1~45에서 서로 다른 6개, 오름차순.
- 작업 증명 대상(응모권 내용)은 `v ‖ round ‖ numbers ‖ pub`.
- 서명 대상은 `"stardraw/ticket-sig/v1" ‖ 0x00 ‖ v ‖ round ‖ numbers ‖ pub ‖ nonce`.
- 응모권 id = `taggedHash("stardraw/ticket/v1", v ‖ round ‖ numbers ‖ pub ‖ nonce)`. 서명이 빠져 서명 모양만 바꾼 복제도 같은 id다.

**작업 증명**: Argon2id(메모리 16MB, 반복 1, 병렬 1, 결과 32바이트). salt = 문제 값(32바이트), password = `응모권 내용(u16 길이 + 바이트) ‖ n(u32)`. 결과 앞 4바이트(u32)가 목표값(`powTarget`, 일정표에 있다)보다 작은 n을 찾는다. 평균 시도 수는 2^32 / 목표값.
- 메모리를 많이 쓰는 계산이라 그래픽카드의 이점이 작다.
- 한 번 계산이 브라우저에서 수십 ms라, 목표값으로 휴대폰에서 몇 초가 되게 맞춘다.
- 문제 값이 회차마다 바뀌고 응모권 내용이 들어가 미리 계산하거나 남의 계산을 쓸 수 없다.

**drand**: quicknet 체인 해시·공개 열쇠·시작 시각·주기(3초)를 규칙에 고정한다. 서명 메시지는 `SHA-256(drand 회차 u64)`, 난수는 `SHA-256(서명)`. 회차 k가 쓸 drand 회차는 `closesAt + 300초` 이후 처음 나오는 회차다.

**당첨 번호**: `seed = taggedHash("stardraw/seed/v1", round(u32) ‖ drand 난수(32))`. 머클 루트·응모 수는 넣지 않는다(8-1 O4).
- `taggedHash("stardraw/draw/v1", seed ‖ i(u32))`를 i = 0, 1, …로 이어 바이트를 하나씩 읽는다. 225 이상은 버리고(거절 표본), `b % 45 + 1`을 번호로, 이미 나온 번호는 건너뛴다. 7개가 되면 멈춘다. 앞 6개가 당첨 번호, 7번째가 보너스.
- 시험 값: 회차 1, 난수 `b22aad47…0af3`(quicknet 1000000회차) → 나온 차례 45, 29, 5, 38, 37, 41, 보너스 4.

**등수**: 6/45 로또와 같다(1등 6개, 2등 5개 + 보너스, 3등 5개, 4등 4개, 5등 3개).

**회차 기록**
```
v(u8) ‖ round(u32) ‖ prev(32) ‖ count(u32) ‖ merkleRoot(32)
‖ registrationCount(u32) ‖ registrationRoot(32) ‖ rootLoggedAt(u64)
‖ void(u8) ‖ drandRound(u64) ‖ drandSig(가변) ‖ numbers(6) ‖ bonus(u8)
‖ 등수 1~5마다 [개수(u32) ‖ 응모권 id(32) × 개수]
‖ 일정 변경 [개수(u16) ‖ (fromRound, length, closeMargin, powTarget, registerPowTarget 각 u32) × 개수]
‖ 별명 [개수(u16) ‖ (round u32 ‖ 응모권 id(32) ‖ 별명(u16 길이 + UTF-8) ‖ 응모자 서명) × 개수]
```
- 머클 루트(응모권)와 등록 루트는 둘 다 RFC 6962 방식, id 사전 순이다.
- **봉인 값** = `taggedHash("stardraw/seal/v1", round ‖ count ‖ merkleRoot ‖ registrationCount ‖ registrationRoot)`. 마감 직후 시각 인증을 받는 값이다(토큰에는 SHA-256(봉인 값)이 실린다). 등록도 drand 전에 고정돼, 결과를 본 뒤 당첨 응모권의 등록을 빼서 무효로 만들 수 없다.
- 기록 해시 = `taggedHash("stardraw/record/v1", 기록)`. 다음 회차의 `prev`이자 문제 값이 된다.
- 1회차의 prev는 `taggedHash("stardraw/genesis/v1", 처음 일정표)`라 처음 일정표도 체인에 묶인다. 일정표 줄마다 단계(phase)가 실린다(11-6).
- 무효 회차는 번호 0 여섯 개, 보너스 0, 당첨 없음, drandSig 빈 값이다.

**별명**(선택): 지난 회차 당첨 응모권의 열쇠로 `"stardraw/nickname/v1" ‖ 0x00 ‖ round ‖ 응모권 id ‖ 별명`에 서명한다. NFC로 맞춘 1~20자, 보이지 않는 글자 없음, 응모권마다 한 번. 그 회차가 닫힌 뒤에 내므로 다음 회차 기록에 들어가고, 기록 안에서는 응모권 id 순이다.

**검사 표본**: 작업 증명은 내 응모권과 당첨 응모권은 전부, 나머지는 회차마다 `taggedHash("stardraw/sample/v1", drand 난수)`로 고른 몇 장만 본다(무효 회차는 머클 루트와 prev로 고른다).

## 5. 응모 비용과 1인 1장

사용자와 정한 방향: **완전한 1인 1장 대신, 한 장마다 비용이 들게 해 대량 응모를 억제한다.** 현실의 로또(돈)·회사 미니로또(광고 시청)처럼 여러 장은 막지 않되 장마다 값을 치른다. 상품이 커피라 속여서 얻을 것도 적다.

| 장치 | 막는 것 |
|---|---|
| 응모자 id 하나당 회차 1장(서버) | 같은 열쇠로 여러 장 |
| 장마다 작업 증명(몇 초) | 열쇠를 많이 만들어 대량 응모 |
| 공인 IP 앞부분당 회차 응모 상한(기본 200장) | 서버 자원 보호용 넉넉한 안전장치. 남용 방지의 1차 수단이 아니다(11-10) |
| 새 열쇠 등록에 큰 작업 증명(예: 1분)과 IP 앞부분당 하루 등록 상한(기본 200개) | 열쇠 대량 생성을 비싸게(상한은 안전장치) |
| 패스키 서명마다 본인 확인(UV) 표시 | 진짜 패스키로 낸 응모는 매번 지문·얼굴·PIN을 거쳤다(가상 인증기는 꾸밀 수 있다, 11-10) |
| 브라우저: 자동 응모 없음, 실제 누름으로만 응모 | 여러 기기로 매시간 내기를 귀찮게(사용자 의도) |

- 지웠다 다시 깔면 열쇠가 바뀌어 예전 응모권은 증명할 수 없다(사용자가 받아들임).
- 남는 한계: 마음먹은 한 사람은 같은 네트워크에서 하루 새 우주인 200명·회차당 200장(네트워크를 여럿 쓰면 더)까지 내 남들보다 수백 배 확률을 가질 수 있다. 비용은 작업 증명뿐이다. 상품을 걸려면 추첨 전, 등록할 때 신원(초대·사내 계정, docs/32)을 묶어야 한다. 당첨자만 신원을 확인하는 것은 소용없다(당첨된 열쇠 주인 한 명만 진짜면 된다). 11-10.
- 버린 안: 사내 감사 표시 봇에서 받은 수만큼 응모권을 주기. 사내 계정으로 1인이 풀리지만, 감사 표시가 응모 수단이 되어 본래 뜻을 흐리고 서로 주고받기를 부른다(사용자, 2026-10-29).

## 6. 당첨 증명 (대면·메신저 모두)

- 커피를 사 줄 사람(확인자)이 무작위 문구를 하나 준다(예: 화면의 "확인 코드 받기").
- 당첨자는 `"claim" ‖ 응모권 id ‖ 확인 문구`에 서명해 건넨다(화면 단추).
- 확인자는 장부의 공개 열쇠로 서명을 검사한다. 확인 문구가 매번 달라 지난 증명을 다시 쓸 수 없다.
- 당첨자가 원하면 장부에 "이 응모권의 당첨자는 ○○" 표시를 남긴다(선택. 기본은 열쇠만 보인다).

## 7. 검증: 누구든, 독립적으로

**검사 항목**(처음 회차부터)
1. 응모권마다 서명, 작업 증명, 1인 1장, 상한이 맞는지
2. 응모권 목록으로 머클 루트를 다시 만들면 같은지
3. drand 값의 BLS 서명이 진짜인지, drand 회차가 마감 시각 규칙대로인지
4. 당첨 번호와 등수가 규칙대로인지
5. 체인이 이어지는지, 기록 해시가 GitHub 앵커와 같은지
6. 내 응모권이 목록에 들어 있는지(머클 증명)

**검사하는 길**
- **터미널 `stardraw-verify`**(`packages/stardraw-cli`, 2026-10-30 만듦): 공개 저장소에서 받아 내 컴퓨터에서 돌린다. 서버가 내준 코드가 아니라 가장 독립적이다(11-8).
- **화면 단추와 콘솔 함수**(`lotto.verify("2026-10-29T15")` 등): 누구나 쉽게 돌려 볼 수 있다. 다만 서버가 내준 코드라 완전히 독립적이지는 않다.
- **기기가 기억한 해시**: 기기가 마지막으로 본 기록 해시를 기억했다가, 다음 장부가 그것을 이어받지 않으면 경고한다.
- **재현 가능한 빌드**: 같은 커밋으로 누가 빌드해도 같은 화면 파일이 나온다. 사이트는 화면 코드 해시 목록(`/build-hashes.json`)을 함께 내고, 검사기가 사이트 파일·직접 빌드한 파일과 비교한다. 목록을 GitHub 릴리스에도 남기는 일은 준비만 하고 꺼 두었다(11-8).
- **규칙 문서**: 4절이 곧 명세다. 다른 언어로 자기 검사기를 짤 수 있다.

**장부 받기**(2026-10-30, 11-15): 공개 장부는 회차마다 파일이라, 받는 쪽은 다 찬 10·100회차 묶음 파일(`bundles/10/000001.json` 등)이 있으면 묶음으로, 없으면 낱개로 받는다. 한꺼번에 4개까지, 서버가 막으면(429·503) 기다렸다 다시 받는다.

**서버 없이 받기**(2026-10-30, 11-16): 같은 장부 파일이 앵커 저장소(`ybbarng/stardraw-ledger`)의 `ledgers/<장부 id>/ledger/` 아래에도 같은 바이트로 올라간다. 터미널 검사기는 이 사본을 기본으로 받고, 화면은 우리 서버가 응답하지 않을 때 지난 회차를 여기서 받는다.

## 8-1. 공격 검토 (규칙이 모두 공개된다는 전제, 2026-10-29)

심각도: 높음 = 설계를 바꿔야 함, 중간 = 장치를 더해야 함, 낮음 = 알고 감수.

### 운영자 쪽

| # | 공격 | 심각도 | 대책(설계에 반영) |
|---|---|---|---|
| O1 | **drand 값을 본 뒤 당첨 응모권을 끼워 넣기.** 머클 루트를 "drand 전에 공개했다"는 것을 남이 증명할 수 없으면, 운영자가 결과를 보고 자기 열쇠로 당첨 번호 응모권을 넣은 뒤 루트를 공개할 수 있다. GitHub 커밋 시각은 커밋하는 쪽이 정할 수 있어 증거가 못 된다 | 높음 | 봉인 값(루트)으로 **공개 시각 인증 기관(RFC 3161 TSA) 여러 곳**의 시각 인증 토큰을 받는다. 토큰은 기관 열쇠로 서명돼 운영자가 시각을 고칠 수 없고, 검사기는 기관 루트 공개 열쇠를 고정해 확인한다(11-7). 가장 이른 토큰 시각이 정해 둔 drand 회차 시각보다 앞서야 그 회차를 유효로 본다. drand 회차는 마감 + 5분으로 넉넉히 둔다. GitHub 앵커는 보조로 남긴다. (처음에는 Sigstore Rekor로 정했다가 2026-10-30 바꿨다: 공급망 서명용 공개 서비스라 이 쓰임이 애매하고, 시험용 로그는 보장이 없다) |
| O2 | **drand 뒤 남의 당첨 응모권 빼기** | 높음 | O1과 같은 시각 증명 + **응모 영수증**: 서버가 응모권을 받으면 `round·응모권 id·받은 시각`에 서버 열쇠로 서명해 돌려준다. 영수증이 있는데 목록에 없으면, 운영자의 잘못을 누구에게나 증명할 수 있다 |
| O3 | **GitHub 앵커 다시 쓰기**: 저장소 관리자는 강제 push로 기록을 바꿀 수 있다 | 중간 | 지난 회차를 고치면 기록 사슬과 봉인 값이 바뀌어, 이미 받은 시각 인증 토큰(운영자가 고칠 수 없다)과 어긋난다(O1). 앵커 저장소는 보조이고, 기기는 마지막으로 본 기록 해시를 기억한다 |
| O4 | **seed 고르기**: seed에 운영자가 바꿀 수 있는 값(머클 루트, 응모 수)이 들어가면 응모권을 넣고 빼며 원하는 seed를 찾을 수 있다 | 높음(넣으면) | seed는 `round`와 drand 값만으로 만든다(4절 그대로). **머클 루트를 seed에 넣지 않는다**를 규칙에 못 박는다 |
| O5 | **브라우저 응모자의 당첨 가로채기**: 열쇠는 내보낼 수 없어도, 서버가 내준 화면 코드는 그 열쇠로 아무것에나 서명할 수 있다. 운영자가 화면 코드를 바꿔 당첨 확인 문구에 몰래 서명하게 하면 당첨을 가져갈 수 있다 | 중간 | 화면 코드 해시 공개·재현 빌드·터미널 검사기(11-8, 2026-10-30)로 사이트가 내준 코드가 공개 저장소의 그 커밋인지 누구나 비교할 수 있다. 응모·증명은 브라우저 패스키로만 하므로(11-10) 브라우저 열쇠는 그 화면을 내주는 쪽을 믿어야 한다는 한계를 화면에 적는다 |
| O6 | 사람마다 다른 장부·문제 값 보여 주기 | 중간 | 문제 값 = 앞 기록 해시라 장부와 함께 검사된다. 기록 해시를 GitHub 앵커 저장소에 남겨 모두가 같은 값과 비교한다 |
| O7 | 운영자가 열쇠 여러 개로 응모(상한 무시) | 낮음 | 막지 못한다. 작업 증명 비용은 똑같이 든다. 장부에 회차별 응모 수와 열쇠 첫 등장 시각을 남겨 이상한 몰림이 보이게 한다 |
| O8 | drand 회차 바꿔치기, 다른 체인 쓰기 | 낮음 | 체인 해시(quicknet)와 회차 계산식을 규칙에 고정하고 검사기가 확인한다 |

### 개인정보

- 같은 공개 열쇠로 낸 응모가 모두 이어져 보인다. 사람은 드러나지 않지만, 당첨 때 이름을 밝히면 지난 응모가 모두 그 사람 것으로 보인다. 열쇠를 바꾸는 방법(새 열쇠 등록)을 안내한다.

### 이 검토로 바뀐 설계 (요약)

1. 봉인 값(루트)의 시각 증명을 공개 시각 인증 기관 여러 곳으로 한다(O1·O3, 처음에는 Rekor였다가 2026-10-30 바꿈). 기록 해시는 GitHub 앵커에 남긴다(O6). drand 회차는 마감 + 5분이다.
2. 응모 영수증을 서버 서명으로 준다(O2).
3. seed에 머클 루트를 넣지 않는다(O4).
4. 서버 확인 순서와 Argon2 동시 실행 제한을 둔다(P1).
5. 작업 증명은 표본 검사가 기본이다(P2).
6. 해시 대상은 고정 바이너리 형식이다(S1).
7. 머클 트리는 RFC 6962 방식이다(S2).
8. 브라우저 열쇠는 화면 코드를 믿어야 한다는 한계를 알린다(O5). 터미널로 증명하는 길은 두지 않기로 했다(11-10).

## 11. 하늘의 별 따기(Stardraw): 사용자와 정한 것 (2026-10-29)

### 11-1. 회차 길이 바꾸기와 마감 여유

- **일정표**를 장부에 기록한다: `{ fromRound, length, closeMargin }` 목록. 바꿀 때는 새 줄을 더하고, 효력은 **3회차 예고 뒤(실린 회차 + 4)부터**다(11-17, 2026-10-31 전에는 "마감 + 24시간"). 이미 응모받는 회차의 시각은 바꿀 수 없다.
- 회차 k의 시각은 일정표만으로 계산된다: `opensAt`(앞 회차 마감), `closesAt`. 검사기도 같은 계산을 한다. epoch는 추첨이 정각에 오게 맞춘다(3절).

| 회차 길이 | 마감 | 추첨(drand) | 응모 창 | 화면 마감 |
|---|---|---|---|---|
| 1시간(정식) | 매시 x:55:00 | 정각 x:00:00 직후 | x:00 ~ x:55 | x:54:55 |
| 10분(시험 기본) | x:05·x:15·…·x:55 | x:10·x:20·…·x:00 직후 | 추첨 직후 ~ 다음 마감(5분) | 마감 5초 전 |
- **시계 오차 흡수**
  - 응모 마감은 서버가 **받은 시각**으로 정하고 영수증에 적는다.
  - 화면은 `closesAt - closeMargin`(기본 5초)부터 응모를 막는다. 사용자 기기 시계가 틀려도 서버 시각(응답 헤더)과 차이를 재서 보정하므로 여유는 시계 차이·전송 시간만 덮으면 된다(처음 60초 → 2026-10-29 5초로 줄임: 마감 시각이 x:55로 분명해져 1분 일찍 막으면 오히려 헷갈린다).
  - 마감 뒤 도착한 응모(앞 회차 응모권이거나 이미 봉인한 회차)는 "마감됐어요(서버 시각 hh:mm:ss)"로 분명히 알린다(`closedMessage`, 한국 시각).
  - 마감 뒤 **처리 기한**(기본 3분) 안에 봉인 값(응모권 루트 + 등록 루트, 4절)의 시각 인증 토큰을 공개 기관에서 받는다. 서로 다른 기관 1곳 이상의 맞는 토큰이 있어야 봉인 성공이고, 봉인 시각(`rootLoggedAt`)은 그중 가장 이른 시각이다(11-7). 기한 안에 한 곳도 못 받으면 그 회차는 무효다.
  - drand 회차는 `closesAt + 5분` 이후 첫 회차다. drand 시각은 drand 체인의 시작 시각과 주기로 계산되므로 우리 서버 시계와 상관없다.
  - 봉인 시각이 drand 시각보다 늦으면 그 회차는 **무효**(당첨 없음, 기록은 남김)다. 운영자가 일부러 늦춰도 그때는 결과를 모르므로 결과를 고를 수 없다.

### 11-2. 당첨을 알고 증명하기

**열쇠: 브라우저 패스키로만**
- 패스키(WebAuthn, ES256 = P-256)는 iCloud 키체인·Google 비밀번호 관리자·1Password에 저장되어 기기를 바꿔도 따라온다. 비밀 열쇠는 사용자도 서버도 볼 수 없어 복사당하지 않는다.
- 응모와 증명 때마다 Face ID·지문 한 번. 사람이 직접 눌러야 해 브라우저 자동 응모가 막힌다(5절 사용자 의도와 같다).
- 서버는 **패스키 번호(credential id)와 공개 열쇠만** 저장한다. 패스키는 만들 때만 공개 열쇠를 알려 주므로 등록 기록을 장부에 남긴다. 이름·이메일·비밀번호·로그인 세션은 없다. 패스키 "사용자 이름" 칸은 "우주인 ○○"이다(처음 "하늘의 별 따기", 2026-10-30 국장 패스키와 가르려고 바꿈, 11-14). 응모자를 부르는 표시(코드·별명)는 두지 않는다(사용자).
- 새 기기에서는 따라온 패스키로 Face ID만 하면 브라우저가 패스키 번호를 알려 주고, 서버가 그 번호로 공개 열쇠를 찾는다.
- 서명은 WebAuthn 형식(authenticatorData ‖ clientDataJSON 해시에 서명, clientDataJSON의 challenge = 서명할 내용의 해시)이라 검사기가 이 형식을 읽는다.
- **브라우저 응모는 패스키로만**(2026-10-29 사용자). 기기 안 열쇠(IndexedDB)로 응모하는 길은 없앴다. 패스키를 쓸 수 없는 환경은 응모 대신 안내한다: 앱 안 브라우저(카카오톡·네이버 앱·인스타그램 등) → "Safari·Chrome으로 열어 주세요"와 주소 복사, WebAuthn이 없는 브라우저 → 업데이트 안내, 이 기기 잠금을 못 씀 → "화면 잠금을 켜면 이 기기에서 바로, 지금은 휴대폰(QR)·보안 키로", 만들기·서명 취소 → "응모되지 않았어요" + 「패스키가 뭐예요?」 문답, ES256을 못 만들거나 본인 확인(UV)을 못 하는 인증기(일부 오래된 Windows Hello) → "다른 기기 사용(휴대폰 QR)".
- 만들기 옵션: ES256(-7)만, attestation `none`, residentKey `required`(새 기기에서 이름 없이 찾기), userVerification `required`, 기기 종류(authenticatorAttachment)는 정하지 않는다(iCloud·Google 비밀번호 관리자·1Password·Bitwarden·Windows Hello·보안 키·휴대폰 QR 모두). 서명도 userVerification `required`. 검사기는 서명마다 UV 표시를 요구하고, 화면은 만들 때 받은 authenticatorData에 UV가 없으면 미리 "본인 확인을 하지 못합니다"로 막는다(11-10).

**패스키 자연스럽게 쓰게 하기(사용자: 이 게임의 목적 중 하나, 2026-10-29)**
- 원칙: 등록을 따로 시키지 않고 응모 자체가 패스키 만들기다. 이득을 쉬운 말로, 조르지 않는다. 패스키에 응모권·확률 혜택은 주지 않는다(공정성).
- 패스키 등록과 서명을 나눈다(2026-10-30 사용자, 같은 날 화면 이름은 「우주인 등록」·「이미 우주인 등록증이 있어요」로 바뀜, 11-9): ① 패스키가 없으면 별을 고르기 전에 "응모하려면 패스키가 필요해요 · 패스키 만들기"(등록만, 확인 한 번). 다른 기기에서 만든 패스키가 따라왔으면 「이미 패스키가 있어요」(이름 없이 찾기). ② 「이 별 6개로 응모하기」가 서명한다(확인 한 번). 두 번째 응모부터는 ②만. 데모도 같은 두 단계로 흉내 시트("패스키를 만들까요?", "패스키로 서명할까요?")를 띄운다. 게임 화면에는 덧붙이는 설명 문장을 두지 않는다(2026-10-30 사용자: "쓸데없는 문구들은 추가하지 마"). 무엇을 하면 되는지, 왜 막혔는지만 짧게.
- 「패스키가 뭐예요?」는 사람들이 실제로 걱정하는 질문에 존댓말로 답하는 문답이다: 얼굴·지문이 서버로 가나요, 서버가 해킹되면요, 가짜 사이트에 속으면요, 휴대폰을 잃어버리면요, 비밀번호보다 왜 나아요, 저를 추적하나요, 어디에 저장되나요, 아이폰과 안드로이드를 같이 쓰면요. 솔직한 한계 한 줄("휴대폰 잠금 비밀번호를 아는 사람은 지문 대신 그 비밀번호로 패스키를 쓸 수 있어요". 패스키는 지문·Face ID가 안 되면 기기 잠금 PIN·패턴·암호로도 열린다)과 "다른 기기에서 열어 보기" 연습을 붙인다. 문답은 설명 페이지 "패스키와 보안"(/stardraw/about#passkey)에만 두고, 게임 화면은 「패스키가 뭐예요?」 링크로 잇는다.
- 내 응모 화면에는 열쇠 칩·"서버가 가진 것" 비교를 두지 않는다(설명 페이지 "패스키와 보안"으로 옮김, 2026-10-30). 패스키 기억이 없는 기기에서는 「다른 기기에서 내 응모권 찾기」: 따라온 패스키로 한 번 확인하고(이름 없이 찾기), 장부에서 그 패스키 번호의 공개 열쇠를 찾아 닫힌 회차의 내 응모권을 모은다(서버 `GET /api/passkeys/:id`).
- 패스키로 서명한 응모권은 영수증에 작은 열쇠 표시("서명: 패스키")가 붙는다. 꾸밈일 뿐 혜택이 아니다.
- 버린 안: 기기 열쇠 응모자에게 "패스키로 바꾸기"를 띄우기, 기기 열쇠로 낸 응모권이 당첨되면 패스키 만들기를 권하기(브라우저는 패스키로만 응모하게 되어 필요 없어졌다).
- 패스키는 주소(game.byb.kr)에 묶인다. 주소를 옮기면 옛 패스키 응모권 증명이 어려워진다.
- 버린 안: 영수증의 QR·코드를 보여 주면 당첨으로 보기(무기명이라 스크린숏으로 복사된다), 영수증의 "긁는 칸"에 열쇠 백업 넣기(긁는 칸도 같은 저장소에 있어 열쇠와 함께 사라진다).

**내가 알기**
- 추첨 때 보고 있으면: 공이 나올 때마다 하늘의 그 별이 켜지고(금빛), 내 별(하늘색)과 겹치면 초록으로 강조한다. 등수에 맞는 연출(1등은 화면이 빛난다).
- 나중에 오면: 지난 응모권이 **봉한 봉투**로 쌓여 있고, 누르면 그 회차 추첨을 다시 돌리며 맞춰 본다.
- 내 응모 이력은 내 공개 열쇠로 장부에서 찾는다. 기기 알림(Web Push)은 나중에 본다.

**당첨자 확인(2026-10-30 다시 설계: 당첨자가 먼저 한 번 쓰는 확인 링크를 보낸다)**
1. 당첨자 기기는 공개 장부로 스스로 당첨을 안다. 내 응모(·첫 화면)에 **카노푸스 우주국 당첨 안내** "시험 n회 k등입니다. 당첨을 알리고 싶은 사람에게 확인 링크를 보내세요"가 뜬다(서버 메시지가 아니라 장부 계산이라 위조할 수 없다, 카드 아래 "공개 장부로 이 기기가 계산한 안내입니다").
2. 「확인 링크 만들기」 → 등록증(패스키)으로 서명 한 번. 기기가 무작위 토큰(18바이트 = 144비트)을 만들고 `토큰 해시 ‖ 회차 ‖ 응모권 id`에 응모권 열쇠로 서명해 서버에 초대를 올린다. 서버는 장부의 그 응모권 공개 열쇠로 서명이 맞아야 받는다 → **응모권 주인만 링크를 만든다**. 서버는 토큰 해시만 둔다. 링크는 `game.byb.kr/stardraw/check#토큰`(토큰은 `#` 뒤라 서버 로그·Referer에 남지 않는다). 공유(Web Share)·복사 단추. 링크는 7일, 응모권당 열린 링크 10개. 「다른 사람에게 보낼 새 링크」로 사람마다 따로 만든다.
3. 확인하는 사람: 링크를 열면 서버가 회차·응모권 id를 알려 주고, 기기가 공개 장부로 그 회차 당첨 응모권인지 확인해 "n회 k등 당첨자가 보낸 확인 링크입니다"를 띄운다. 「확인 시작」 → 임시 ECDH 열쇠를 만들어 그 링크에 요청을 붙이고, 링크는 이때 닫힌다(한 번만). 이미 쓰인 링크면 "이미 사용된 링크입니다. 당첨자에게 새 링크를 받으세요", 없거나 기한이 지났으면 "없는 링크이거나 기한(7일)이 지났습니다". 같은 기기에서 같은 링크를 다시 열면 이어서 확인한다.
4. 당첨자 기기: 그 한 건의 요청을 스스로 찾아(열 때·열려 있는 동안) "보낸 확인 링크로 n회 k등 당첨 확인 요청이 왔습니다", 작게 "○시에 만든 링크 · 전달: 카노푸스 우주국", "링크를 보낸 적이 없으면 거절하세요". 「등록증으로 승인」 → 패스키 서명과 자기 임시 ECDH 공개 열쇠를 올린다. [거절]도 알린다. **24시간** 안에.
5. 당첨자 화면: 네모 하늘에서 **별 세 개**가 ①②③ 차례로 빛난다. "링크를 보낸 사람에게, 당첨을 알렸던 그 메신저·메일로 이 세 별 이름을 차례대로 보내 주세요", "별 세 개는 내가 당첨을 알린 그 사람에게만 보내세요." 보낼 별은 화면을 닫아도 남는다.
6. 확인하는 사람 화면: 브라우저가 장부의 응모권 열쇠로 서명을 직접 검사하고, 통과하면 "당첨자가 보낸 별 세 개를 하늘에서 차례로 눌러 주세요". 맞으면 초록불이 하늘 전체로 번지며 "n회 k등 당첨자 본인이 맞습니다". 틀리면 다시, **세 번 틀리면 닫는다**(새 링크를 받는다). 별 누르기에는 기한이 없다. 당첨자 화면에는 "확인하는 분의 화면에 초록불이 켜졌습니다". 실패면 빨간 "본인 확인에 실패했습니다"와 이유.
- **판정은 늘 확인하는 사람의 기기에서** 한다. 당첨자 화면이나 그 스크린숏은 증거가 아니다.
- **별 세 개를 ECDH로 뽑는 이유**: 요청 문구와 서명만으로 뽑으면 둘 다 서버를 거치므로, 서버(나 응답을 엿본 누구든)가 별을 알아 가짜 당첨자에게 넘길 수 있다. 양쪽 기기가 요청마다 임시 P-256 ECDH 열쇠를 만들어 공개 열쇠만 주고받으면 공유 비밀은 두 기기만 계산할 수 있어 서버는 별을 모른다. 당첨자는 서명할 문구에 양쪽 임시 공개 열쇠를 묶어(`sasChallenge`) 가운데서 열쇠를 바꿔치기할 수 없게 한다. 별 = taggedHash("stardraw/sas/v1", 공유 비밀 ‖ 요청 id)에서 당첨 번호와 같은 거절 표본으로 1~45 중 서로 다른 3개(차례 있음). 규칙 패키지 `sas.ts`, 시험 값은 Node·파이썬으로 따로 맞췄다.
- 확인 요청의 요청자 칸(`claim` 형식은 그대로)은 이름 대신 늘 "확인 링크"(`CHECK_LINK_REQUESTER`)다. 확인 문구 증명 형식과 공개 장부·기록 형식은 바꾸지 않았다.
- 확인하는 사람 기기는 확인 기록(링크 토큰 해시, 임시 ECDH 비밀 열쇠는 꺼낼 수 없는 CryptoKey로 IndexedDB 2판, 1판 묶음 기록은 버린다)을 저장해 화면을 닫았다 열어도 이어서 확인한다. 지난 회차 화면에 "확인 중인 당첨자 N건 · 별 세 개를 기다리는 중".
- **확인함 표시**: 초록불이 켜진 응모권은 확인한 날짜와 함께 확인하는 사람 기기(IndexedDB)에만 남고, 그 기기의 지난 회차 화면에서 그 응모권 옆에 "확인함 · 10/30"이 보인다. 메모 칸·「상품 드림」·메모 내보내기/들여오기는 두지 않는다(2026-10-30 사용자: "메모를 옮길 일은 없고, 어차피 패스키에 응모/당첨 모두 귀속된다").
- 전달 서버(`apps/stardraw-server` relay.ts): `POST /api/confirm/invites`(서명한 초대) · `/peek`(토큰 → 회차·응모권, 쓰였는지) · `/start`(토큰 + 확인자 임시 공개 열쇠 → 요청, 초대를 닫는다) · `/open`(응모권 id들로 열린 요청) · `/:id/answer`(서명이 맞아야 받는다) · `/:id/report`(요청을 붙인 기기의 결과 열쇠). 토큰은 주소가 아니라 본문으로만 보낸다. 요청·응답·결과 보관 **7일**. 연습 장부·데모는 같은 기기 안(localStorage) 전달로 흉내 낸다(`ConfirmRelay` 인터페이스, 초대 서명은 검사하지 않는다).

AVIF, BT.2020 + PQ(CICP 9/16/9), 10비트, 알파. 모양은 캔버스의 별과 같다(작은 원판 + 가는 십자 빛줄기 + 흐린 빛 번짐). 모든 화소의 색을 1000 nit(보통 흰색 203 nit의 약 5배)로 두고 모양은 알파로만 만든다. 처음 그림은 빛 번짐이 160 nit로 흰색보다 어두워 아래 별빛을 가리는 회색 테두리가 될 수 있었다. 밝은 원판은 캔버스의 켜진 별 가운데(약 2px)와 같은 크기다(star.byb.kr 시험: 몇 px 핵만 밝으면 눈은 넓이까지 합쳐 느껴 오히려 SDR보다 어둡게 보였다). `scripts/build-stardraw-hdr-glow.mjs`가 16비트 PNG를 직접 써서 libavif의 `avifenc`(Homebrew `libavif`)로 만든다.
  - 형식 고른 근거: Chrome(macOS)과 Safari 26(iOS 26·macOS 26, HDR 화면)이 둘 다 PQ AVIF를 HDR로 보여 준다. 게인 맵 JPEG는 Safari 26.0에서 position·transform이 걸린 img를 SDR로 그리는 버그(WebKit 301398, 뒤에 고쳐짐)가 있었고, 별빛은 하늘 위에 겹치는 그림이라 PQ로 했다. 같은 이유로 img 자체에는 위치·변형을 걸지 않고 감싸는 칸을 백분율 여백으로 놓는다.
  - 2D 캔버스는 SDR이라 HDR 그림이 잘린다. 그래서 `SkyBoard` 캔버스 위에 img로 겹친다(`hdr` 속성, `hdr-glow.ts`). WebGPU HDR 캔버스는 Chrome만이라 쓰지 않았다.
  - 강도는 `globals.css`의 `--sd-hdr-strength`(기본 1, 불투명도에 곱한다) 하나로 바꾼다. `--sd-hdr-limit`은 `dynamic-range-limit` 값(기본 `no-limit`. `constrained`는 Chrome만 알아듣고 Safari는 기본값으로 둔다, `standard`면 HDR을 끈다). 기기·OS가 HDR 밝기를 낮추면(배터리 절약, 밝기) 브라우저가 그대로 따른다.
  - 보너스 별은 빛줄기가 대각선(✕)인 `star-glow-hdr-diag.avif`를 쓴다(2026-10-31). ＋ 그림을 CSS로 돌리지 않는 것은 위 Safari 버그 때문이다. 하늘 그림이 ✕인데 HDR 그림이 ＋면 보너스가 8방향으로 빛났다(사용자 HDR 맥에서 발견, 헤드리스 시험에서는 HDR 층이 그려지지 않아 보이지 않았다).
  - 직접 보기: HDR 맥·아이폰에서 데모 → 화면 둘러보기 「1등」(맞은 별 6개가 맥동), 데모 흐름에서 「지금 추첨」 뒤 룰렛(켜지는 별마다 번쩍임). 「응모」 하늘에는 HDR이 없다.
- **응모 화면 머리와 응모권**(2026-10-30 사용자: "별 6개 고르기 화면이 응모 참여 느낌이 덜 난다", "제목이랑 부제목이 사라져서 그런 듯"): 맨 위에 첫 화면과 같은 제목 "하늘의 별 따기"와 소개 문구(`StardrawTitle`), 그 아래 "시험 15회 응모권"(회차 이름 + 응모권) 용지. 용지는 분홍빛 로또 용지 결에 칸 6개이고, 별을 고르면(하늘이든 번호 칸이든) 빈 칸이 번호 공과 별 이름으로 채워진다(작은 수부터). 채운 칸을 누르면 그 별이 빠진다. 다 채우면 테두리가 금빛으로 바뀌고 아래 큰 「응모하기」가 켜진다. 하늘 고르기·정보 칸·번호 칸·자동 단추는 그대로다. 우주인 등록 단계도 같은 제목을 쓴다.
- **영수증의 소원 한 줄**(사용자가 직접 원한 문구): 내 별 하늘 바로 아래 작고 은은하게 "내 별에 소원을 빌어 보세요". 다른 문구는 늘리지 않는다.
- **첫 화면 인사**(사용자: "인사 옆 ID 이미지 불필요해 보여"): 작은 등록증 그림을 빼고 "○○에 거주하는 ○○ 님, 안녕하세요" 문장만. 문장을 누르면 `/stardraw/id`(밑줄 없는 은은한 링크).
- **당첨 축하**(사용자: "당첨 화면에는 축하 느낌이 좀 더 나면 좋겠다"): 추첨 결과가 나오면(룰렛을 끝까지 보든 「결과 바로 보기」든) 등수가 높을수록 크게 축하한다. 계산은 `celebrate.ts`, 그림은 `Celebration.tsx`(하늘 위 `SkyBoard` `overlay`와 결과 상자).
  - 모든 등수: 맞은 내 별(2등은 보너스 포함)이 하나씩 켜진 뒤 그 별들 사이에 선이 그어져 **나만의 별자리**가 하늘 위에 생긴다. 선은 가장 왼쪽 별에서 시작해 가장 가까운 별을 하나씩 잇는 최소 신장 트리라 겹치지 않고, 같은 별이면 늘 같은 모양이다. HDR 화면이면 별이 켜지는 순간마다 HDR 번쩍임(hdr-glow.ts flash에 `delay`)이 겹치고, 그 뒤 맞은 별 맥동은 예전 그대로.
  - 별자리 별도 하늘의 별과 같은 결(작은 점 + 흐린 빛 번짐 + 가는 십자 빛줄기). 별자리가 다 생기면 별마다 십자 빛줄기가 길게 뻗었다 사라진다(4·5등 한 번, 1~3등 두 번). 5·4등은 여기까지(가볍게).
  - 3등 이상: 별똥별이 하늘을 가로지른다(3등 3개, 2등 6개, 1등 18개의 별똥별 비). 자리는 늘 같다.
  - 1~3등: 마지막에 등록증 직인과 같은 붉은 용골자리 인장에 "당첨"을 새긴 **카노푸스 우주국 당첨 직인**이 결과 상자에 위에서 내려와 찍힌다. 그 순간 안드로이드는 `navigator.vibrate`로 짧게 떨린다(1등은 세 번, 지원하지 않으면 없는 일). 1등은 결과 상자가 예전처럼 은은하게 빛난다.
  - 축하 문구는 등수 표시("1등 당첨"·맞은 별 수)뿐이다.
  - 움직임은 모두 CSS 지연(연출 시작부터의 ms)으로 내서 화면이 늦게 그려져도 차례가 어긋나지 않는다. 떨림만 `Clock`으로 잰다. 움직임 줄이기면 처음부터 별자리와 직인이 다 보이고 고리·별똥별·번쩍임·떨림은 없다.
  - 직접 보기: 데모 → 화면 둘러보기 「1등」「3등」「5등」(2·4등도 있다).
- 반짝임 빈도: 번호 별은 평균 약 1초에 하나, 별자리 선의 어두운 별은 약 1.5초에 하나(더 약하게), 유성은 8~22초마다. `Clock` 타이머로 낸다.
- 글꼴은 게임 센터와 같은 기본 고딕. 회차·시각·응모권 번호·번호 공 숫자만 고정폭(tabular-nums)으로 영수증 느낌을 낸다.

### 11-4. 나중에: 게임 한 판 = 응모권 한 장

- 혼자 하는 게임은 기기 안에서 돌아 "했다"는 것을 증명할 수 없다. 화면을 고치면 판을 안 해도 응모권을 받는다.
- 온라인 대전은 두 사람이 서명한 기록이 있어 조금 낫지만, 둘이 짜면 똑같다.
- 그래서 "게임 한 판 = 작업 증명 대신 쓰는 비용"으로 보되, 응모권 상한(열쇠당 회차 1장)은 그대로 둔다. 그때 다시 설계한다.

### 11-6. 시험 운영과 정식 시작: 이어지는 장부(2026-10-30 사용자: 장부를 새로 만들지 않고 하나의 사슬을 끝까지 잇는다)

처음에는 "시험 장부를 지우고 정식 장부를 새로 만든다(패스키 등록만 옮김, `start-live`)"로 정했다가 2026-10-30 바꿨다. 시험 회차도 영원히 남고, 정식 시작은 장부 안의 일정 바꾸기다. `start-live`와 등록 옮기기(`carried`)는 코드·시험·문서에서 지웠다.

**단계(phase)**
- 일정표 한 줄(`ScheduleEntry`)에 `phase: "trial" | "live"`를 둔다. 줄 바이트 끝에 u8(0 없음, 1 시험, 2 정식)로 실려 genesis 해시와 기록 해시에 묶인다.
- 서버의 새 장부는 시험 단계 한 줄로 시작한다(`STARDRAW_ROUND_SECONDS`, 기본 10분. `STARDRAW_EPOCH`을 비우면 띄운 뒤 첫 맞춘 마감이 1회차 마감).
- 정식 시작 = 일정 바꾸기 한 줄 추가(`fromRound`, length 3600, closeMargin 5, 작업 증명 목표값, `phase: "live"`). 기존 일정 바꾸기 규칙(3회차 예고, 11-17)을 그대로 따라 3회차 전에 장부에 예고된다.
- 규칙(`checkSchedule`·`checkScheduleChange`): 단계는 모든 줄에 있거나(서버 장부) 모두 없다(기기 안 연습 장부). 정식 단계 뒤로 시험 단계를 둘 수 없다.
- 서버는 `STARDRAW_MODE` 없이 장부의 지금 단계를 따른다. `/api/state`의 `mode`(지금 회차 단계)로 화면이 시험 띠를 띄우고, `liveFrom`(정식 첫 사슬 회차, 없으면 null)을 함께 준다. 시각 인증은 단계와 상관없이 켠다.

**보이는 회차 번호**
- core `displayRound(schedule, round)` 하나로 화면·검사기·검증 페이지가 같이 쓴다: 정식 단계 첫 회차가 "정식 1회", 그 앞은 "시험 n회", 단계가 없으면 "n회". 화면은 연습 장부에서 예전처럼 "제 n회"를 보인다(`round-label.ts`).
- 데이터의 기준은 늘 사슬 회차 번호(`round`)다: 기록, 공유 주소(`/stardraw/ticket#<회차>-…`), 앵커 경로.
- 화면의 원격 장부(`RemoteLedger.schedule`)는 처음 일정표에 닫힌 기록의 일정 바꾸기를 모두 반영한 일정표다(정식 단계부터 회차 길이가 1시간으로 바뀐다).

**다시 시작 막기**
- 서버는 장부를 처음 만들 때 앵커 저장소 main 브랜치에 `genesis.txt`(장부 id, genesis 해시, epoch)를 한 번 커밋한다. 이미 다른 내용이 있으면 덮어쓰지 않고 1분마다 다시 시도하며 기록을 남긴다(사람이 봐야 한다).
- 검사기(`verifyLedger`의 `genesisAnchorVerifier`, anchor.ts `githubGenesisVerifier`)는 장부의 처음 일정표가 그 파일과 같은지 본다. 다르면 "장부를 다시 시작했다"로 실패, 없으면 건너뜀. 규칙 "이 장부는 다시 시작하지 않는다"는 검증 페이지에도 적었다.
- 회차 앵커 브랜치는 그 회차의 단계로 정한다(시험 `trial`, 정식 `main`, `anchorBranch`). 검사기도 같은 규칙으로 읽는다.

**정식 예약 명령**
- `node server.mjs schedule-live --from <ISO, x:55> [--round-seconds 3600]`: 돌고 있는 서버의 데이터 폴더에 예약만 넣는다(`pendingChange`). 명령은 먼저 규칙을 확인한다: 시험 단계 장부인지, 이미 정식 단계가 있거나 예약이 있는지, 시작이 정각 추첨에 맞는지(1시간이면 x:55), 시험 회차가 열리는 시각인지, 다음에 닫히는 기록(지금 닫힌 기록 수 + 1) 회차 + 4회차 이후인지(3회차 예고).
- 서버는 다음 회차 기록을 닫을 때 예약을 기록의 `scheduleChanges`에 싣고 지운다. 그사이 늦어져 예고 규칙에 맞지 않으면 싣지 않고 지운 뒤 기록을 남긴다(다시 예약해야 한다).
- 절차는 `deploy/stardraw/README.md`.

### 11-7. 봉인 시각 증명과 앵커(2026-10-30)

**공개 시각 인증 기관(RFC 3161 TSA) 여러 곳**(사용자 결정: Rekor 대신. Rekor 공개 인스턴스는 공급망 서명용 공공 서비스라 이 쓰임이 애매하고, 시험용 로그는 보장이 없다)
- 서버(`TsaRootLog`): 마감 직후 `SHA-256(봉인 값)`을 담은 TimeStampReq(인증서 함께, nonce 없음)를 기관들에 동시에 보낸다(10초 제한). 받은 토큰은 검사기와 같은 규칙(`verifyTimestampToken`)으로 먼저 확인해 맞는 것만 싣는다. 서로 다른 기관 `STARDRAW_TSA_MIN`곳 이상이면 봉인 성공, 모자라면 다음 진행 때 모두에게 다시 묻는다. 마감 + 3분까지 모자라면 무효 회차.
- 기본 기관: **DigiCert**(`http://timestamp.digicert.com`), **Sectigo**(`http://timestamp.sectigo.com`). 둘 다 2026-10-30 실제로 SHA-256 요청에 응답(Granted)하는 것을 확인했다. FreeTSA(`https://freetsa.org/tsr`)도 응답하지만 개인 운영이라 검사기 목록에만 두고 서버 기본에서는 뺐다.
- **최소 기관 수 기본 1**: 기관 한 곳이 멈추거나 느려도 회차가 무효가 되지 않게 하는 쪽(가용성)을 골랐다. 서버는 늘 두 곳에 묻고 받은 것을 모두 싣기 때문에, 평소에는 두 기관 토큰이 함께 남아 두 기관이 함께 거짓말하지 않는 한 시각을 바꿀 수 없다. 커피 규모에서 한 기관과 운영자가 짜는 위험은 감수한다. 더 엄격히 하려면 `STARDRAW_TSA_MIN=2`(검사기 규칙의 기본은 1이라 화면 판정은 그대로다).
- 장부 형식(`seals/N.json`의 `log`): `{ kind: "tsa", tokens: [{ tsa, genTime, token }] }`. `token`은 ContentInfo DER의 표준 base64, `genTime`은 토큰 안 시각(초, 소수점 아래 버림)을 사람이 읽기 쉽게 함께 적은 것이다. `rootLoggedAt` = 가장 이른 `genTime`.
- 검사(`packages/stardraw-core/src/tsa.ts`, 브라우저에서도 WebCrypto): 토큰마다 ① messageImprint가 SHA-256이고 값이 `SHA-256(봉인 값)` ② 서명된 속성의 messageDigest·contentType ③ 서명(RSA PKCS#1 v1.5 SHA-256/384/512, ECDSA P-256/384/521) ④ 서명 인증서에서 올라가며 서명을 확인해 고정한 공개 열쇠(인증서 SPKI DER의 SHA-256)에 닿는지 ⑤ 그 아래 인증서가 `genTime`에 유효한지 ⑥ 서명 인증서가 시각 인증용(EKU timeStamping)인지 ⑦ 적어 둔 `genTime`이 토큰과 같은지. 실린 토큰은 모두 맞아야 하고 서로 다른 기관 `DEFAULT_TSA_MIN`(1)곳 이상, 가장 이른 시각이 기록의 `rootLoggedAt`과 같아야 한다. drand 시각과의 앞뒤는 무효 회차 규칙(`isVoidRound`)이 본다.
- 고정한 열쇠(루트 SPKI SHA-256): DigiCert Trusted Root G4 `59df317bfa9f4f0ab7ca514d7772296aa2c765b87664d08b96e57399e364729c`, Sectigo Public Time Stamping Root R46 `a4db8668c6796ebf476ddc5ace453a9260dbd4dbb09f51ecec9a839003824795`, FreeTSA Root CA `52c54ba340885605314daa1857c8763b94087d05c636092938d4e2d1818e99b5`. 기관이 루트를 바꾸면 core에 새 열쇠를 더한다(옛 열쇠는 지난 회차 검사를 위해 남긴다).
- 묶음 크기 때문에 pkijs/asn1js를 들이지 않고 필요한 만큼의 DER 읽기를 직접 썼다(`der.ts`). 시험은 세 기관에서 실제로 받아 둔 토큰(`tsa.fixtures.ts`)으로 네트워크 없이 돌고, 회차 봉인 값을 담은 토큰은 시험용 가짜 기관(`@mighty/stardraw-core/testing`의 `FakeTsa`)이 만든다.
- Rekor(`rekor.ts`, `RekorRootLog`)는 꺼 둔 선택지로 남긴다: `STARDRAW_TSA=off`이고 `STARDRAW_REKOR_URL`이 있을 때만 쓴다(시험 운영은 rekor.sigstage.dev만, 정식은 rekor.sigstore.dev만). 2026-10-30 시험용 로그에 실제로 한 번 올려(uuid `71d46696…0e3`, integratedTime 1793324413) 검사기가 맞는 것을 확인했다.

**GitHub 앵커**(사용자 승인, 저장소 `ybbarng/stardraw-ledger` 공개)
- 회차가 닫힐 때마다 커밋 하나를 남긴다: `ledgers/{장부 id}/{회차 6자리}.txt`. 장부 id는 genesis 해시 앞 16자리라 시험 장부를 새로 시작해도 섞이지 않는다. 같은 커밋에 그 회차의 장부 JSON 사본도 함께 올린다(11-16, git tree/commit API. 사본이 없으면 예전처럼 Contents API 한 번).

### 11-8. 화면 코드를 덜 믿게: 터미널 검사기, 재현 빌드, 화면 코드 해시(2026-10-30)

"막지 못하는 것" 가운데 "화면 코드는 운영자가 내준다"(8-1 O5)를 줄인다. 화면 코드를 바꿔 패스키로 몰래 서명하게 하는 일 자체는 여전히 막지 못하지만, 사이트가 내준 코드가 공개 저장소의 어느 커밋인지 누구나 비교할 수 있고, 장부 검사는 화면 없이 할 수 있다.

**터미널 검사기 `stardraw-verify`**(`packages/stardraw-cli`)
- 계산은 core의 `checkPublicLedger` 하나로 검증 페이지와 같다(`verifyLedger`, quicknet BLS, TSA `verifyTsaProof`, 앵커 `githubAnchorVerifier`·`githubGenesisVerifier`). 페이지에 있던 공개 장부 검사 코드를 core로 옮겼다.
- 앵커는 서버를 거치지 않고 raw.githubusercontent.com에서 `ybbarng/stardraw-ledger`를 직접 읽는다(처음 일정표 main, 시험 회차 trial, 정식 회차 main).
- 명령
  - `stardraw-verify [서버 주소]`(기본 `https://game.byb.kr/stardraw-api`, 장부는 기본으로 앵커 저장소 사본에서 받는다. `--source server|<폴더>`, `--compare`, 11-16): 회차별 한 줄(보이는 회차, 마감, 응모 수, 당첨 번호 또는 무효, 그 회차의 문제·건너뜀)과 항목별 통과·실패·건너뜀. `--pow-sample n`, `--pow-all`, `--anchor-repo`, `--no-anchor`, `--json`.
  - `--ticket <회차-일련번호>`(여러 번): 영수증 앞 12자리나 공유 주소를 그대로 받는다. 장부에서 찾아 머클 증명, 등수, 작업 증명(전부)을 본다.
  - `stardraw-verify site [사이트]`(기본 `https://game.byb.kr`): 아래 해시 목록과 사이트 파일, `--build <out>`이면 직접 빌드한 파일을 비교한다. 기본 범위는 하늘의 별 따기 페이지(HTML·화면 전환용 .txt), 모든 화면 코드(`_next/`), 서비스 워커. `--all`은 목록 전부(그림 포함).
  - 끝 상태: 0 통과(건너뜀 포함), 1 어긋남, 2 사용법·네트워크 오류.
- 실행: 저장소를 받아 `pnpm install` 뒤 맨 위 폴더에서 `pnpm stardraw-verify [인자]`(묶고 바로 돈다). 묶은 파일 `dist/stardraw-verify.mjs` 하나만 있으면 Node 24로 저장소 없이도 돈다.
- 시험은 2026-10-30 시험 서버에서 받아 둔 실제 장부·앵커 파일(`src/fixtures/`)로 네트워크 없이 돈다. 진짜 drand 서명과 DigiCert·Sectigo 토큰이라 실제 검사 경로 그대로다.
- npm 발행은 준비만 했다(바깥 발행이라 사용자 확인 뒤): `package.json`에 `bin`·`files`·`engines`를 두었다. 발행하려면 이름을 정하고(예: `stardraw-verify`, `@mighty/*`는 npm에 없는 범위), `private`을 빼고, `pnpm -C packages/stardraw-cli build` 뒤 `npm publish --provenance`(GitHub Actions에서 하면 어느 커밋에서 묶었는지 npm에 남는다). core가 작업 공간 패키지라 묶은 파일만 올린다.

**재현 빌드**
- 흔들리던 것은 Next 빌드 id 하나였다(빌드마다 무작위, HTML·화면 전환 파일·`_next/static/<id>/`에 들어간다). `next.config.ts`의 `generateBuildId`를 빌드한 커밋으로 바꿨다(`SOURCE_COMMIT`, 없으면 `git rev-parse HEAD`). 커밋이 바뀌면 `_next/static/<id>/` 주소도 바뀌어 오래 두는 캐시와 섞이지 않는다.
- 확인: 같은 폴더에서 두 번(캐시 지우고), 다른 경로(worktree)에서 한 번 빌드해 `out/` 전체가 같았다. 배포된 사이트(Linux Docker 빌드, c8ea466)를 이 맥에서 같은 빌드 id로 다시 빌드하니 295개 가운데 293개가 같았고, 다른 둘은 공유 미리보기 그림(`opengraph-image/share.png`, `gostop/opengraph-image/share.png`)이었다. 그림 그리기가 운영체제에 따라 조금 다른 것으로 보고, 코드가 아니어서 검사기 기본 범위에서는 뺀다(하늘의 별 따기 공유 그림은 같았다).
- 같은 파일을 얻는 조건: 같은 커밋, 같은 빌드 변수(`NEXT_PUBLIC_*`, 해시 목록 `env`에 적힌다), 깨끗한 작업 트리(`apps/web/public/cards-local/`처럼 저장소에 없는 파일이 있으면 그만큼 더 생긴다), lockfile대로 설치. Node 판은 목록에 참고로 적는다.

**화면 코드 해시 목록**
- 빌드 끝에 `apps/web/scripts/build-hashes.mjs`가 `out/`의 모든 파일 SHA-256을 `out/build-hashes.json`에 적는다: `commit`, `dirty`, `env`, `node`, `files`(경로 → 해시, 바이트 순), `digest`(files를 sha256sum 형식 `"<hex>  <경로>\n"`으로 적은 글의 SHA-256). 우리 도구 없이도 `out/` 안에서 `jq -r '.files|to_entries[]|"\(.value)  \(.key)"' build-hashes.json | sha256sum -c`로 확인할 수 있다.
- 어디에 두나(되돌리기 쉬운 쪽부터)
  1. **사이트 `/build-hashes.json`**(켬): 빌드 결과에 들어가 배포와 함께 바뀐다. 사이트가 "지금 어느 커밋을 내주는지" 밝히는 곳이고, 검사기가 여기서 시작한다. 운영자가 내주는 파일이라 그 자체로는 증거가 아니다. 직접 빌드한 해시와 맞아야 의미가 있다.
  2. **Image 워크플로 기록**(켬): Docker 빌드에서 같은 파일을 꺼내(`hashes` 단계) 실행 요약에 digest를 적고 기록 파일(90일)로 남긴다. 이 저장소 안의 일이라 새로 바깥에 공개하는 것이 아니다.
  3. **재현 확인 작업 `reproduce`**(켬): 배포마다 Docker 밖(러너의 Node + pnpm)에서 같은 커밋·같은 빌드 변수로 다시 빌드해 이미지의 목록과 `--all`로 비교한다. 배포는 막지 않고 어긋나면 이 작업만 실패로 남는다.
  4. **GitHub 릴리스 `site-<커밋 앞 12자리>`**(준비만, 꺼 둠): `publish-hashes` 작업이 목록을 릴리스 파일로 올린다. 사이트 밖에 배포 기록이 남아, 운영자가 잠깐 다른 코드를 내줬다가 되돌리는 것을 나중에도 비교할 수 있다. 저장소 변수 `STARDRAW_PUBLISH_HASHES=true`로 켠다. 릴리스는 지우면 그만이라 되돌리기 쉽다.
  - 버린 안: 앵커 저장소(`ybbarng/stardraw-ledger`)에 남기기. 장부 기록과 섞이고, Actions에 다른 저장소 쓰기 토큰을 새로 넣어야 한다.
- 확인하는 순서: ① `stardraw-verify site`로 사이트 파일이 목록과 같은지 ② 목록의 커밋을 받아 같은 빌드 변수로 `pnpm --filter @mighty/web build` ③ `stardraw-verify site --build apps/web/out`. ①②③이 맞으면 사이트가 내준 하늘의 별 따기 화면 코드는 공개 저장소의 그 커밋에서 나온 것이다.

**아직 남는 한계**
- 내 브라우저가 받은 파일이 검사기가 받은 파일과 같다는 보장은 없다. 운영자가 사람마다·때마다 다른 파일을 내주면 검사기로는 그때 받은 것만 비교된다. 서비스 워커가 저장해 둔 옛 파일을 쓰는 동안에도 마찬가지다.
- 패스키 서명은 여전히 브라우저 화면 코드가 시킨다. 응모·증명은 브라우저 패스키로만 하므로(11-10) 이 한계는 남는다.

### 11-9. 우주인 등록과 우주인 등록증, 카노푸스 우주국(2026-10-30)

**판정은 공개 열쇠 전체와 서명으로만**
- 이름·주소·사진은 재미로 붙인 것이다. 열쇠를 많이 만들면 이름·주소·사진이 같은 등록증은 쉽게 나오고, 40비트 등록번호도 약 1조(2^40) 번이면 맞출 수 있다. 그래서 응모·당첨자 확인 판정은 언제나 공개 열쇠 전체와 서명으로 하고, 등록번호로 무언가를 판정하는 코드는 두지 않는다.
- **효력은 서명에서 나온다**: 진짜 "우주국 관인"은 서버 서명 열쇠의 서명이다(영수증 등). 등록증의 붉은 직인은 꾸밈이다. 앞으로 우주국이 직접 보내는 것(공지, 정식 시작 예고 등)은 서버 서명 열쇠로 서명하고, 화면이 장부 genesis의 서버 공개 열쇠로 확인했을 때만 관인 표시를 붙인다. 지금 있는 것 가운데 그런 것은 없고, **당첨자 확인 요청에는 관인이 붙지 않는다**(우주국은 전달만 한다). 당첨 안내는 서버가 보내지 않고 기기가 장부로 계산한다.

**남의 등록증은 그리지 않는다**
- 등록증은 공개 열쇠에서 누구나 계산할 수 있다(공개 가명의 성질, 이더리움 주소 아이콘처럼). 이 방식은 유지한다. 대신 **우리 화면은 남의 등록증(얼굴·이름·주소)을 그려 주지 않는다**: 지난 회차, 당첨자 목록, 검증 페이지, 당첨자 확인 화면 어디에도 띄우지 않고, 이 기기의 내 등록증만 보인다(데모는 가짜 우주인). 기존 "응모자 신원 표시 없음" 결정을 등록증에도 적용한 것이다. 그래서 공유도 공개 열쇠 주소 대신 인사 문구와 첫 화면 주소만 보낸다.
- 버린 안: WebAuthn PRF 확장으로 기기만 아는 값에서 등록증을 만들어 예측을 막기. 지원이 브라우저·인증기마다 고르지 않고, 공개 열쇠를 그대로 보여 주는 의도와 부딪힌다.

**개인정보**
- 공유 단추 아래 한 줄: "등록증을 보여 주면 장부 속 응모가 내 것인 줄 알 수 있습니다."
- **공개 열쇠는 앞면·공유에서 빼고 등록증 뒷면에 가려 둔다**(2026-10-30 사용자). 등록증 그림을 나눌 때 글자 검색으로 장부 속 응모가 바로 찾히는 것을 막는다. 등록번호로도 장부의 열쇠를 하나씩 계산해 보면 찾을 수 있다는 한계는 남는다.
  - 카드를 옆으로 세게 밀거나(카드 너비의 35% 넘게) 「뒷면 보기」를 누르면 3D로 뒤집힌다. 움직임 줄이기면 돌지 않고 바로 바뀐다. 앞면은 주인 확인, 뒷면은 열쇠 꺼내 보기로 역할을 나눈다.
  - 뒷면: 공개 열쇠 바이트에서 정해지는 별 무늬(`key-art.ts`, 꾸밈), 가린 공개 열쇠 줄(●●●●), "카노푸스 우주국". 가린 줄을 누르면 앞면 주인 확인과 같은 본인 확인(그 등록증의 패스키, 기기 안에서 확인) 뒤 공개 열쇠·복사 단추와 "이 값으로 장부 속 내 응모를 찾을 수 있습니다" 한 줄. 30초 뒤나 다시 뒤집으면 가린다. 실패·취소면 조용히 그대로. 데모·화면 둘러보기는 흉내 패스키로 같은 흐름.
  - 이것은 보안이 아니라 실수 방지다(캡처·어깨너머). 공개 열쇠는 장부와 기기 저장소에 있어 비밀이 아니다. 그래서 화면 말도 "잠금"이 아니라 "꺼내 보기 전에 본인 확인"으로 가볍게 쓴다.
- 공개 열쇠는 가명이다. 가명도 사람과 이어지면 개인정보가 된다. 우리는 장부 밖에서 가명을 사람과 잇는 정보(이름·이메일·전화번호)를 받지 않는다. 응모 제한용 IP는 앞부분(IPv4 /24, IPv6 /48)만 메모리에서 센다. 장부는 고칠 수 없어 지울 수 없다는 한계가 있다. 이어지지 않게 하려면 새 우주인으로 다시 등록하면 그때부터 이어지지 않는다. 설명 페이지 "우리가 저장하는 것"(/stardraw/about#privacy)에 쉬운 말로 적었다.

**당첨자 확인 승인과 장난 요청**
- 당첨자 기기: "보낸 확인 링크로 n회 k등 당첨 확인 요청이 왔습니다", 작게 "○시에 만든 링크 · 전달: 카노푸스 우주국". 우주국은 배달한 곳으로만 적고 요청 주체처럼 쓰지 않는다. 「등록증으로 승인」을 누르면 내 등록증 카드가 나타나 확인을 받고(본인 확인과 같은 움직임), 별 세 개가 빛난다. "별 세 개는 내가 당첨을 알린 그 사람에게만 보내세요" 한 줄과 "우주국은 전달만 하고 별 세 개는 모릅니다"(임시 ECDH).
- 2026-10-30 확인 링크로 다시 설계(11-2): 요청은 당첨자가 만든 링크로만 붙어 요청 폭탄·칸 채우기가 없다(8-1 P7). 이름 칸과 이름 사칭 검사(core `requesterProblem`, "우주국·국장·카노푸스·운영")는 이름 칸과 함께 없앴다(P8). 상한: IP 앞부분마다 하루 링크 만들기 100번(`STARDRAW_INVITES_PER_PREFIX`, 2026-10-30 30→100, 옛 `STARDRAW_CONFIRMS_PER_PREFIX`는 없앴다), 없는 링크 조회 60번, 응모권당 열린 링크 10개. 링크를 받은 사람이 다른 확인자에게 별을 넘겨 당첨자인 척하는 것은 "별 세 개는 알린 그 사람에게만" 한 줄로 막는다. 판정(서명·별 세 개)은 그대로다.

**나중에(아이디어, 만들지 않음)**: 우주국 창구·관인 공지·명예의 전당. 행사·상품이 생기면 본다(map.json next-lotto의 아이디어).

### 11-10. 본인 확인 표시, IP 상한, 터미널 도구의 범위(2026-10-30)

시험 서버가 돌고 있지만 응모가 0장일 때 정했다. 그래서 응모 검사 규칙을 바꿔도 지난 기록이 걸리지 않는다(장부는 다시 시작하지 않았다).

**패스키 서명마다 UV 표시를 요구한다**
- 규칙: 패스키 서명의 authenticatorData flags에 UP(0x01)와 UV(0x04)가 모두 켜져야 한다(core `checkAuthenticatorData`, `FLAG_UP`·`FLAG_UV`). 다른 비트(BE·BS·AT·ED)는 보지 않는다. 응모권, 별명, 당첨자 확인 승인, 확인 링크 만들기 등 `verifyEntrantSignature`를 거치는 모든 서명에 같이 걸리고, 서버·검증 페이지·터미널 검사기(`verifyLedger`·`checkPublicLedger`)가 같은 코드라 규칙도 같다. 시험 값에 "패스키 authenticatorData" 묶음을 더했다.
- 이유: 화면은 늘 `userVerification: "required"`로 부르는데 검사는 UP만 봐서, 장부만 보고는 본인 확인을 거쳤는지 알 수 없었다. 이제 진짜 패스키로 낸 응모는 매번 지문·얼굴·PIN을 거쳤다고 장부가 보장한다.
- 한계: 개발자용 가상 인증기(브라우저 개발 도구, 소프트웨어 인증기)는 UV 표시도 꾸밀 수 있다. 그래서 이 규칙은 자동화를 막지 못한다. 진짜 인증기로 낸 서명의 뜻을 분명히 할 뿐이다.
- 등록에는 서명이 없어 장부가 UV를 볼 수 없다. 첫 응모권 서명이 UV를 요구하므로 UV 없이 만든 패스키는 응모할 수 없다. 화면은 만들 때 받은 authenticatorData에 UV가 없으면 미리 막는다(`hasUserVerification`).
- 시험용 가짜 인증기(core `testing.ts` `fakePasskey`, 기본 0x05)와 배우기의 흉내 패스키(`lab.ts` `demoAssertion`)는 UP·UV를 함께 켠다. 배우기 패스키 흉내에서 "지문·얼굴·PIN 없이 서명"을 고르면 UP만 켜져 검사기가 거절한다. 데모 지갑도 흉내 패스키(UP·UV)로 서명한다(11-11).
- ~~원시 열쇠(kind 1)는 규칙에 남아 있어 UV 없이 응모할 수 있다~~ → 같은 날 규칙과 서버에서 막았다(11-11).

**응모는 브라우저 패스키로만, 터미널 도구는 검사 전용**
- 처음 계획한 터미널 응모(`enter`, 열쇠 파일, 자동 응모), `status`, `claim`, `confirm`은 뺐다. `packages/stardraw-cli`는 장부·화면 코드 검사(`stardraw-verify`)만 하고 열쇠를 다루지 않는다. 문서·배우기·설명·검증 페이지의 "터미널로 응모·증명" 언급을 고쳤다.
- 그래서 "패스키 서명은 화면 코드가 시킨다"(8-1 O5)는 한계로 남는다. 줄이는 길은 재현 빌드와 화면 코드 해시 비교(11-8)다.

**IP 앞부분 상한 기본값: 공유 IP 기준으로 넉넉히**
- 서버 기본값(`apps/stardraw-server/src/config.ts` `DEFAULT_PREFIX_LIMITS`): 하루 새 열쇠 등록 10→**200**(`STARDRAW_REGISTRATIONS_PER_PREFIX`), 회차 응모 20→**200**(`STARDRAW_ENTRIES_PER_PREFIX`), 하루 확인 링크 만들기 30→**100**(`STARDRAW_INVITES_PER_PREFIX`). 시험 서버 compose는 이미 이 값이었다.
- 이유: 회사·학교·통신사 NAT/CGNAT에서는 외부 IP 하나를 여럿이 쓴다(사용자: 회사 외부 IP 1개에 직원 100명 넘음). IP는 사람·기기 식별자가 아니라 낮은 상한은 정상 사용자끼리 몫을 깎고, 공격자는 다른 네트워크·클라우드 주소로 쉽게 옮긴다. IP 상한은 서버 자원을 지키는 넉넉한 안전장치이고 남용 방지의 1차 수단이 아니다. 응모 비용은 작업 증명이 맡는다.
- 막지 못하는 것(배우기 "막지 못하는 것"에 적음): 마음먹은 한 사람은 같은 네트워크에서 하루 새 우주인 200명·회차당 200장, 네트워크를 여럿 쓰면 더 낼 수 있어 혼자 수백 배 확률을 가질 수 있다. 비용은 작업 증명뿐이다. 가상 인증기로 만든 열쇠는 구별할 수 없고, 기기 증명(attestation)을 요구하면 가릴 수 있지만 동기화 패스키(iCloud 키체인, 구글 비밀번호 관리자, 1Password)는 기기 증명을 주지 않아 요구하지 않는다. 상품을 걸려면 추첨 전, 등록할 때 신원을 묶어야 한다. 당첨자만 신원을 확인하는 것은 소용없다(당첨된 열쇠 주인 한 명만 진짜면 된다).

**프록시 헤더(`X-Real-Ip`)는 위조할 수 없다**
- 서버는 `STARDRAW_TRUST_PROXY=1`이면 `X-Real-Ip`로 IP를 센다(`http.ts` `clientIp`). 운영 Traefik은 v3.7.16이고 바깥 80·443을 직접 받으며, 진입점에 `forwardedHeaders`(`trustedIPs`·`insecure`)를 두지 않았다(servers 저장소 `byb.kr/traefik/traefik.yml`). 회차 서버 컨테이너는 `ports`가 없어 `web` 네트워크 안에서만 닿는다(`byb.kr/apps/stardraw/compose.yaml`).
- Traefik v3.7.16 소스 `pkg/middlewares/forwardedheaders/forwarded_header.go`: 믿는 주소가 아니고 insecure도 아니면 `DeleteXForwardedHeaders`가 들어온 X-Forwarded-*와 `X-Real-Ip`(밑줄 변형 `X_Real_Ip` 포함)를 지우고, `rewrite`가 `X-Real-Ip`를 실제 접속 주소(RemoteAddr)로 넣는다. 공식 문서(entryPoints `forwardedHeaders`)도 `insecure` 기본 false, `trustedIPs` 기본 없음이다. 그래서 클라이언트가 보낸 `X-Real-Ip`는 서버에 닿지 않는다. 코드는 그대로 두고 주석에 근거를 적었다.
- 전제가 깨지는 경우: Traefik 앞에 CDN 같은 다른 프록시를 두면 그 프록시만 `trustedIPs`로 믿게 함께 바꿔야 한다(아니면 모두가 CDN 주소 하나로 세어진다). `web` 네트워크의 다른 컨테이너는 서버에 직접 붙어 헤더를 꾸밀 수 있지만, 그 컨테이너는 운영자가 띄운 것이다.

### 11-11. 원시 열쇠를 받지 않는다(2026-10-30)

사용자와 정한 방향: 응모는 브라우저 패스키로만, 터미널 응모 도구는 만들지 않는다, 모든 설계는 상품이 걸린 것을 전제로 한다. 11-10에 남은 한계(원시 열쇠로는 UV 없이 응모할 수 있다)를 같은 날 막았다. 시험 서버가 돌고 있지만 응모 0장·등록 0개라(받아 둔 장부 `packages/stardraw-cli/src/fixtures/live-ledger-2026-10-30.json`, 시험으로 확인) 지난 기록이 걸리지 않는다. 장부는 다시 시작하지 않았다.

**규칙**
- 등록 kind 1과 응모자 서명 kind 1은 바이트를 읽는 단계(core `decodeRegistration`·`readSignature`)에서 `RawKeyRejected`로 거절한다. 그래서 응모권·별명·당첨자 확인 승인·확인 링크·`verifyLedger`·`checkPublicLedger`(장부를 받을 때 거절)가 모두 같은 코드로 막힌다.
- 형식에서 kind 바이트는 없애지 않고 값 2만 받는다. 고른 근거: ① 이미 장부에 실렸거나 앞으로 실릴 패스키 등록·서명 바이트가 그대로 읽히고 id·머클 루트가 바뀌지 않는다. kind 바이트를 없애면 형식이 달라져 공개 장부 호환이 깨지고 장부를 다시 시작해야 한다. ② 검사 단계(`verifyEntrantSignature`가 false)가 아니라 읽는 단계에서 막아, 타입(`SignatureData`, `KeyRegistration`)에서 원시 열쇠가 아예 사라지고 코드가 단순해졌다(`KeyKind`, 등록의 `kind` 필드, `makeRegistration`의 kind 인자를 없앰). ③ 나중에 다른 서명 모양이 필요하면 새 kind 값으로 늘릴 수 있다.
- 서버 영수증의 서버 열쇠 서명(원시 64바이트)은 응모자 서명이 아니라 그대로다.

**서버**: 원시 열쇠 등록이나 서명이 든 응모는 400 "패스키로만 응모할 수 있습니다. 직접 만든 열쇠는 받지 않습니다", 원시 서명 확인 링크는 400 "패스키로 서명한 확인 링크만 받습니다". 당첨자 확인 승인은 원래대로 403(서명이 아니다).

**원시 열쇠를 쓰던 곳을 흉내 패스키로**
- core `softPasskeySigner(signer, { policy, flags })`: 기기 안 P-256 열쇠로 브라우저와 같은 모양의 단언을 만든다(기본 UP·UV, 실제 사이트 정책). 패스키 번호는 공개 열쇠에서 정해지므로(`softCredentialId`, 16바이트) 열쇠 쌍만 저장해도 같다.
- 시험 도구(`testing.ts` `signers`·`registerKeys`·`fakePasskey`), 서버 시험 참가자, 연습 장부의 컴퓨터 참가자(이 페이지 주소 정책), 데모 지갑(흉내 확인 시트는 그대로), 둘러보기, 배우기(서명 상자, 별 세 개, 공격해 보기)가 모두 흉내 패스키를 쓴다. 검사기는 흉내 패스키를 진짜와 구별하지 못한다(가상 인증기와 같다, 11-10). 연습 장부·데모는 기기 안에서만 도는 흉내라 상관없다.
- 연습 장부 저장 판을 1→2로 올렸다. 판 1에는 컴퓨터 참가자의 원시 열쇠 등록이 있어 읽지 않고 새로 시작한다(지갑은 다른 장부 표시의 응모권을 세지 않는다).
- 공개 시험 값(`vectors.ts`, /stardraw/verify): 응모권 바이트를 패스키 서명으로 바꾸고, 고정 열쇠(WINNER_JWK)로 미리 한 서명의 확인(true), 원시 서명·원시 열쇠 등록 거절을 더했다. 원시 열쇠 등록 바이트·id 값은 뺐다. 검증 페이지 규칙 글도 고쳤다.

**남는 것**: 가상 인증기·흉내 패스키로 스스로 프로그램을 짜는 사람은 여전히 UV 표시를 꾸밀 수 있다(11-10). 이번 일은 "규칙이 허용한 우회로"를 닫은 것이고, 열쇠를 여럿 만드는 비용은 여전히 작업 증명뿐이다(5절).

### 11-12. 우주국장 관리 화면과 운영 기록(2026-10-30)

사용자와 정한 방향: 앞으로 "소속"(예: 어느 기관 계정 도메인을 가진 사람만 받는 성단, 소속별 상품 자격)을 더한다. 소속 추가 같은 운영자 일은 서버 DB에 직접 넣지 않고 **국장 패스키로 서명한 요청 → 서버가 확인 → 공개 장부에 3회차 예고 기록**으로 한다. 정식 시작 예약(`schedule-live`, 서버 컨테이너 안 명령)도 이 길로 옮긴다. 상품 자격(블라인드 서명, 기관 계정 연동)은 이번 범위가 아니다(보류, 설계는 11-13). 시험 장부는 다시 시작하지 않고(응모 0장), 장부 형식은 **더하기만** 한다.

한 줄 원칙: **국장도 장부에 남는 기록으로만 일한다.** 서버는 국장 서명이 맞는 요청만 싣고, 실은 기록은 3회차가 지나야 효력이 생기며, 그사이 누구나 보고 국장은 취소할 수 있다.

**① 데이터의 뜻·연결·책임**

| 데이터 | 뜻 | 누가 서명 | 어디에 |
|---|---|---|---|
| 관인(서버 서명 열쇠) | 우주국 자체. 영수증에도 서명한다 | — | 첫 관인 운영 기록에서 장부에 처음 실리고 고정된다(`head.json`의 `serverKey`와 같아야 한다) |
| 국장 열쇠 | 운영자의 패스키(P-256). 여러 개 둘 수 있다 | 지정·빼기 모두 관인(서버 설정에서 온 것)이나 이미 쓰는 국장 | 운영 기록 "국장 열쇠 지정·빼기" |
| 운영 기록(operation) | 국장·관인이 서명한 일 한 건. 효력 회차가 있다 | 종류마다 정해짐 | 회차 기록 v2의 끝 칸(이 회차에 받은 것) |
| 소속 | 별·성단 이름, 배지, 신원 확인 방법 이름, 자격 열쇠 자리, 발급 수 자리 | 국장 | "소속 추가"의 운영 기록 id가 소속 id |

- 국장 열쇠는 **응모용 우주인 패스키와 따로** 만든다(같은 rpId `game.byb.kr`, 다른 패스키). 규칙으로 섞이지 않게 한다: 우주인으로 등록된 열쇠·패스키 번호는 국장으로 지정할 수 없고, 국장으로 지정된 적 있는 열쇠·패스키 번호는 우주인으로 등록할 수 없다. 그래서 국장이 응모하려면 보통 우주인처럼 다른 패스키로 등록해야 하고, 장부에서 국장의 응모는 남과 구별되지 않는다.
- 서명 형식은 응모자 서명과 같은 패스키 단언(UP·UV 필수, origin `https://game.byb.kr`, 4절)이다. 서명 대상의 용도 이름(`stardraw/op-sig/v1`)이 응모권·별명·확인 링크와 달라, 국장 서명을 응모 서명으로 돌려쓰거나 그 반대로 쓸 수 없다.
- 실제 기관 도메인 같은 비공개 값은 장부에 넣지 않는다. 소속에는 "기관 계정", "초대 코드" 같은 **방법 이름**만 싣고 실제 값은 서버 설정에만 둔다(나중에 자격 발급을 만들 때).

**운영 기록 형식**(고정 바이너리, 4절 규칙)
```
본문 = v(u8 = 1) ‖ kind(u8) ‖ after(32) ‖ effectiveRound(u32) ‖ 내용
  kind 1 국장 열쇠 지정   credentialId(u16 길이 + 1~1023바이트) ‖ pub(65)
  kind 2 국장 열쇠 빼기   pub(65)
  kind 3 소속 추가        이름(text) ‖ 배지(u8) ‖ 방법(text) ‖ 자격 열쇠(u16 길이 + 0 또는 65바이트) ‖ 발급 수(u32)
  kind 4 소속 바꾸기      대상 소속 id(32) ‖ 소속 추가와 같은 칸
  kind 5 소속 끝내기      대상 소속 id(32)
  kind 6 예고 취소        대상 운영 기록 id(32)
  kind 7 일정 바꾸기      일정표 한 줄(4절, 단계 u8까지)
운영 기록 = 본문 ‖ 서명자(u8: 1 관인, 2 국장) ‖ pub(65) ‖ 서명(관인: r‖s 64바이트, 국장: 패스키 서명 4절)
서명 대상 = "stardraw/op-sig/v1" ‖ 0x00 ‖ 본문
운영 기록 id = taggedHash("stardraw/op/v1", 본문)   (서명이 빠져 서명 모양만 바꾼 복제도 같은 id)
```
- 배지: 1 별, 2 성단, 3 성운, 4 은하. 이름·방법은 NFC로 맞춘 1~20자, 보이지 않는 글자 없음(별명 규칙과 같다). 자격 열쇠는 지금 비워 두고(0바이트) 나중에 "소속 바꾸기"로 채운다. 발급 수는 소속 추가 때 0이고 나중에 "소속 바꾸기"로 공개한다.
- **회차 기록 v2** = v1 기록 바이트 ‖ 운영 기록 [개수(u16, 1 이상) ‖ (운영 기록 u16 길이 + 바이트) × 개수]. 운영 기록이 없는 회차는 지금처럼 v1으로 쓴다. 그래서 지금까지의 기록과 해시는 그대로이고, 운영 기록이 있는 회차만 v2다. 목록은 운영 기록 id 순, 한 번씩.
- 기록 해시가 운영 기록까지 덮으므로 GitHub 앵커(기록 해시)에도 그대로 남는다. 따로 파일을 두지 않는다(공개 장부 `rounds/N.json`의 `record`에 들어 있다).

**② 꼭 지킬 규칙과 보장하는 곳**(core `operations.ts`, 검사기 `verifyLedger`와 서버가 같은 코드)

| 규칙 | 내용 |
|---|---|
| 자리 고정(재사용 방지) | `after`는 서명할 때의 장부 끝 해시다. 운영 기록은 `prev`가 그 값인 회차 기록, 곧 서명 뒤 처음 닫히는 기록에만 실릴 수 있다. 예전 서명을 다른 회차에 다시 넣으면 `after`가 맞지 않는다. 같은 기록 안에서는 id가 한 번씩이다. 서버가 일회용 challenge를 따로 낼 필요가 없고, 검사하는 사람도 장부만으로 확인한다 |
| 3회차 예고와 회차 경계 | 회차 k 기록에 실린 운영 기록의 효력 회차 E는 `E ≥ k + 4`(일정 바꾸기와 같은 규칙, 11-1·11-17). 효력은 회차 E가 열릴 때부터라 회차 중간에 바뀌지 않는다. 일정 바꾸기는 E = fromRound |
| 서명자 | 국장 열쇠 지정·빼기는 관인이나 국장. 나머지는 국장만. 국장 서명은 회차 k에 쓰는 중인 국장 열쇠(지정 효력 회차 ≤ k, 빼기 효력 전)여야 한다 |
| 관인 고정 | 장부에 처음 실린 관인 운영 기록의 열쇠가 이 장부의 관인이다. 뒤의 관인 기록은 모두 같은 열쇠여야 한다. 공개 장부 검사는 `head.json`의 서버 공개 열쇠(영수증 확인용)와도 같은지 본다 |
| 취소 | 국장. 관인은 자기가 서명한 국장 열쇠 지정만 취소할 수 있다(설정에서 뺀 열쇠, 서버가 다음 기록에 싣는다). 대상은 이미 장부에 실렸고, 아직 효력이 없고(취소가 실린 회차 < 대상 E), 취소되지 않은 운영 기록(취소 기록은 취소할 수 없다). 취소는 실리는 즉시 효력(E = 0) |
| 일정 바꾸기 | 한 번에 하나만 예고한다. 예고 중에는 다른 일정 바꾸기(옛 `scheduleChanges` 칸 포함)를 받지 않는다. 취소하면 그 줄이 일정표에서 빠진다(마지막 줄이라 앞 회차 시각은 그대로). 다른 운영 기록의 예고는 회차 수로 세므로 예고 중인 일정 바꾸기와 상관없다 |
| 소속 | 바꾸기·끝내기 대상은 이미 효력이 생겼고 끝나지 않았고 끝내기 예고도 없는 소속 |
| 국장·우주인 분리 | 위 ① |

- 서버는 국장 요청(`POST /api/director/ops`)을 받을 때 다음 기록에 실렸다고 치고 같은 규칙으로 먼저 확인해 거절하고, 기록을 닫을 때 다시 확인해 맞는 것만 싣는다(같은 함수 `selectOperations`).
- 처음 국장 지정: 서버 설정 `STARDRAW_DIRECTOR_KEYS`(`<패스키 번호 base64url>.<공개 열쇠 base64url>`을 쉼표로)에 있는데 장부에 아직 없는 열쇠를, 서버가 다음 기록을 닫을 때 관인으로 서명해 "국장 열쇠 지정"으로 싣는다. 그래서 처음 지정도 3회차 예고를 거친다. 지정이 취소된 열쇠는 다시 싣지 않는다(설정에서 빼고 새 열쇠를 넣는다).
- 교체·분실: 국장 열쇠는 여러 개 둘 수 있다. 새 기기 패스키는 쓰는 중인 국장 열쇠로 서명해 지정하거나 설정에 더하면 3회차 예고 뒤부터 쓰고, 잃은 열쇠는 남은 국장 열쇠나 관인으로 "빼기"(이것도 3회차 예고). 국장 열쇠를 모두 잃어도 관인(서버 설정)으로 새 열쇠를 지정할 수 있다.
- 서버 열쇠가 새 나갔을 때: 훔친 사람이 관인으로 자기 열쇠를 국장으로 지정해도 3회차 예고 동안 장부에 보이고, 진짜 국장이 취소할 수 있다(취소는 국장만 한다). 다만 서버 자체를 가진 사람은 취소 요청을 싣지 않을 수 있다. 그 경우도 장부에 "취소되지 않은 지정"으로 남아 드러난다.

**누가 국장이 되나: 관리 화면에 아무나 들어와도 국장이 되지 않는다**(2026-10-30 사용자 질문 "관리 화면에 다른 사람이 들어가도 등록할 수 있는 거 아니야?")
- `/stardraw/admin`은 누구나 열 수 있고, 거기서 패스키를 만드는 것도 누구나 할 수 있다. 그러나 패스키를 만든다고 국장이 되지 않는다. 국장 열쇠가 되는 길은 둘뿐이다: ① 처음은 **서버 설정 파일**(`STARDRAW_DIRECTOR_KEYS`, 서버를 가진 사람만 고친다)에 넣은 열쇠를 서버가 관인으로 서명해 장부에 싣는 것, ② 그 뒤로는 **이미 쓰는 국장 열쇠의 서명**. 어느 쪽이든 장부에 "국장 열쇠 지정" 기록이 남고 3회차 예고 뒤에야 쓸 수 있다.
- 인정되지 않은 열쇠로 서명한 요청은 서버가 거절하고(403 "국장 열쇠가 아닙니다"), 서버가 잘못 실어도 공개 장부 검사(검증 페이지·터미널 검사기)가 "국장 열쇠가 아니다"로 잡는다.
- 화면에도 적는다: "이 화면에서 만든 패스키는 우주국이 지정해야 국장 열쇠가 됩니다."

**국장 열쇠 지문**
- 공개 열쇠 65바이트를 사람이 눈으로 대조하기는 어렵다. 그래서 짧은 지문을 둔다: `국장-XXXX-XXXX-XXXX` = taggedHash("stardraw/director-fp/v1", pub) 앞 60비트를 Crockford base32 12자로(우주인 등록번호처럼). core `directorFingerprint`.
- 지문을 보이는 곳: 관리 화면(패스키를 만든 직후, 서명할 때 고른 열쇠), 서버 시작 기록(설정의 국장 열쇠마다 지문과 장부 상태: 예고 중·쓰는 중·새로 싣기), 서버가 지정을 실을 때의 기록, 검증 페이지·터미널 검사기의 "국장 열쇠 내력".
- 지문은 사람이 대조하는 보조 표시다. 판정은 늘 공개 열쇠 전체와 서명으로 한다(등록번호와 같은 원칙, 11-9). 60비트라 일부러 같은 지문을 만들려면 약 2^60번 계산이 든다.

**위협 둘을 더 본다**

| # | 공격 | 심각도 | 대책 |
|---|---|---|---|
| D1 | **처음 지정 때 공개 열쇠 바꿔치기**(사회공학): 운영자가 화면에서 만든 값을 설정에 옮기는 사이, 누군가 "이 값을 넣어 주세요"라며 자기 열쇠 값을 건네거나 복사한 값을 바꾼다 | 중간 | 관리 화면이 만든 패스키의 공개 열쇠와 지문을 함께 보이고, 서버는 시작할 때와 지정을 실을 때 설정 열쇠의 지문을 기록에 찍는다. 운영자는 자기 기기 화면의 지문과 서버 기록의 지문을 대조한다. 지정 뒤 예고 3회차 동안 장부에도 지문이 보여(검증 페이지 내력) 한 번 더 대조할 수 있다. 잘못 들어갔으면 설정에서 빼면 서버가 다음 기록에 관인으로 그 예고를 취소한다. 이미 쓰는 국장이 있으면 국장도 취소할 수 있다 |
| D2 | **서버를 장악해 설정 파일로 국장 열쇠 바꾸기** | 중간 | 설정의 국장 열쇠도 장부에 관인 서명 "국장 열쇠 지정" 기록으로만 효력이 생긴다(설정만 바꾸고 장부에 없으면 국장 서명이 검사에서 거절된다). 그 기록은 3회차 예고라 검증 페이지와 터미널 검사기의 **국장 열쇠 내력**(언제, 어느 열쇠(지문)가, 누구 서명(관인/국장)으로 지정·빼기됐고, 취소됐는지)에 드러나고, 진짜 국장은 예고를 취소할 수 있다. 서버를 가진 사람이 취소 요청을 싣지 않을 수는 있지만, 그 경우도 장부에 "몰래 바뀐 지정"이 남아 앵커(GitHub)와 함께 고칠 수 없게 드러난다 |

**③ 사람과 AI가 찾아 쓰는 법**
- 공개 장부 `rounds/N.json`의 기록 바이트 하나에 다 들어 있다. core `verifyLedger`가 운영 기록을 함께 검사하고 결과(`operations`)를 돌려준다. 장부 검사 항목 "운영 기록(국장·관인)".
- 검증 페이지와 터미널 검사기의 "국장 열쇠 내력": 지정·빼기·취소를 회차·지문·서명자와 함께 차례로 보인다.
- 서버 `GET /api/director/state`: 다음 기록 회차와 장부 끝 해시(서명할 `after`), 가장 이른 효력 회차, 국장 열쇠·운영 기록·소속 목록(예고 중·적용·취소), 받아 두고 아직 싣지 않은 요청.
- 화면 `/stardraw/admin`(메뉴에 없음, 주소로 들어감), 데모 `/stardraw/demo`의 "국장 모드", 검증 페이지 운영 기록 규칙과 시험 값, 배우기 "공격해 보기"의 국장 기록 위조 둘.

**④ 요구사항이 바뀌면**
- 새 운영 종류(자격 열쇠 교체, 발급 수 공개 주기, 관인 교체 등)는 kind 값을 더하고 core `operations.ts`의 읽기·확인·적용 한 곳을 고친다. 기록 형식(v2)은 그대로다.
- 소속별 상품 자격(블라인드 서명)을 만들 때: 소속의 자격 열쇠 칸을 "소속 바꾸기"로 채우고, 등록·응모권에 자격 증명을 붙이는 칸이 필요하면 그때 등록·응모권 판을 올린다(이번 일과 따로). → 11-13에서 다시 정했다: 소속 칸은 늘 0으로 두고 자격 기간(kind 8)·발급 수(kind 9)를 따로 싣고, 응모권 판을 올린다.
- 예고 길이가 바뀌면 `NOTICE_ROUNDS` 하나다(일정 바꾸기와 같이 바뀐다).

**⑤ 고른 근거와 버린 안**
- 기록 판을 올리되(v2) 운영 기록이 있을 때만: 지난 기록·해시·앵커를 하나도 바꾸지 않는다. 옛 검사기는 v2 기록을 만나면 "모르는 기록 판"으로 **멈춘다**(조용히 통과하지 않는다). 버린 안: 끝에 칸을 그냥 덧붙이기(판이 같은데 바이트가 남아 옛 검사기 오류가 덜 분명하다), 운영 기록을 별도 파일·별도 사슬로 두기(앵커·사슬 검사를 새로 만들어야 하고 기록 해시와 묶이지 않는다).
- 재사용 방지는 서버 challenge 대신 장부 끝 해시: 검사하는 사람이 서버를 믿지 않고 장부만으로 "이 서명은 이 자리에서만 쓰인다"를 확인할 수 있다. 대가는 서명하는 사이 기록이 하나 닫히면(10분 회차의 추첨 때) 다시 서명해야 한다는 것(화면이 알려 준다).
- 국장 지정을 관인 서명으로: 서버는 어차피 장부에 무엇을 실을지 정하지만, 관인 서명이 있으면 지정이 "영수증에 서명하는 그 우주국"에서 나왔다는 것을 장부 밖으로 들고 다닐 수 있다. 관인 열쇠를 genesis에 넣지 않은 장부라(지금 장부는 다시 시작하지 않는다) 첫 관인 기록에서 고정한다.
- 처음 지정을 화면에서 하지 않고 서버 설정으로: 아직 국장이 없을 때 화면으로 받으면 아무나 먼저 지정 요청을 넣을 수 있다. 설정 파일은 서버를 가진 사람만 고친다. 그 뒤의 지정은 국장 서명으로도 할 수 있어 서버 설정을 다시 고치지 않아도 된다(관인 길은 국장 열쇠를 모두 잃었을 때의 예비).
- 정식 시작 예약 명령(`schedule-live`)은 남겨 둔다(국장 열쇠가 없을 때 예비). 화면 길이 기본이다. 둘 다 예고 중인 일정 바꾸기가 있으면 거절한다.

**화면**
- `/stardraw/admin`: ① 국장 패스키 만들기(이름 "카노푸스 우주국장", 우주인 패스키와 다른 패스키). 만든 뒤 `STARDRAW_DIRECTOR_KEYS`에 넣을 값을 보여 준다. ② 국장 열쇠로 서명: 시험 소속 추가, 예고 취소, 정식 시작 예약(x:55 시각 고르기, 3회차 예고 안내), 국장 열쇠 빼기. ③ 예고 중·적용·취소된 운영 기록과 소속 목록. 서명할 때 패스키를 고르게 하고, 고른 패스키가 장부의 국장 열쇠가 아니면 "국장 열쇠가 아닙니다"로 멈춘다(서버도 거절한다).
- 데모 국장 모드: 흉내 패스키로 국장 패스키를 만들고, "서버 설정에 넣기"(데모 관인이 다음 기록에 지정) → 「하루 건너뛰기」로 국장이 된 뒤 시험 소속 추가 → 다시 하루 건너뛰어 적용을 본다. 「국장 아닌 패스키로 해 보기」는 거절된다.

### 11-13. 상품 자격과 소속: 블라인드 서명 자격 증서(2026-10-30, 설계만)

사용자와 정한 방향: 하늘의 별 따기를 회사에 알리며 상품을 건다. **응모와 당첨 확인은 지금처럼 누구나, 상품 자격은 그 기관 사람만.** 그리고 **우주국(서버·운영자)도 어느 우주인이 누구인지 모르게** 한다. 2026-10-30 문서로 설계하고 2026-10-31 갈림길을 정해 만들기 시작했다(연동 방법은 아래 "기관 계정 연동 방법").

**지금 구조의 구멍**: 우주인 = 패스키이고 누구나 공짜로 만든다. 한 사람이 우주인 여럿으로 확률을 높일 수 있다. IP 상한은 공유 IP 때문에 넉넉하고(11-10), 작업 증명은 컴퓨터가 많은 쪽이 유리하다. 당첨자만 신원을 확인해도 소용없다(당첨된 열쇠의 주인 한 명만 진짜면 된다). 패스키는 "누가 이 열쇠의 주인인가"만 증명하고 "한 사람이 몇 개를 갖는가"는 따로다. 그래서 "신원" 칸을 채운다. 다만 신원을 우주인에 직접 묶지 않고, **사람마다 한 장씩 받는 자격 증서**를 응모권에 붙인다.

**한 줄 요약**: 기관 계정으로 확인된 사람은 기간마다 한 번, 기기에서 만든 **자격 열쇠**의 공개 열쇠를 **먹지 봉투에 넣은 채로(블라인드)** 우주국 도장을 받는다. 우주국은 무엇에 도장을 찍었는지 모른다. 응모권에 자격 증서(자격 공개 열쇠 + 도장)와 자격 열쇠 서명을 붙이면 그 응모권이 소속의 **상품 대상**이 된다. 한 회차에 같은 자격이 두 장 이상이면 그 응모권 모두 상품 대상에서 빠진다.

#### 사용자 안을 다듬은 곳 둘(이 문서가 정한 것)

1. **자격 번호는 비밀이 아니라 공개 열쇠다.** 사용자 안은 "무작위 자격 번호 + 도장"을 비밀값으로 들고 다니는 것이었다. 그런데 응모권에 붙으면 장부에 그대로 공개된다. 그러면 누구나 장부에서 증서를 베껴 **주인이 응모하지 않은 다른 회차**에 붙일 수 있다(같은 회차 규칙으로는 못 막는다). 그래서 기기가 자격 열쇠 쌍을 만들고 **공개 열쇠에** 도장을 받는다. 응모권에는 공개 열쇠·도장과 함께 **자격 비밀 열쇠로 그 응모권에 한 서명**을 붙인다. 장부에서 베낀 사람은 서명을 못 만든다. 들고 다닐 비밀은 자격 비밀 열쇠(를 만드는 씨앗)다. "복구 코드처럼 들고 있는 사람이 주인"이라는 성질은 그대로다.
2. **백업은 기본이 평문 복구 코드다.** 사용자 안은 저장과 백업을 패스키 PRF 값으로 잠그는 것이었다. 그런데 백업이 필요한 때가 바로 **패스키를 잃었을 때**라, 잃은 패스키로 잠근 백업은 열 수 없다. 그래서 내보내는 백업(복사·QR·파일)은 복구 코드처럼 평문에 주의 안내를 붙인다. "이 패스키로 잠근 백업"도 고를 수 있게 하되 "패스키를 잃으면 열 수 없습니다"를 적는다. 사용자 확인을 기다리는 갈림길로 남긴다(map.json `stardraw-qual-backup`).

#### ① 데이터의 뜻·연결·책임

| 데이터 | 뜻 | 누가 만들고 서명하나 | 어디에 |
|---|---|---|---|
| 소속 | 별·성단 이름, 배지, 신원 확인 방법 이름. 상품을 거는 단위 | 국장(운영 기록 kind 3, 11-12) | 회차 기록 v2의 운영 기록. 소속 id = 그 운영 기록 id |
| 자격 기간 | 한 소속의 한 기간(시작·끝 시각)과 그 기간의 **도장 공개 열쇠** | 국장(새 운영 기록 kind 8). 도장 비밀 열쇠는 서버가 기간마다 새로 만든다 | 운영 기록. 기간 id = 그 운영 기록 id |
| 발급 수 | 그 기간에 지금까지 찍은 도장 수(누적) | 관인(새 운영 기록 kind 9, 서버가 자동으로) | 운영 기록 |
| 자격 열쇠 | 사람이 기기에서 만든 P-256 열쇠 쌍. 공개 열쇠 = **자격 번호** | 사람(기기). 씨앗 16바이트에서 만든다 | 비밀: 사람의 기기·백업. 공개: 응모권에 붙으면 장부 |
| 도장 | 자격 공개 열쇠에 대한 기간 열쇠의 BLS 서명. 블라인드로 받아 우주국은 무엇에 찍었는지 모른다 | 서버(가린 값에 서명) → 기기가 벗김 | 기기·백업, 응모권 |
| 자격 증서 | 기간 id + 자격 공개 열쇠 + 도장. 공개해도 되는 부분 | — | 응모권 v2 |
| 복구 코드 | 기간 + 씨앗 + 도장. 들고 있는 사람이 자격의 주인 | 기기 | 사람이 보관(복사·QR·파일) |
| 발급 장부(서버 안) | 한 기간에 한 계정 한 번을 지키는 표. 계정 값의 HMAC과 기간 id만 | 서버 | 서버 DB(공개하지 않음) |

- **연결**: 기관 계정 → (서버가 한 번 확인, 블라인드라 여기서 끊김) → 도장 → 자격 열쇠 → 응모권 → 우주인 열쇠. 서버가 아는 것은 "이 계정이 이 기간에 도장을 받았다"와 받은 시각뿐이고, 어느 자격 번호인지는 모른다.
- **책임**: 소속·기간을 여는 것은 국장(3회차 예고), 도장을 찍고 발급 수를 싣는 것은 서버, 증서를 지키는 것은 사람, 상품 대상 판정은 공개 규칙(검사기·서버·화면이 같은 코드)이다.
- **소속 기록의 빈 칸 채우기**: kind 3·4의 "자격 열쇠"와 "발급 수" 칸(11-12)은 **채우지 않고 늘 0으로 둔다**(검사 규칙을 "0바이트·0이어야 한다"로 좁힌다). 자격 열쇠는 기간마다 바뀌고 발급 수는 회차마다 바뀌는데, 소속 칸에 두면 이름·배지까지 다시 서명하는 "소속 바꾸기"를 그때마다 해야 하고 3회차 예고 때문에 발급 수가 하루씩 늦는다. 그래서 기간과 발급 수를 따로 둔다. 시험 장부에 소속 기록이 있어도 두 칸이 0이라 그대로 읽힌다.
- **비공개 값**: 기관 이름·도메인·로고는 공개 저장소·장부에 쓰지 않고 서버 설정에만 둔다. 장부에는 "기관 계정", "초대 코드" 같은 **방법 이름**만 싣는다. 상품 내용도 장부에 싣지 않는다(상품은 지금처럼 하늘의 별 따기 밖에서 정한다, 11절). 장부는 "누가 상품 대상인가"만 정한다.

**첫 소속: 벌집 성단**(Beehive Cluster, 프레세페, M44). 게자리의 산개 성단이고 서울에서 맨눈으로 보인다. 배지 2(성단), 방법 "기관 계정". 다른 소속도 더할 수 있다. 이름은 별·성단 이름으로 짓고, 실제 단체 이름·로고는 그 단체의 허락이 있을 때만 쓴다.

**데이터 형식 초안**(고정 바이너리, 4절 규칙. 시험 값은 만들 때 정한다)

```
운영 기록 kind 8 자격 기간 열기   소속 id(32) ‖ 기간 번호(u16) ‖ startsAt(u64) ‖ endsAt(u64)
                                 ‖ 도장 방식(u8 = 1, BLS12-381 G1 서명) ‖ 도장 공개 열쇠(u16 길이 + 96바이트, G2 압축)
운영 기록 kind 9 발급 수         기간 id(32) ‖ 누적 발급 수(u32)

도장 받을 메시지 m = "stardraw/qual/v1" ‖ 0x00 ‖ 기간 id(32) ‖ 자격 공개 열쇠(33, SEC1 압축)
도장 = BLS 서명(G1 압축 48바이트), hash-to-curve DST "STARDRAW-QUAL-V1_BLS12381G1_XMD:SHA-256_SSWU_RO_"

자격 증서(응모권 안) = 기간 id(32) ‖ 자격 공개 열쇠(33) ‖ 도장(48)                          113바이트
자격 서명 대상 = "stardraw/qual-sig/v1" ‖ 0x00 ‖ v ‖ round ‖ numbers ‖ pub ‖ 자격 증서
자격 서명 = 자격 비밀 열쇠의 P-256 서명 r‖s(64)

응모권 v2 = v(u8 = 2) ‖ round(u32) ‖ numbers(6) ‖ pub(65) ‖ 자격 증서(113) ‖ 자격 서명(64) ‖ nonce(u32) ‖ 응모자 서명
  작업 증명 대상 = v ‖ round ‖ numbers ‖ pub ‖ 자격 증서 ‖ 자격 서명
  응모자 서명 대상 = "stardraw/ticket-sig/v1" ‖ 0x00 ‖ (nonce까지의 앞부분 전체)
  응모권 id = taggedHash("stardraw/ticket/v1", nonce까지의 앞부분 전체)

복구 코드 = "SDQ1-" ‖ base32(v(u8 = 1) ‖ 기간 id 앞 8바이트 ‖ 씨앗(16) ‖ 도장(48))        73바이트 → 117자
  자격 비밀 열쇠 = P-256 스칼라로 바꾼 taggedHash("stardraw/qual-key/v1", 씨앗)
보이는 자격 번호 = "Q-XXXX-XXXX" (taggedHash("stardraw/qual-id/v1", 기간 id ‖ 자격 공개 열쇠) 앞 40비트, Crockford base32)
```

- 응모권은 **판을 올린다**(v1은 그대로 받고 상품 대상이 아니다). 자격 없는 응모는 앞으로도 v1으로 낸다. 옛 검사기는 v2 응모권을 만나면 "모르는 응모권 판"으로 멈춘다(조용히 통과하지 않는다, 11-12와 같은 원칙). 회차 기록 형식은 바꾸지 않는다. 응모권 목록·머클 루트는 응모권 바이트 그대로라 v1·v2가 섞여도 된다.
- 자격 서명은 원시 P-256 서명이지만 **응모자 서명이 아니다**(응모자 서명은 여전히 패스키만, 11-11). 자격 열쇠는 백업해야 해서 꺼낼 수 없는 패스키에 둘 수 없다. 응모자 서명이 자격 칸까지 덮으므로, 자격 서명은 "이 응모권에 이 자격을 붙인 사람이 비밀을 가졌다"만 맡는다. 자격 서명 대상에 nonce를 넣지 않아 작업 증명 전에 서명할 수 있다.
- 기간 id는 복구 코드에서 앞 8바이트만 쓰고 장부의 kind 8 기록에서 찾는다(소속·기간 수가 적어 겹치지 않는다. 겹치면 불러오기가 고르게 한다).
- 회차 k가 기간에 속하는지는 `closesAt(k)`가 `[startsAt, endsAt)` 안인지로 본다(일정이 바뀌어도 시각 기준이라 흔들리지 않는다).

**기간**: 한 소속에 기간은 겹치지 않게 차례로 연다(다음 기간의 startsAt ≥ 앞 기간의 endsAt). 도장은 kind 8의 효력 회차부터 endsAt까지 받을 수 있어서, 다음 기간 증서는 앞 기간이 끝나기 전에 미리 받는다. 길이는 **1년**으로 정했다(2026-10-31 사용자, 갈림길 `stardraw-qual-period`). 대가: 떠난 사람의 자격이 그해 끝까지 남고, 증서와 복구 코드를 모두 잃으면 다음 해까지 다시 못 받는다. 길이는 kind 8의 값이라 다음 기간부터 바꿀 수 있다. 기간마다 도장 열쇠가 새것이라 앞 기간 증서와 새 증서는 이어지지 않는다.

#### ② 꼭 지킬 규칙과 보장하는 곳

모두 core(새 파일 `qualification.ts`, 운영 기록은 `operations.ts`)의 같은 함수로 서버·검증 페이지·터미널 검사기가 확인한다.

| 규칙 | 내용 | 보장 |
|---|---|---|
| 증서가 진짜 | 기간 id가 효력이 생긴(끝나지 않은 소속의) kind 8이고, 회차 `closesAt`이 그 기간 안이고, 도장이 기간 열쇠로 m에 대한 BLS 서명이고(G1 점 검사·무한원점 거절), 자격 서명이 맞다 | 서버는 틀린 증서가 든 응모를 400으로 거절. 장부에 실렸으면 검사 실패(서버 잘못) |
| **한 회차 한 자격 한 장** | 한 회차에 같은 자격 공개 열쇠가 붙은 응모권이 둘 이상이면 **그 응모권 모두 상품 대상에서 빠진다.** 응모권 자체는 유효해서 등수는 그대로다 | 판정은 장부만으로 계산(서버 판단 없음). 서버는 두 번째 응모도 **받아야 한다**: 먼저 낸 쪽만 받으면 증서를 훔친 사람이 먼저 내서 주인을 밀어낼 수 있다. 둘 다 빠지게 하면 훔친 사람은 방해만 할 수 있고 가져갈 수 없다 |
| 한 사람 한 장 | 한 계정은 한 기간에 도장 한 번 | 서버 발급 장부(계정 HMAC + 기간 id). 블라인드라 장부로는 확인할 수 없고, 아래 발급 수로 드러나게 한다 |
| **발급 수보다 많이 쓰이지 않는다** | 한 기간에서 회차 k까지 응모권에 쓰인 서로 다른 자격 번호 수 ≤ 회차 k 기록까지 실린 그 기간의 최신 발급 수. 발급 수는 줄지 않는다 | 검사기가 회차마다 센다. 어기면 "발급 수보다 많은 자격이 쓰였습니다"로 실패. 서버는 회차를 닫을 때 그 회차 마감 시각까지의 발급 수가 바뀌었으면 kind 9를 관인으로 서명해 싣는다(실린 즉시 효력, E = 0) |
| 기간 열쇠는 하나 | 한 기간 id에 도장 열쇠 하나. 바꿀 수 없다(바꾸려면 기간을 새로 연다) | kind 8 형식. 화면은 서버 응답이 아니라 **장부의 열쇠로** 벗긴 도장을 확인한다(사람마다 다른 열쇠로 표시하는 공격을 막는다) |
| 서명자 | kind 8은 국장만(3회차 예고, 예고 취소 가능), kind 9는 관인만 | 11-12 서명자 규칙에 더한다 |
| 소속 칸 비우기 | kind 3·4의 자격 열쇠 0바이트, 발급 수 0 | `operations.ts` 확인을 좁힌다 |

**우주국도 모르게: 블라인드 서명**
- 기기: 자격 열쇠를 만들고 m을 곡선 위 점 H(m)으로 바꾼 뒤 무작위 r을 곱해 **가린 값** r·H(m)을 보낸다. 서버: 계정을 확인하고 가린 값에 비밀 열쇠 sk를 곱해 돌려준다. 기기: r의 역수를 곱해 sk·H(m), 곧 m에 대한 보통 BLS 서명을 얻는다. 서버가 본 r·H(m)은 무작위 점과 구별되지 않아, 나중에 장부에서 도장을 봐도 누구에게 찍어 준 것인지 모른다.
- 우리 화면도 서버가 내준 코드라는 한계(8-1 O5)는 남는다. 화면 코드가 가린 값 대신 맨 값을 보내도록 바뀌면 블라인드가 깨진다. 재현 빌드·화면 코드 해시(11-8)로 비교할 수 있다.

**남는 한계(정직하게 적는다)**

| 한계 | 왜 | 줄이는 법 |
|---|---|---|
| 시간으로 이어질 수 있다 | 서버는 "어느 계정이 몇 시에 도장을 받았나"를 안다. 받은 직후 처음 보는 자격 번호로 응모하면 짐작된다. 회차마다 오르는 발급 수도 그 짐작을 돕는다 | 화면은 받은 그 자리에서 응모하지 않게 하고, 증서를 저장해 **다음 응모 때** 붙인다(받은 뒤 적어도 한 회차 지나서). 같은 시각에 여럿이 받으면 섞인다(소속 공지 때 한꺼번에 받게 안내). 서버는 발급 시각을 저장하지 않는다(발급 장부에 시각 칸 없음) |
| 국장이 몰래 더 찍을 수 있다 | 도장 비밀 열쇠는 서버에 있다 | 몰래 찍은 증서를 쓰면 "쓰인 자격 수 > 발급 수"로 걸리고, 발급 수를 부풀리면 소속 사람 수보다 많은 숫자가 공개된다(사람들이 대략 안다) |
| 자격을 넘길 수 있다 | 복구 코드를 남에게 주면 그 사람이 쓴다 | 전체 수는 늘지 않는다. 넘겨준 사람과 받은 사람이 같은 회차에 내면 둘 다 빠진다 |
| 같은 자격의 응모끼리 이어져 보인다 | 자격 공개 열쇠가 장부에 남는다 | 우주인 열쇠와 같은 수준이다(이미 같은 우주인 응모는 이어진다). 기간이 바뀌면 끊긴다 |
| 소속을 떠난 사람의 자격이 기간 끝까지 남는다 | 블라인드라 증서 하나를 골라 취소할 수 없다 | 기간을 짧게. 상품 줄 때 확인하는 사람이 판단한다 |
| 증서와 백업을 모두 잃으면 그 기간에는 다시 못 받는다 | 한 계정 한 번, 취소 불가 | 다음 기간에 새로 받는다 |

#### ③ 사람과 AI가 찾아 쓰는 법

- 공개 장부 `rounds/N.json`의 기록(운영 기록 kind 8·9)과 응모권 목록(v2 응모권)에 모두 들어 있다. 따로 파일을 두지 않는다.
- core `verifyLedger` 결과에 회차마다 소속별 `prizeEligible`(등수별 상품 대상 응모권 id), `excludedDuplicates`(같은 자격이라 빠진 응모권 수), 기간별 `issued`·`used`를 더한다. 검증 페이지·터미널 검사기에 "소속과 상품 자격" 항목: 소속마다 방법 이름·기간·도장 열쇠 지문·발급 수·쓰인 자격 수.
- 서버: `GET /api/director/state`의 소속 목록에 기간을 더한다. 발급은 `POST /api/qual/:기간 id/blind`(계정 확인 + 가린 값 → 가린 도장). 장부에 이미 있는 값은 새 조회 API를 두지 않는다.
- 소속별 발급 수 공개: 검증 페이지와 소속 안내(자세히)에 "벌집 성단 · 2026년 4분기 · 발급 n개 · 응모에 쓰인 자격 m개 · 확인 방법: 기관 계정". 직원 수보다 크면 누구나 알아챈다.
- 화면 코드 자리(만들 때): `apps/web/src/stardraw/qualification/`(받기·백업·불러오기·저장), 배우기 단계는 `/stardraw/learn`.

#### ④ 요구사항이 바뀌면 어디까지 고치나

- 소속을 더하거나 끝내기: 운영 기록만(코드 그대로).
- 기간 길이: kind 8의 startsAt·endsAt 값만. 정해진 길이를 규칙으로 두지 않는다.
- 도장 방식을 RSA 블라인드로 바꾸기: kind 8의 도장 방식 값 2를 더하고 증서의 도장 길이를 방식에 따라 읽는다(응모권 v3이 필요할 수 있다). 기간마다 방식을 고를 수 있어 바꾸는 기간부터만 다르다.
- 기관 계정 연동 방법이 정해지거나 바뀌기: 서버의 계정 확인 부분 하나. 장부·증서·화면 흐름은 그대로(방법 이름만 소속 기록에).
- 소속마다 여러 장(예: 한 사람 회차 둘)이 필요해지면: "한 회차 한 자격 한 장" 규칙의 숫자를 kind 8에 칸으로 더해야 한다(새 kind 또는 판 올림). 지금은 두지 않는다.
- 회차 사이에도 이어지지 않게 하라는 요구가 생기면: 같은 자격을 회차마다 다른 모습으로 보이는 영지식 방식(아래 ⑤의 버린 안)으로 바꿔야 하고 응모권 형식이 크게 바뀐다.

|---|---|---|---|---|
| B | 기관 계정으로 로그인해 우주인 열쇠를 계정에 직접 묶는다 | 쉽다(다시 로그인해 새 우주인을 묶으면 된다) | **안다**(계정 ↔ 우주인 표가 서버에 있다) | 버림. "우주국도 모르게"를 못 지킨다 |
| 원래 A | 우주인 공개 열쇠에 블라인드 도장 | 해결 없음(패스키를 잃으면 자격도 잃고, 한 기간 한 번이라 다시 못 받는다) | 모른다 | 버림(사용자: 분실 해결이 없다) |
| **바꾼 A** | 자격 열쇠에 블라인드 도장, 응모권에 증서를 붙이고 응모권 전체는 패스키로 서명 | 복구 코드를 새 우주인에 불러온다 | 모른다 | **고름**. 대신 복구 코드가 새 나가면 남이 쓸 수 있어 "같은 회차 두 장이면 둘 다 제외"를 둔다 |

**도장 방식: BLS 블라인드 vs RSA 블라인드(RFC 9474)**

| | BLS12-381 블라인드 | RSA 블라인드(RSABSSA-SHA384-PSS) |
|---|---|---|
| 도장 길이 | 48바이트 | 256바이트(2048비트)~384바이트 |
| 증서(공개 열쇠 + 도장) | 81바이트 | 290바이트 안팎 |
| 표준 | 블라인드 형태는 RFC가 없다(서명 자체는 BLS 초안, 보안 근거는 Boldyreva 2003의 one-more CDH) | RFC 9474로 표준, Privacy Pass(RFC 9578)가 쓴다 |
| 코드 | 이미 drand 확인에 쓰는 `@noble/curves` bls12-381(새 의존 없음). 가리기·벗기기는 점 곱셈 몇 번 | 큰 정수 계산 직접 또는 새 라이브러리 |
| 검사 비용 | 서명마다 짝짓기(pairing) 두 번. 같은 기간 열쇠라 무작위 계수를 곱해 회차마다 한 번에 묶어 확인할 수 있다 | 아주 빠르다 |

- **BLS를 고른다.** 응모권마다 붙고 복구 코드·QR에 들어가 길이가 중요하고, 이미 쓰는 라이브러리라 새 의존이 없다. 대가: 블라인드 형태가 표준이 아니다. 그래서 서버는 받은 가린 값이 G1 부분군의 점이고 무한원점이 아닌지 꼭 보고, 도장 열쇠는 기간마다 새로 만들어 다른 곳에 쓰지 않는다. 묶어서 확인할 때는 무작위 계수를 곱한다(안 곱하면 틀린 두 도장이 서로 지워져 통과할 수 있다).
- 만들 때 브라우저에서 짝짓기 시간을 재 보고, 휴대폰에서 장부 검사가 너무 느리면 묶어 확인을 기본으로 둔다. BLS 쪽에 문제가 보이면 RSA로 바꾼다(④ 도장 방식 값).

**그 밖에 버린 안**
- 당첨자만 신원 확인: 위 "구멍"처럼 소용없다.
- Privacy Pass처럼 한 번 쓰는 토큰을 회차마다 받기: 회차마다 기관 계정 로그인이 필요하고, 발급 시각과 응모 시각이 바로 붙어 시간으로 이어지기 쉽다.
- 영지식 증명(BBS+ 익명 자격, Semaphore 같은 nullifier): 회차마다 다른 모습이라 응모끼리 이어지지 않는 장점이 있지만, 브라우저 코드·검사기가 크게 무거워지고 다른 언어로 독립 검사기를 짜기 어렵다(원칙 2). 커피 규모에 비해 과하다.
- 소속 기록의 자격 열쇠 칸에 열쇠를 넣기: 위 ①(기간마다·회차마다 바뀌는 값).
- 우주인 등록 때 자격을 묶기(등록 판 올리기): 패스키 분실 해결이 원래 A와 같이 없다.

#### 기관 계정 연동 방법: ① 별 따기 전용 구글 로그인 + `hd` 확인(2026-10-31 정함)

- 2026-10-31 사용자 개인 구글 클라우드 프로젝트의 웹 클라이언트(앱 이름 "하늘의 별 따기", 외부, 테스트 중·테스트 사용자)로 기관 계정 로그인을 해 보니 막히지 않았고 `hd`(기관 도메인)·`email_verified`가 왔다.
- **클라이언트 보안 비밀은 쓰지 않는다.** 화면이 Google Identity Services로 ID 토큰을 받아 서버로 보내고, 서버가 구글 공개 열쇠(JWKS)로 서명과 `iss`·`aud`(클라이언트 ID)·`exp`·`email_verified`·`hd`를 확인한다. 화면이 보낸 다른 값은 믿지 않는다.
- 클라이언트 ID는 공개 값이라 코드 상수 하나(core `GOOGLE_CLIENT_ID`)로 둔다. 화면과 서버가 같은 값을 쓴다. 비어 있으면 받기 단추가 "준비 중"으로 보인다. 기관 도메인은 비공개 서버 설정(`STARDRAW_QUAL_AFFILIATIONS`)에만 둔다.
- 공개 전에 동의 화면을 게시 상태로 바꾸고(브랜딩: 홈페이지 `https://game.byb.kr/stardraw`, 개인정보처리방침 `/stardraw/privacy`, 승인 도메인 `byb.kr`) 기관 계정으로 다시 확인한다. 기본 범위(openid·email)만 써서 구글 검수는 필요 없다.
- 바깥 지인 소속(카카오톡 단톡방)은 나중에 연다. 확인 방법은 "신청 + 국장 승인"(링크로 이름을 적어 신청하면 국장이 관리 화면에서 승인)을 먼저, 사칭이 문제가 되면 카카오 로그인 + 승인. 서버의 확인 방법은 소속마다 바꿔 끼울 수 있게 둔다.

아래 표는 정할 때 비교한 것이다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| ① 별 따기 전용 구글 로그인 + 기관 도메인(`hd`) 확인 | 별 따기 서버만으로 끝난다. 로그인 결과(ID 토큰)를 서버가 직접 확인 | 기관 관리자 설정에 따라 외부 앱 허용을 IT 담당에게 받아야 할 수 있다. `hd`는 서버에서 토큰 서명과 함께 확인해야 한다(화면 값 믿지 않기) |
| ② 운영자가 이미 쓰는 기관 안 서비스의 구글 클라우드 인증을 다시 쓰기 | 이미 허용된 앱이라 새 승인이 필요 없을 수 있다 | 다른 서비스에 기대는 의존이 생기고, 그 서비스 설정이 바뀌면 같이 깨진다. 그 서비스 쪽 기록에 별 따기 로그인이 남는다 |

- 어느 쪽이든 서버가 받는 것은 "이 계정이 기관 사람이고 이번 기간에 처음이다"뿐이어야 한다. 이메일은 HMAC으로만 남기고 이름·프로필은 받지 않는다. 기관 계정은 2026-11-12부터 패스키 로그인이 필수라 계정 탈취는 어렵다.
- 공유 계정·서비스 계정처럼 사람이 아닌 계정을 가를 수 있는지 정할 때 같이 확인한다.
- 연동 전에는 소속 방법 "초대 코드"로 같은 흐름을 시험할 수 있다(국장이 코드를 만들어 나눠 준다. 배지에 방법 이름이 보여 기관 계정보다 약한 확인임이 드러난다).

#### 만든 것(2026-10-31)

- **core**: `qualification.ts`(블라인드 도장, 자격 열쇠, 복구 코드, 자격 번호, `GOOGLE_CLIENT_ID`), `prize.ts`(상품 대상 판정), 응모권 v2, 운영 기록 kind 8·9, `verifyLedger`의 `qualification`. 시험 값은 파이썬(표준 라이브러리로 짠 P-256 곱셈)과 RFC 9380 시험 값으로 따로 맞췄다(검증 페이지 시험 값 「상품 자격 증서」).
- **서버**: `POST /api/qual/:기간 id/blind`(구글 ID 토큰 확인 `google.ts` + 가린 값에 도장), `POST /api/director/qual-key`(기간마다 새 도장 열쇠, 비밀은 SQLite), `GET /api/qual`, 응모권 v2 받기, kind 9 자동 싣기. 발급 장부는 `qual_issued(period, account HMAC, blinded)`뿐이고 받은 시각은 없다. 같은 가린 값을 다시 보내면 같은 도장을 다시 준다(응답을 못 받은 경우).
- **화면**: `/stardraw/qualify`(받기·복구 코드 복사·QR·파일·불러오기), `/stardraw/privacy`, 응모 화면 「○○ 상품 대상」(받은 다음 회차부터), 영수증 "상품 대상 · Q-…", 지난 회차 "상품 대상 당첨자 n명"과 같은 자격으로 빠진 수·내 응모권이 빠졌을 때 안내, 등록증 소속 배지(이 기기 지갑의 열쇠일 때만), 국장 화면 「자격 기간 열기(1년)」, 데모 6단계(데모 국장으로 소속·기간을 차리고 데모 기관 계정으로 받기).
- **바꾼 곳**: 기기 안 저장본의 PRF 잠금은 하지 않는다. 이 기기 저장소에 평문으로 두고, 화면에는 알리지 않는다(사람이 알아듣기 어렵고 할 수 있는 일이 없다, 2026-10-31 사용자 지적).
  - **"응모 서명과 같은 확인 한 번에 PRF로 푼다"는 위 설계는 응모권 v2 순서상 안 된다**(2026-10-31 확인). 응모권은 ① 자격 서명이 든 몸통(`unsignedTicket`, 여기서 자격 씨앗이 필요) → ② 그 몸통의 작업 증명 → ③ 패스키 서명(`signTicket`) 순서로 만든다(`packages/stardraw-core/src/ticket.ts` `makeTicket`). PRF 값은 ③의 확인에서야 나오는데 씨앗은 ①에서 필요하다. 작업 증명 대상이 자격 서명을 덮으므로 ③ 뒤에 자격 서명을 붙이도록 바꾸려면 응모권 형식(판)을 바꿔야 한다.
  - 잠그려면 확인이 하나 는다. 선택지: (가) 자격을 붙인 응모만 확인 두 번(증서 풀기 + 응모 서명) (나) 탭마다 처음 자격을 붙일 때만 한 번 더 풀고 그 탭 동안 메모리에 둔다 (다) 지금처럼 평문. 받기·불러오기는 지금도 패스키 확인이 없어(구글 로그인·코드 붙여넣기뿐) 잠가 저장하려면 거기서도 확인이 하나 는다.
  - (다)를 고른 근거: 평문 저장본을 노리는 공격(이 출처의 스크립트 주입, 잠금 풀린 기기)은 사용자가 따로 보관하는 평문 복구 코드와 같은 수준의 노출이고, 훔친 증서로 낸 응모와 주인의 응모가 같은 회차에 겹치면 둘 다 상품 대상에서 빠져 가져갈 수는 없다(위 "한 회차 한 자격 한 장"). 패스키를 잃으면 잠근 저장본도 못 연다는 단점은 (가)·(나)에도 같고, 그때는 평문 복구 코드로 되살린다. 확인 횟수를 늘려도 되면 (나)가 가장 덜 번거롭다.
- **연 뒤 할 일(사용자)**: 국장이 관리 화면에서 벌집 성단(방법 "기관 계정") 소속 추가 → 3회차 뒤 「자격 기간 열기(1년)」 → 3회차 뒤 받기. 서버 설정 `STARDRAW_QUAL_AFFILIATIONS=벌집 성단=google:<기관 도메인>`. 공개 전에 구글 동의 화면을 게시하고 기관 계정으로 다시 확인한다.

### 11-14. 우주인 등록 때 바로 장부에 등록, 패스키 이름, 첫 화면 다시 설계(2026-10-30)

사용자: "내가 로그인 상태인지 아닌지 확인이 어렵고", "응모 페이지가 카운트다운 숫자만 크게 2개 있고, 그 밑에 각종 컴포넌트가 있어서 좀 혼란스럽거든", "문구를 과도하게 넣으려는 경향이 있는데 그러지 마".

**등록을 바로 장부에**
- 예전에는 열쇠가 첫 응모 때 응모권과 함께 장부에 올랐다. 이제 「우주인 등록」(패스키 만들기) 직후 등록만 올린다. 등록 회차가 곧 등록증 발급일(`issuedAtOf`의 첫 순위)이다.
- 서버 `POST /api/register` `{ registration, proof, head }` → `{ round }`. 응모와 같은 확인을 같은 순서로 한다: IP 앞부분 하루 등록 상한(응모와 같은 셈) → 형식(원시 열쇠 거절) → 받는 때(응모를 받는 동안만, 다르면 409) → 문제 값이 지금 값인지(아니면 409) → 국장 열쇠 거절(403) → 패스키 번호 한 번만 → **등록 증명 서명(UV까지)** → 작업 증명(Argon2 동시 실행 제한). 이미 등록된 열쇠면 그 회차를 그대로 돌려준다.
- **등록 증명**(core `registrationProofMessage`): `"stardraw/register-proof/v1" ‖ 0 ‖ v ‖ kind ‖ credentialId ‖ pub`(nonce를 뺀 등록 앞부분)에 그 패스키로 한 서명. 등록에는 원래 서명이 없어(4절) 응모권 서명이 열쇠를 가졌음을 증명했는데, 등록만 올릴 때는 그 몫을 이 서명이 한다. 서버가 확인만 하고 **장부에는 싣지 않는다**(공개 장부·등록 형식 그대로).
- 그래서 우주인 등록은 확인이 두 번이다: 패스키 만들기, 바로 이어서 등록 증명 서명. 증명은 nonce를 빼고 서명했으므로 지갑에 두었다가, 회차가 바뀌거나 마감에 걸려 작업 증명을 다시 풀어도 다시 묻지 않는다(`registrar.ts`, 응모를 받는 동안 2초마다 다시 본다). 서명을 취소했거나 증명이 없는 예전 열쇠는 예전처럼 첫 응모 때 응모권과 함께 등록한다.
- 첫 화면을 열 때 이 기기 열쇠가 장부에 있는지(`GET /api/keys/:pub`) 보고, 없고 증명이 있으면 이어서 올린다. 「이미 우주인 등록증이 있어요」로 찾은 열쇠는 장부에서 찾은 것이라 이미 등록돼 있다.
- 서버와 화면 배포: 화면이 `POST /api/register`를 부르므로 서버를 먼저(또는 같은 커밋으로) 올린다. 화면만 먼저 올라가면 등록은 실패해 첫 응모 때 응모권과 함께 등록된다(응모는 깨지지 않는다).

**패스키 이름**
- 기기의 패스키 고르는 창에서 가르게: 국장 패스키는 "카노푸스 우주국장"(전부터), 우주인 패스키는 "우주인 ○○". 이름은 공개 열쇠에서 정해지는데 공개 열쇠는 만든 뒤에야 알아, 만들 때는 "하늘의 별 따기 우주인"으로 만들고 곧바로 `PublicKeyCredential.signalCurrentUserDetails`(지원하는 브라우저만)로 바꾼다. 「이미 우주인 등록증이 있어요」로 찾을 때도 userHandle로 한 번 더 알린다.

### 11-15. 장부 받기: 묶음 파일, 기다렸다 다시 받기, 앞단 상한(2026-10-30)

**왜**: 터미널 검사기가 31회차쯤에서 "rounds/000031.json를 받지 못했습니다(429)"로 멈췄다. 공개 장부는 회차마다 회차 파일·봉인 파일 두 개라 전체 검사는 회차 수의 두 배만큼 요청하는데, 운영 앞단(Traefik)이 IP마다 1분 300번·한꺼번에 60번으로 막았다. 정식은 하루 24회차라 1년이면 파일이 약 1만 7천 개가 되어, 상한이 없어도 낱개로 받으면 느리다.

**정한 것**
- **앞단 상한**(servers 저장소, 2026-10-30 코디네이터가 바꿈): 공개 장부 파일(`/stardraw-api/ledger/`)은 앞단 IP 상한이 없다(끝난 기록을 읽어 주기만 해 비싸지 않고 캐시된다. 누구나 전체를 검사할 수 있어야 한다). 나머지 API는 공유 IP(회사·통신사 NAT) 기준으로 넉넉히(1분 6000번, 한꺼번에 600번). 비싼 일은 앞단 상한이 아니라 응모 상한(IP 앞부분마다 회차당 응모·하루 등록·확인 링크, 11-10)과 응모권마다의 작업 증명이 지킨다.
- **묶음 파일**(장부 형식·낱개 파일은 그대로, 더하기만): 서버는 10회차·100회차 구간이 다 닫히면 그 구간의 회차·봉인 파일을 그대로 담은 `bundles/10/000001.json`(1~10회차), `bundles/100/000101.json`(101~200회차) 꼴을 함께 쓴다. 모양은 `{ v: 1, first, size, rounds: [회차 파일…], seals: [봉인 파일…] }`. 한 번 쓰면 다시 쓰지 않고(바뀌지 않는 파일, 오래 캐시), 서버를 띄울 때 빠진 묶음을 채운다(이미 닫힌 회차도). 묶음을 못 써도 회차는 그대로 닫는다(낱개가 있다).
- **받는 쪽**(`@mighty/stardraw-core` `loadRoundFiles`, 검사기·검증 페이지·화면의 서버 장부가 같이 쓴다): 1회차부터 큰 묶음(100) → 작은 묶음(10) → 낱개 순으로 나눠 받는다. 묶음이 404면(묶음을 내지 않는 옛 서버) 그 구간을 낱개로 받는다. 묶음은 구간·개수·봉인 회차 번호가 맞는지 보고, 내용은 원래대로 처음부터 다시 계산해 검사한다(묶음이라고 덜 믿을 것은 없다).
- **기다렸다 다시 받기**(`politeFetch`): 한꺼번에 4개까지. 429·503이면 Retry-After(초 또는 날짜)만큼, 없으면 1초부터 두 배씩(최대 30초) 0.5~1배로 흔들어 기다린다. 하나가 막히면 같은 받기의 다른 요청도 그때까지 쉰다. 한 요청에 6번·2분까지, 넘으면 "서버가 요청이 많다며 잠시 막았습니다(429). 1~2분 뒤 다시 해 보세요"로 알린다. 화면은 읽기(GET)만 이렇게 하고, 응모·등록(POST)은 서버의 응모 상한(429)일 수 있어 다시 보내지 않는다. 시험은 손으로 옮기는 시계로 정확한 순간을 본다.
- **화면이 처음 받는 양**: 처음 일정표 + 상태 + 묶음(100회차마다 1개) + 다 차지 않은 구간(10회차 묶음 최대 9개 + 낱개 최대 9개). 34회차인 지금 묶음 3개 + 낱개 4개, 정식 1년(약 8천8백 회차)이어도 100여 개이고, 닫힌 회차·묶음은 브라우저 캐시로 받아 다시 열 때는 새로 닫힌 것만 받는다.

**고르지 않은 것**
- 화면은 끝 부분만 받고 전체는 누를 때만: 화면이 일정표(일정 바꾸기·운영 기록)와 내 응모권 확인에 지난 기록을 다 쓰므로 고칠 곳이 넓다. 묶음이면 요청 수 문제는 풀린다.
- 늘 고쳐 쓰는 "끝 부분 묶음"(tail.json): 한 파일로 끝나지만 바뀌는 파일이라 캐시하지 못하고 head.json과 어긋날 때를 다뤄야 한다. 10·100 두 단계면 모든 묶음이 바뀌지 않는다.
- 묶음 하나 크기만(예: 100): 다 차지 않은 구간이 최대 99회차라 처음 받기가 다시 길어진다. 1000 단계는 회차가 그만큼 쌓이면 더한다(받는 쪽은 `BUNDLE_SIZES`만 고치면 된다. 옛 받는 쪽은 모르는 묶음을 묻지 않을 뿐이다).

**배포**: 서버와 화면을 같은 커밋으로 올릴 필요는 없다. 새 받는 쪽은 옛 서버에서 묶음 404 → 낱개로 돌고(2026-10-30 운영 34회차 검사 통과로 확인), 옛 받는 쪽은 묶음을 묻지 않는다. 새 서버는 띄울 때 지난 구간 묶음을 채운다.

### 11-16. 장부 JSON 사본을 앵커 저장소에도(2026-10-30, 사용자와 합의)

**왜**: 장부 내용(회차 기록·응모권·등록·봉인 시각 인증 토큰)은 우리 서버 `/stardraw-api/ledger/`에만 있었다. 서버가 멈추거나 사라지면 아무도 검사할 수 없고, 앵커(`.txt`)에는 기록 해시만 있다. 같은 파일을 공개 GitHub 저장소에도 두면 우리 서버 없이 받아 처음부터 검사할 수 있다.

**올리는 것**(서버 `engine.ts` 앵커 흐름, `outside.ts` `GitHubAnchor`)
- 경로: `ledgers/{장부 id}/ledger/{서버와 같은 상대 경로}` — `genesis.json`, `head.json`, `rounds/NNNNNN.json`, `seals/NNNNNN.json`, `bundles/10/NNNNNN.json`, `bundles/100/NNNNNN.json`. 받는 쪽은 기준 주소만 `https://raw.githubusercontent.com/ybbarng/stardraw-ledger/{브랜치}/ledgers/{장부 id}`로 바꾸면 된다(core `githubLedgerBase`, `loadPublicLedger` 그대로).
- 회차·봉인·묶음·genesis 파일은 서버가 공개한 파일을 **같은 바이트로** 읽어 올린다. `head.json`만은 그 커밋까지 오른 회차를 가리키게 새로 쓴다(`rounds`·`sealed` = 그 회차, `head` = 그 회차 기록 해시, `serverKey`). 서버의 head.json은 다음 회차 봉인 수가 앞설 수 있어서다. 형식은 같다.
- 회차 앵커 커밋 하나에 앵커 파일(`.txt`), 그 회차 회차·봉인 파일, 그 회차에서 끝나는 묶음, head.json(1회차면 genesis.json도)을 담는다. API는 앵커 파일 확인, 브랜치 끝, 트리, 커밋, 브랜치 옮기기 다섯 번(회차당 커밋 하나 유지). 앵커 파일이 이미 같은 내용이면 사본도 같은 커밋에 들어간 것이라 성공으로 본다(응답만 잃은 경우). 기존 `.txt` 형식·경로는 그대로다.
- 브랜치: 회차의 단계를 따른다(시험 trial, 정식 main). 정식 첫 회차를 남기기 전에 지난 시험 회차 사본을 main에도 채워, 정식 시작 뒤에는 **main 하나로 장부 전체**를 받는다. 브랜치가 없으면 main 끝에서 만든다.
- 서버는 브랜치마다 "사본을 올린 마지막 회차"를 저장소(meta `mirrored:<브랜치>`)에 적어 둔다. 회차 사본은 그 브랜치에 바로 앞 회차까지 있을 때만 앵커 커밋에 싣는다(빈틈 없게).

**지난 회차 채우기**
- 띄울 때(그리고 앵커를 남길 때마다) 마지막 앵커 회차의 브랜치에 빠진 사본이 있으면, 커밋 하나에 글 2MB까지 회차를 묶어 차례로 채운다(커밋 메시지 `하늘의 별 따기 장부 파일 1~36회 (장부 …)`). 회차 하나가 2MB를 넘으면 그 회차만 담는다. 이미 같은 내용이면 커밋하지 않는다.
- 크기 어림(2026-10-30 시험 운영): 봉인 파일이 시각 인증 토큰 둘로 약 17KB, 회차 파일은 응모가 적으면 1KB 안쪽이라 회차당 약 18KB, 10회차 묶음 약 180KB. 36회차는 묶음 3개를 더해 약 1.2MB라 **채우기 커밋 1개**다. 100회차 묶음은 약 1.8MB.
- GitHub 상한: 인증 요청 1시간 5천 번, 쓰기(내용을 만드는 요청) 1분 80번·1시간 500번. 회차마다 쓰기 3번(트리·커밋·브랜치), 채우기 커밋도 3번이라 넉넉하다.
- 실패해도 막지 않는다: 사본을 만들지·올리지 못하면 기록을 남기고 앵커 파일만 따로 남긴 뒤(Contents API) 10분 뒤 다시 채운다. 회차 진행(봉인·추첨)은 원래대로 앵커와 따로 돈다.

**받는 쪽**
- core `findGitHubLedger`: main의 `genesis.txt`에서 장부 id를 읽고, main → trial 순으로 `head.json`이 있는 브랜치를 쓴다. 장부 id를 알면(화면) 그것으로 찾는다.
- 터미널 검사기(11-8): 기본 원천이 앵커 저장소다. `--source server`면 우리 서버, `--source <폴더>`면 앵커 저장소를 `git clone` 받은 폴더(장부 id는 `genesis.txt`, 없으면 사본이 하나뿐인 장부. trial 사본은 `git clone -b trial`). 원천이 앵커 저장소여도 서버 `head.json`을 한 번 물어 "아직 앵커에 오르지 않은 회차"를 보인다(앵커는 회차가 닫힌 뒤 오르고 raw는 약 5분 캐시). 서버에 닿지 못해도 검사는 한다. `--compare`는 두 원천을 겹치는 회차까지 대조한다(처음 일정표, 기록 해시, 응모권·등록 목록, 봉인 파일). 다르면 끝 상태 1.
- 화면(`remote-ledger.ts`): 우리 서버를 먼저 쓰고, 서버가 응답하지 않을 때(네트워크 오류·5xx)만 처음 일정표와 지난 회차를 사본에서 받는다. 서버가 4xx처럼 틀린 응답이면 넘어가지 않는다. 서버는 10초마다 다시 묻고 닿으면 서버로 이어 받는다. 사본 위치는 1분마다만 다시 찾는다. raw.githubusercontent.com은 `Access-Control-Allow-Origin: *`(없는 파일 404에도)와 `Cache-Control: max-age=300`을 준다(2026-10-30 확인).

**믿음**: 사본은 운영자가 올리는 것이라 그 자체로 증거가 아니다(강제 push로 고칠 수 있다). 받는 쪽은 늘 처음부터 다시 계산하고, 시각은 시각 인증 토큰이, 다시 시작하지 않음은 `genesis.txt`가 지킨다. 서버와 사본이 다르면 `--compare`로 드러난다.

**고르지 않은 것**
- 파일마다 Contents API로 올리기: 회차당 커밋이 서너 개로 늘고 API도 그만큼 는다.
- 사본만 따로 커밋: 회차당 커밋이 둘이 되고, 앵커와 사본이 어긋나는 순간이 생긴다.
- 서버의 head.json을 그대로: 다음 회차 봉인 수가 앞서 있을 수 있고, 지난 회차를 채울 때는 그 시점의 head가 없다.

**앵커 저장소 README**: 서버가 쓰지 않는다. 2026-10-30 손으로 올렸고, 같은 내용을 [36-stardraw-ledger-readme.md](36-stardraw-ledger-readme.md)에 둔다.

**배포**: 서버를 새 판으로 올리면 첫 진행 때 trial 브랜치에 지난 회차 사본을 채운다. 화면·검사기는 서버보다 먼저 올라가도 된다(사본이 없으면 검사기는 `--source server`를 쓰라고 알리고, 화면은 서버가 응답할 때 사본을 보지 않는다).

### 11-17. 예고를 24시간에서 3회차로, 국장 알림(2026-10-31, 사용자와 합의)

24시간 예고는 큰돈이 걸린 운영 시간 잠금의 관례를 옮긴 값이라 이 서비스에는 과했다(사용자: "2~5회차 뒤면 더 합리적"). 예고가 막는 것은 둘이다: 일정 바꾸기는 응모하는 사람이 다음 회차가 어떻게 돌지 미리 보면 되고, 훔친 관인으로 한 국장 지정은 진짜 국장이 알아채고 취소할 시간이 있으면 된다. 알아채는 시간은 예고 길이보다 알림에 달려 있다.

- **규칙**: 회차 k 기록에 실린 일정 변경·운영 기록의 효력 회차는 `k + 4` 이상(`NOTICE_ROUNDS = 3`, `earliestNoticeRound`). k+1은 이미 응모받는 중이고 k+1·k+2·k+3 동안 장부에 보인 뒤 k+4부터 효력이 생긴다. 1시간 회차면 약 3시간, 20분 시험 회차면 약 1시간. 회차 수로 세므로 예고 중인 일정 바꾸기가 취소되든 말든 같다.
- **이어지는 장부**: 기록에 표시를 더하지 않고 규칙만 바꿨다. 지금까지 실린 기록(20분 회차, 24시간 예고)은 모두 새 규칙보다 늦게 효력이 생기므로 새 규칙으로 검사해도 통과한다(바꾼 뒤 실제 장부 39회차 검사 통과). 운영 기록은 서명된 효력 회차를 들고 있어 18회에 실린 국장 열쇠 지정은 그대로 91회부터다. 옛 규칙이 더 엄격했으므로 옛 기록을 새 규칙으로 보는 것은 아무것도 풀어 주지 않는다.
- **국장 알림**: 서버 `/api/state`의 `pending`(장부에 실렸고 효력 회차가 아직 열리지 않은 운영 기록 수). 서버 감시(servers 저장소 gatus "별 따기 운영 예고", `[BODY].pending == 0`)가 0이 아니면 ntfy로 휴대폰에 알린다. 국장 자신이 한 예고도 알림이 온다(확인용).
- **한계**: 서버를 장악한 사람은 이 응답을 숨길 수 있다. 그래도 효력을 내려면 운영 기록을 장부에 실어야 하고, 장부와 앵커 사본에 남아 검사기의 국장 열쇠 내력에 드러난다. 장부를 밖에서 읽어 알리는 감시(예: 앵커 사본을 정기 검사)는 아직 없다.
