# 36. 하늘의 별 따기(Stardraw): 운영자도 믿을 필요 없는 정시 로또 (2026-10-29)

docs/35의 둘째 안(정시 추첨)을 사용자와 나눈 이야기(응모 비용, 공개 장부, 검증 도구)를 바탕으로 다시 설계한 것이다. 아직 만들지 않았다. 9절의 갈림길을 정하면 10절 순서로 만든다.

## 0. 한 줄 요약

매시 한 회차, 누구나 터미널 도구나 화면으로 응모권 한 장을 낸다. 응모권마다 몇 초짜리 계산(작업 증명)과 서명이 들어간다. 마감 때 응모권 목록을 머클 루트로 묶어 공개하고, 그 뒤에 나올 공개 난수(drand)로 당첨 번호를 만든다. 모든 회차 기록은 해시로 이어진 공개 장부에 쌓이고, 장부 끝 해시는 GitHub에도 남긴다. 누구든 공개된 규칙과 독립 검사 도구로 처음부터 다시 계산해 볼 수 있다. 당첨되면 응모권의 비밀 열쇠로 서명해 당첨자 본인임을 확인하고, 상품(커피)은 사람끼리 앱 밖에서 주고받는다.

## 1. 원칙과 막을 것

**원칙**
1. **운영자도 믿을 필요 없게.** 서버(운영자)가 결과를 고르거나, 결과를 보고 장부를 고치거나, 당첨을 가로챌 수 없게 한다. 할 수 있는 나쁜 일은 남기되 반드시 드러나게 한다.
2. **한 명만 확인해도 드러나게.** 모두가 검사할 필요는 없다. 누구든 마음먹으면 독립적으로 검사할 수 있고, 한 사람만 검사해도 조작이 드러난다.
3. **정직한 사람은 불편하지 않게.** 응모는 몇 초, 검사는 단추 하나.
4. **상품이 작다는 것도 방어다.** 커피 한 잔이라 속여서 얻는 기댓값이 작다. 그 크기에 맞는 만큼만 막는다. 상품이 커지면 다시 본다.

**막을 것(위협)**
| 위협 | 누가 | 이 설계에서 |
|---|---|---|
| 당첨 번호를 고르거나 미리 알기 | 운영자 | 불가능(drand, 3절) |
| 결과를 보고 응모권 끼워 넣기·빼기 | 운영자 | 드러남(머클 루트를 drand 전에 공개) |
| 지난 회차 고치기 | 운영자 | 드러남(체인 + GitHub 앵커) |
| 사람마다 다른 장부 보여 주기 | 운영자 | 드러남(GitHub 앵커, 기기가 기억한 해시) |
| 당첨 가로채기, 남의 이름으로 응모 | 운영자·누구나 | 불가능(서명) |
| 한 사람이 응모권 대량으로 내기 | 누구나 | 비용으로 억제(작업 증명, 상한), 완전히는 못 막음(5절) |
| 응모권 받지 않기(검열) | 운영자 | 막지 못하지만 드러남(내 응모권 포함 증명이 안 나옴) |
| 검사 도구가 거짓말하기 | 운영자 | 독립 검사로 드러남(7절) |

## 2. 구성

```
[터미널 도구]   [게임 센터 화면]          ← 응모·결과·검사
       \            /
        [회차 서버]  ── 장부 파일(정적) ── 누구나 내려받기
            |
     [drand 공개 난수]   [공개 시각 인증 기관(TSA)]   [GitHub 앵커 저장소]
```
- **회차 서버**: 응모권을 받고, 마감·추첨·장부 쓰기를 한다. 개인 서버에 Node + SQLite. 신호 서버처럼 Traefik 요청 한도를 건다.
- **장부**: 회차 기록과 응모권 목록을 정적 파일(JSON)로 낸다. nginx가 내주고 캐시한다.
- **drand**: League of Entropy가 운영하는 공개 난수. quicknet 체인(3초마다, BLS 서명)을 쓴다.
- **공개 시각 인증 기관(RFC 3161 TSA)**: 마감 직후 봉인 값의 시각 인증 토큰을 준다. 기본 DigiCert·Sectigo(11-7).
- **GitHub 앵커 저장소**: 회차마다 기록 해시를 커밋한다(`ybbarng/stardraw-ledger`, 11-7).
- **터미널 도구**: 공개 저장소에서 빌드한 실행 파일 하나. 응모, 결과, 당첨 증명, 장부 검사(`verify`).
- **화면**: 게임 센터 로또 페이지. 응모(직접 누를 때만), 남은 시간, 결과 연출, 콘솔 검사 함수.

## 3. 회차 흐름 (회차 k, 마감 시각 `closesAt` 기준)

회차 시각은 일정표로 계산한다(11-1). 아래는 구현(`packages/stardraw-core`) 기준이다.

**매시 정각 추첨, 55분 마감**(2026-10-29 사용자: "추첨 5분 전 마감"이 명확하다). 마감 `closesAt`은 x:55:00이고 drand 회차는 그 5분 뒤 첫 회차라 정각(x:00:00) 직후에 추첨한다. 이렇게 되도록 일정표 epoch를 맞춘다: `(epoch + 5분) % 회차 길이 = 0`(`isAlignedEpoch`, `alignedEpoch`). 1시간 회차는 x:55 시작 → 다음 x:55 마감 → 정각 추첨, 시험용 10분 회차는 x:05·x:15… 마감, x:10·x:20… 추첨이다. 다음 회차 응모는 앞 회차 추첨(정각) 뒤에 열리므로 응모 창은 회차마다 x:00~x:55다. 화면은 "매시 정각 추첨 · 55분 마감"과 함께 마감까지·추첨까지를 따로 센다.

| 시각 | 일 |
|---|---|
| 앞 회차 확정 직후 | 이번 회차의 **문제 값** = 앞 회차 기록 해시(1회차는 처음 일정표의 genesis 해시). 앞 회차가 drand로 확정돼야 알 수 있어서 미리 계산해 둘 수 없다 |
| ~ `closesAt` (x:55) | 응모권을 받는다(5절 비용·상한). 서버가 받은 시각으로 마감하고 영수증을 준다. 화면·터미널은 `closesAt - closeMargin`(5초)부터 막는다. 마감 뒤 도착한 응모는 "마감됐어요(서버 시각 hh:mm:ss)"로 돌려준다 |
| `closesAt` | 마감. 응모권을 응모권 id 순으로 정렬해 **머클 루트**를 만든다. 응모권 목록 파일과 루트를 공개하고 처리 기한(기본 3분) 안에 봉인 값의 시각 인증 토큰을 공개 기관 여러 곳에서 받는다 |
| `closesAt` + 5분 이후 첫 drand 회차 (정각 직후) | 미리 정해 둔 drand 회차의 값이 나온다(`drandRoundForClose`) |
| 직후 | 당첨 번호를 만들고(4절) 등수를 정해 **회차 기록**을 쓰고 장부 체인에 붙인다. 기록 해시를 GitHub 앵커 저장소에 남긴다 |

- 머클 루트(봉인 값)가 drand 값보다 먼저 시각 인증을 받으므로, 운영자도 결과를 알기 전에 응모권 목록이 고정된다. 봉인 시각이 drand 시각보다 늦으면 그 회차는 무효다(11-1).
- drand 회차 번호는 마감 시각에서 계산식으로 정해져 있어 운영자가 고를 수 없다.
- drand가 멈추면 그 회차는 기다렸다가 정해진 회차의 값이 나오면 확정한다(값을 바꾸지 않는다).

## 4. 데이터와 계산 규칙 (검사기가 따라 할 공개 규칙)

구현은 `packages/stardraw-core`이고, 시험 파일에 시험 값(입력 → 바이트 → 해시)이 있다.

**직렬화와 해시**
- 해시·서명 대상은 모두 **고정 바이너리 형식**이다(8-1 S1). 정수는 빅엔디언, 가변 길이 값(글자, drand 서명)은 앞에 u16 길이를 붙인다. 글자는 UTF-8.
- 해시는 SHA-256. 용도마다 이름을 앞에 붙인다: `taggedHash(이름, …) = SHA-256(이름 ‖ 0x00 ‖ …)`. 이름은 `stardraw/ticket/v1`, `stardraw/record/v1`처럼 판을 담는다.

**열쇠**: ECDSA P-256. 공개 열쇠는 압축하지 않은 65바이트, 공개 열쇠 SHA-256의 앞 16바이트가 **응모자 id**다. 브라우저는 패스키로만 응모한다(11-2). 터미널은 설정 폴더의 열쇠 파일(원시 열쇠)이다.

**응모자 서명**(응모권·당첨 증명·별명): 두 모양 중 하나다.
```
1 ‖ r‖s(64)                                           원시 P-256 서명
2 ‖ authenticatorData ‖ clientDataJSON ‖ DER 서명(각 u16 길이 + 바이트)   패스키(WebAuthn ES256)
```
- 패스키 서명은 `authenticatorData ‖ SHA-256(clientDataJSON)`에 대한 서명이다. 검사기는 clientDataJSON의 `type = "webauthn.get"`, `challenge = base64url(SHA-256(서명할 내용))`, `origin`이 허용 목록(`https://game.byb.kr`)에 있는지, `crossOrigin`이 true가 아닌지, authenticatorData의 rpIdHash = `SHA-256("game.byb.kr")`인지, flags에 UP(0x01, 사람이 있었다)와 UV(0x04, 지문·얼굴·PIN으로 본인 확인을 했다)가 모두 켜졌는지(다른 비트는 보지 않는다, 2026-10-30 UV 추가, 11-10)를 본 뒤 서명을 확인한다.
- 서버 영수증은 서버 열쇠의 원시 서명(64바이트)이다.

**열쇠 등록**: 응모하려면 공개 열쇠를 먼저 장부에 등록한다(그 회차 기록에 들어간다).
```
v(u8 = 1) ‖ kind(u8: 1 원시, 2 패스키) ‖ credentialId(u16 길이 + 바이트) ‖ pub(65) ‖ nonce(u32)
```
- 원시 열쇠는 패스키 번호가 비고, 패스키는 1~1023바이트. 같은 열쇠·같은 패스키 번호는 장부에 한 번만 들어간다(먼저 들어간 것이 이긴다).
- 작업 증명 대상은 `"stardraw/register/v1" ‖ 0x00 ‖ nonce를 뺀 앞부분`, 목표값은 일정표의 `registerPowTarget`(응모권보다 훨씬 무겁게). 문제 값은 응모권과 같다.
- 등록에는 서명이 없다. 남의 공개 열쇠를 먼저 등록해 봐야 서명할 수 없어 쓸모가 없고, 열쇠를 가졌다는 것은 응모권 서명이 증명한다.
- 등록 id = `taggedHash("stardraw/registration/v1", 등록)`. 응모권의 열쇠는 그 회차까지 등록돼 있어야 한다.

**응모권**(앞부분 80바이트 + 응모자 서명)
```
v(u8 = 1) ‖ round(u32, 회차 차례 번호) ‖ numbers(6바이트) ‖ pub(65) ‖ nonce(u32) ‖ 응모자 서명
```
- 번호는 1~45에서 서로 다른 6개, 오름차순.
- 작업 증명 대상(응모권 내용)은 `v ‖ round ‖ numbers ‖ pub`.
- 서명 대상은 `"stardraw/ticket-sig/v1" ‖ 0x00 ‖ v ‖ round ‖ numbers ‖ pub ‖ nonce`.
- 응모권 id = `taggedHash("stardraw/ticket/v1", v ‖ round ‖ numbers ‖ pub ‖ nonce)`. 서명이 빠져 서명 모양만 바꾼 복제도 같은 id다.

**작업 증명**: Argon2id(메모리 16MB, 반복 1, 병렬 1, 결과 32바이트). salt = 문제 값(32바이트), password = `응모권 내용(u16 길이 + 바이트) ‖ n(u32)`. 결과 앞 4바이트(u32)가 목표값(`powTarget`, 일정표에 있다)보다 작은 n을 찾는다. 평균 시도 수는 2^32 / 목표값.
- 메모리를 많이 쓰는 계산이라 그래픽카드의 이점이 작다.
- 한 번 계산이 브라우저에서 수십 ms라, 목표값으로 휴대폰에서 몇 초가 되게 맞춘다.
- 문제 값이 회차마다 바뀌고 응모권 내용이 들어가 미리 계산하거나 남의 계산을 쓸 수 없다.

**drand**: quicknet 체인 해시·공개 열쇠·시작 시각·주기(3초)를 규칙에 고정한다. 서명 메시지는 `SHA-256(drand 회차 u64)`, 난수는 `SHA-256(서명)`. 회차 k가 쓸 drand 회차는 `closesAt + 300초` 이후 처음 나오는 회차다.

**당첨 번호**: `seed = taggedHash("stardraw/seed/v1", round(u32) ‖ drand 난수(32))`. 머클 루트·응모 수는 넣지 않는다(8-1 O4).
- `taggedHash("stardraw/draw/v1", seed ‖ i(u32))`를 i = 0, 1, …로 이어 바이트를 하나씩 읽는다. 225 이상은 버리고(거절 표본), `b % 45 + 1`을 번호로, 이미 나온 번호는 건너뛴다. 7개가 되면 멈춘다. 앞 6개가 당첨 번호, 7번째가 보너스.
- 시험 값: 회차 1, 난수 `b22aad47…0af3`(quicknet 1000000회차) → 나온 차례 45, 29, 5, 38, 37, 41, 보너스 4.

**등수**: 6/45 로또와 같다(1등 6개, 2등 5개 + 보너스, 3등 5개, 4등 4개, 5등 3개).

**회차 기록**
```
v(u8) ‖ round(u32) ‖ prev(32) ‖ count(u32) ‖ merkleRoot(32)
‖ registrationCount(u32) ‖ registrationRoot(32) ‖ rootLoggedAt(u64)
‖ void(u8) ‖ drandRound(u64) ‖ drandSig(가변) ‖ numbers(6) ‖ bonus(u8)
‖ 등수 1~5마다 [개수(u32) ‖ 응모권 id(32) × 개수]
‖ 일정 변경 [개수(u16) ‖ (fromRound, length, closeMargin, powTarget, registerPowTarget 각 u32) × 개수]
‖ 별명 [개수(u16) ‖ (round u32 ‖ 응모권 id(32) ‖ 별명(u16 길이 + UTF-8) ‖ 응모자 서명) × 개수]
```
- 머클 루트(응모권)와 등록 루트는 둘 다 RFC 6962 방식, id 사전 순이다.
- **봉인 값** = `taggedHash("stardraw/seal/v1", round ‖ count ‖ merkleRoot ‖ registrationCount ‖ registrationRoot)`. 마감 직후 시각 인증을 받는 값이다(토큰에는 SHA-256(봉인 값)이 실린다). 등록도 drand 전에 고정돼, 결과를 본 뒤 당첨 응모권의 등록을 빼서 무효로 만들 수 없다.
- 기록 해시 = `taggedHash("stardraw/record/v1", 기록)`. 다음 회차의 `prev`이자 문제 값이 된다.
- 1회차의 prev는 `taggedHash("stardraw/genesis/v1", 처음 일정표)`라 처음 일정표도 체인에 묶인다. 일정표 줄마다 단계(phase)가 실린다(11-6).
- 무효 회차는 번호 0 여섯 개, 보너스 0, 당첨 없음, drandSig 빈 값이다.

**별명**(선택): 지난 회차 당첨 응모권의 열쇠로 `"stardraw/nickname/v1" ‖ 0x00 ‖ round ‖ 응모권 id ‖ 별명`에 서명한다. NFC로 맞춘 1~20자, 보이지 않는 글자 없음, 응모권마다 한 번. 그 회차가 닫힌 뒤에 내므로 다음 회차 기록에 들어가고, 기록 안에서는 응모권 id 순이다.

**검사 표본**: 작업 증명은 내 응모권과 당첨 응모권은 전부, 나머지는 회차마다 `taggedHash("stardraw/sample/v1", drand 난수)`로 고른 몇 장만 본다(무효 회차는 머클 루트와 prev로 고른다).

## 5. 응모 비용과 1인 1장

사용자와 정한 방향: **완전한 1인 1장 대신, 한 장마다 비용이 들게 해 대량 응모를 억제한다.** 현실의 로또(돈)·회사 미니로또(광고 시청)처럼 여러 장은 막지 않되 장마다 값을 치른다. 상품이 커피라 속여서 얻을 것도 적다.

| 장치 | 막는 것 |
|---|---|
| 응모자 id 하나당 회차 1장(서버) | 같은 열쇠로 여러 장 |
| 장마다 작업 증명(몇 초) | 열쇠를 많이 만들어 대량 응모 |
| 공인 IP 앞부분당 회차 응모 상한(예: 20장) | 한곳에서 대량 응모 |
| 새 열쇠 등록에 큰 작업 증명(예: 1분)과 IP당 하루 등록 상한 | 열쇠 대량 생성 |
| 터미널: 기기 식별자 해시(소금 넣음)로 같은 기기 둘째 열쇠 거절 | 설정 폴더만 바꿔 열쇠 여러 개(방지턱. 고친 프로그램은 못 막음) |
| 브라우저: 자동 응모 없음, 실제 누름으로만 응모 | 여러 기기로 매시간 내기를 귀찮게(사용자 의도) |

- 터미널은 스크립트로 자동 응모해도 된다(사용자 결정).
- 지웠다 다시 깔면 열쇠가 바뀌어 예전 응모권은 증명할 수 없다(사용자가 받아들임).
- 남는 한계: 여러 기기·네트워크로 몇 장 더 내는 것, 자원이 많은 사람이 더 내는 것은 막지 못한다. 상품이 커지거나 순위를 붙이면 신원(초대·사내 계정, docs/32)을 다시 본다.
- 버린 안: 사내 감사 표시 봇에서 받은 수만큼 응모권을 주기. 사내 계정으로 1인이 풀리지만, 감사 표시가 응모 수단이 되어 본래 뜻을 흐리고 서로 주고받기를 부른다(사용자, 2026-10-29).

## 6. 당첨 증명 (대면·메신저 모두)

- 커피를 사 줄 사람(확인자)이 무작위 문구를 하나 준다(예: 화면의 "확인 코드 받기").
- 당첨자는 `"claim" ‖ 응모권 id ‖ 확인 문구`에 서명해 건넨다(터미널 `claim` 명령, 화면 단추).
- 확인자는 장부의 공개 열쇠로 서명을 검사한다. 확인 문구가 매번 달라 지난 증명을 다시 쓸 수 없다.
- 당첨자가 원하면 장부에 "이 응모권의 당첨자는 ○○" 표시를 남긴다(선택. 기본은 열쇠만 보인다).

## 7. 검증: 누구든, 독립적으로

**검사 항목**(처음 회차부터)
1. 응모권마다 서명, 작업 증명, 1인 1장, 상한이 맞는지
2. 응모권 목록으로 머클 루트를 다시 만들면 같은지
3. drand 값의 BLS 서명이 진짜인지, drand 회차가 마감 시각 규칙대로인지
4. 당첨 번호와 등수가 규칙대로인지
5. 체인이 이어지는지, 기록 해시가 GitHub 앵커와 같은지
6. 내 응모권이 목록에 들어 있는지(머클 증명)

**검사하는 길**
- **터미널 `stardraw-verify`**(`packages/stardraw-cli`, 2026-10-30 만듦): 공개 저장소에서 받아 내 컴퓨터에서 돌린다. 서버가 내준 코드가 아니라 가장 독립적이다(11-8).
- **화면 단추와 콘솔 함수**(`lotto.verify("2026-10-29T15")` 등): 누구나 쉽게 돌려 볼 수 있다. 다만 서버가 내준 코드라 완전히 독립적이지는 않다.
- **기기가 기억한 해시**: 기기가 마지막으로 본 기록 해시를 기억했다가, 다음 장부가 그것을 이어받지 않으면 경고한다.
- **재현 가능한 빌드**: 같은 커밋으로 누가 빌드해도 같은 화면 파일이 나온다. 사이트는 화면 코드 해시 목록(`/build-hashes.json`)을 함께 내고, 검사기가 사이트 파일·직접 빌드한 파일과 비교한다. 목록을 GitHub 릴리스에도 남기는 일은 준비만 하고 꺼 두었다(11-8).
- **규칙 문서**: 4절이 곧 명세다. 다른 언어로 자기 검사기를 짤 수 있다.

## 8. 신뢰: 무엇을 믿고 무엇을 안 믿나

| 운영자가 하려 하면 | 결과 |
|---|---|
| 당첨 번호 고르기·미리 알기 | 불가능 |
| 당첨 가로채기 | 불가능 |
| 결과 뒤 응모권 끼워 넣기·빼기, 지난 회차 고치기, 사람마다 다른 장부 | 검사하면 드러남 |
| 등수 판정 속이기 | 검사하면 드러남 |
| 특정 응모권 받지 않기 | 막지 못함. 당사자에게는 드러남 |
| 스스로 열쇠 여러 개로 응모 | 남들과 같은 비용이 든다. 서버 상한은 운영자가 어길 수 있다(장부에 같은 IP 정보가 없으니 드러나지 않을 수 있다) |
| 서버 멈춤 | 회차가 밀린다 |

개인정보
- 장부에는 공개 열쇠, 번호, 작업 증명, 서명만 있다.
- IP는 상한 계산에만 메모리에서 쓰고 남기지 않는다.
- 기기 식별자는 소금 넣은 해시만 받는다.

## 8-1. 공격 검토 (규칙이 모두 공개된다는 전제, 2026-10-29)

심각도: 높음 = 설계를 바꿔야 함, 중간 = 장치를 더해야 함, 낮음 = 알고 감수.

### 운영자 쪽

| # | 공격 | 심각도 | 대책(설계에 반영) |
|---|---|---|---|
| O1 | **drand 값을 본 뒤 당첨 응모권을 끼워 넣기.** 머클 루트를 "drand 전에 공개했다"는 것을 남이 증명할 수 없으면, 운영자가 결과를 보고 자기 열쇠로 당첨 번호 응모권을 넣은 뒤 루트를 공개할 수 있다. GitHub 커밋 시각은 커밋하는 쪽이 정할 수 있어 증거가 못 된다 | 높음 | 봉인 값(루트)으로 **공개 시각 인증 기관(RFC 3161 TSA) 여러 곳**의 시각 인증 토큰을 받는다. 토큰은 기관 열쇠로 서명돼 운영자가 시각을 고칠 수 없고, 검사기는 기관 루트 공개 열쇠를 고정해 확인한다(11-7). 가장 이른 토큰 시각이 정해 둔 drand 회차 시각보다 앞서야 그 회차를 유효로 본다. drand 회차는 마감 + 5분으로 넉넉히 둔다. GitHub 앵커는 보조로 남긴다. (처음에는 Sigstore Rekor로 정했다가 2026-10-30 바꿨다: 공급망 서명용 공개 서비스라 이 쓰임이 애매하고, 시험용 로그는 보장이 없다) |
| O2 | **drand 뒤 남의 당첨 응모권 빼기** | 높음 | O1과 같은 시각 증명 + **응모 영수증**: 서버가 응모권을 받으면 `round·응모권 id·받은 시각`에 서버 열쇠로 서명해 돌려준다. 영수증이 있는데 목록에 없으면, 운영자의 잘못을 누구에게나 증명할 수 있다 |
| O3 | **GitHub 앵커 다시 쓰기**: 저장소 관리자는 강제 push로 기록을 바꿀 수 있다 | 중간 | 지난 회차를 고치면 기록 사슬과 봉인 값이 바뀌어, 이미 받은 시각 인증 토큰(운영자가 고칠 수 없다)과 어긋난다(O1). 앵커 저장소는 보조이고, 기기는 마지막으로 본 기록 해시를 기억한다 |
| O4 | **seed 고르기**: seed에 운영자가 바꿀 수 있는 값(머클 루트, 응모 수)이 들어가면 응모권을 넣고 빼며 원하는 seed를 찾을 수 있다 | 높음(넣으면) | seed는 `round`와 drand 값만으로 만든다(4절 그대로). **머클 루트를 seed에 넣지 않는다**를 규칙에 못 박는다 |
| O5 | **브라우저 응모자의 당첨 가로채기**: 열쇠는 내보낼 수 없어도, 서버가 내준 화면 코드는 그 열쇠로 아무것에나 서명할 수 있다. 운영자가 화면 코드를 바꿔 당첨 확인 문구에 몰래 서명하게 하면 당첨을 가져갈 수 있다 | 중간 | 화면 코드 해시 공개·재현 빌드·터미널 검사기(11-8, 2026-10-30)로 사이트가 내준 코드가 공개 저장소의 그 커밋인지 누구나 비교할 수 있다. 큰 상품이 걸리면 "터미널 도구(소스에서 빌드)로 증명하기"를 권한다. 브라우저 열쇠는 그 화면을 내주는 쪽을 믿어야 한다는 한계를 화면에 적는다 |
| O6 | 사람마다 다른 장부·문제 값 보여 주기 | 중간 | 문제 값 = 앞 기록 해시라 장부와 함께 검사된다. 기록 해시를 GitHub 앵커 저장소에 남겨 모두가 같은 값과 비교한다 |
| O7 | 운영자가 열쇠 여러 개로 응모(상한 무시) | 낮음 | 막지 못한다. 작업 증명 비용은 똑같이 든다. 장부에 회차별 응모 수와 열쇠 첫 등장 시각을 남겨 이상한 몰림이 보이게 한다 |
| O8 | drand 회차 바꿔치기, 다른 체인 쓰기 | 낮음 | 체인 해시(quicknet)와 회차 계산식을 규칙에 고정하고 검사기가 확인한다 |

| # | 공격 | 심각도 | 대책 |

| P4 | 당첨 증명 재사용·남에게 넘기기 | 낮음 | 확인 문구가 매번 달라 재사용이 안 된다. 열쇠째 넘기는 것은 막을 이유가 없다(상품이 사람끼리) |

| P6 | 마감 직전 몰아치기, 시계 다툼 | 낮음 | 마감은 서버가 받은 시각으로 정하고 영수증에 적는다 |
| P7 | **당첨자 확인 요청 폭탄·칸 채우기**: 누구나 당첨 응모권에 확인 요청을 보낼 수 있으면 100명이 눌러 요청 100개가 가고, 응모권당 상한을 두면 장난꾼이 칸을 채워 진짜 확인을 막는다 | 중간 | 2026-10-30 다시 설계: 당첨자가 응모권 열쇠로 서명해 만든 **한 번 쓰는 확인 링크**로만 요청이 붙는다(서버가 장부의 응모권 공개 열쇠로 서명을 확인). 응모권당 열린 링크 10개 상한은 주인만 만들 수 있어 방해 도구가 되지 않는다. IP 앞부분마다 하루 링크 만들기 30번, 없는 링크 조회 60번 |

| P9 | 확인 링크 가로채기·엿보기 | 낮음 | 토큰(144비트)은 `#` 뒤라 서버 로그·Referer에 남지 않고, 서버는 토큰 해시만 둔다. 가로챈 사람이 먼저 「확인 시작」하면 진짜 받은 사람 화면에 "이미 사용된 링크"가 떠서 드러나고, 별 세 개는 당첨자가 알린 그 사람에게만 가므로 가로챈 사람은 초록불을 켤 수 없다 |

| S1 | **직렬화 차이**: JSON 숫자·유니코드·키 순서가 언어마다 달라, 검사기끼리 해시가 어긋나거나 같은 내용에 다른 id가 생긴다 | 높음 | JSON 대신 고정 길이 바이너리 형식으로 해시한다(필드 순서·길이 고정, 번호는 바이트 6개). 규칙 문서에 시험 값(입력 → 바이트 → 해시)을 둔다 |
| S2 | **머클 트리 변조**: 잎과 가지를 구별하지 않으면 가지 값을 잎인 척하는 위조, 홀수 개 처리 차이로 다른 루트가 생긴다 | 높음 | RFC 6962 방식(잎은 0x00, 가지는 0x01을 앞에 붙여 해시, 홀수 개 처리 규칙 고정)을 따른다. 정렬 순서(응모권 id 순)도 규칙에 둔다 |
| S3 | 당첨 번호 뽑기 치우침 | 중간 | 거절 표본 방식과 카운터 방식을 정확히 쓰고 시험 값을 둔다(4절) |
| S4 | **공급망**: 설치 스크립트(`curl | bash`), GitHub 계정 탈취, 의존 패키지 | 중간 | 릴리스 체크섬과 Sigstore 서명, 재현 가능한 빌드, 의존성 판 고정. 설치 스크립트는 체크섬을 확인하고, 내용을 페이지에 보인다 |
| S5 | drand 신뢰 | 낮음 | League of Entropy 노드 과반이 짜면 미래 값을 알 수 있다. 커피 규모에서는 감수한다. quicknet이 바뀌거나 멈추는 때의 규칙(다음 회차로 미루기)을 둔다 |

### 개인정보

- 같은 공개 열쇠로 낸 응모가 모두 이어져 보인다. 사람은 드러나지 않지만, 당첨 때 이름을 밝히면 지난 응모가 모두 그 사람 것으로 보인다. 열쇠를 바꾸는 방법(새 열쇠 등록)을 안내한다.
- 서버는 상한 계산을 위해 IP와 기기 해시를 잠깐 본다. 저장하지 않고, 이 사실을 화면에 적는다.

### 이 검토로 바뀐 설계 (요약)

1. 봉인 값(루트)의 시각 증명을 공개 시각 인증 기관 여러 곳으로 한다(O1·O3, 처음에는 Rekor였다가 2026-10-30 바꿈). 기록 해시는 GitHub 앵커에 남긴다(O6). drand 회차는 마감 + 5분이다.
2. 응모 영수증을 서버 서명으로 준다(O2).
3. seed에 머클 루트를 넣지 않는다(O4).
4. 서버 확인 순서와 Argon2 동시 실행 제한을 둔다(P1).
5. 작업 증명은 표본 검사가 기본이다(P2).
6. 해시 대상은 고정 바이너리 형식이다(S1).
7. 머클 트리는 RFC 6962 방식이다(S2).
8. 브라우저 열쇠는 화면 코드를 믿어야 한다는 한계를 알리고, 큰 상품이면 터미널로 증명하게 한다(O5).

## 11. 하늘의 별 따기(Stardraw): 사용자와 정한 것 (2026-10-29)

이름은 **하늘의 별 따기(영어 Stardraw)**(처음 이름 빕또·bybtto에서 2026-10-29 바꿈). 9절 갈림길과 화면 요구를 아래처럼 정했다. "고름"은 사용자가 맡긴 기본값으로 내가 고른 것이고 바꿀 수 있다.

**정한 것(사용자)**
- 참여: 누구나(9절 1번).
- 회차: 우선 1시간. 회차 길이는 바꿀 수 있어야 한다(2시간, 하루, 더 짧게).
- 응모 화면은 실제 로또 용지에 번호를 칠하듯, 추첨은 실제 추첨기처럼 그럴싸하게.
- 보안 설계를 소개하고 직접 해 보며 배우는 페이지, 지난 회차 당첨 이력, 내 상태와 응모 이력을 모두 볼 수 있게.
- 당첨되면 내가 알 수 있고, 운영자(사용자)에게 연락해 증명할 수 있게. 당첨 사실과 증명 과정의 사용 경험이 좋아야 한다.
- 나중에: 게임 한 판 = 응모권 한 장 같은 연결.
- **상품·상금 없음.** 등수는 실제 로또와 같다(1~5등). 상품은 하늘의 별 따기 밖에서 사용자가 정한다(예: 회사에 알리며 "1등은 커피"). 장부에 "상품 받음" 표시는 두지 않는다.
- 소개 문구: **"로또 1등과 하늘의 별 따기, 어느 게 더 쉬울까요?"** (게임 목록 카드 설명, 페이지 제목 아래). 앞서 정한 "재미로 즐기는 로또…"는 버렸다.
- **화면은 별자리 테마**다. 다만 용어는 실제 로또와 같다(응모, 응모권, 회차, 당첨, 1~5등). 별자리는 화면 꾸밈에만 쓴다(열쇠 별자리 지문은 사용자가 없앴다, 2026-10-29). 게임 이름만 "하늘의 별 따기"다("별을 땄다" 같은 말은 가벼워 보여 쓰지 않는다, 사용자).
  - 추첨 연출은 네모 하늘 룰렛이다(11-3). 처음 만든 유리 천구의 공 연출은 "공이 떠서 떨다 갑자기 내려와 어색하다"는 사용자 의견으로 버렸다(2026-10-30).
  - 첫 화면 비교: 눈에 보이는 별은 약 9천 개라 별 하나 맞히기는 1/9,000, 로또 1등은 1/8,145,060으로 **약 900배 어렵다**.
- 주소: `game.byb.kr/stardraw`(이 저장소). 화면마다 주소가 있다(2026-10-30 사용자: 뒤로가기가 게임 목록으로 나가 불편): 첫 화면 `/stardraw`, 응모 `/stardraw/enter`, 내 응모 `/stardraw/mine`(영수증 `#t-<일련번호>`), 지난 회차 `/stardraw/rounds`(회차 `#12`, 추첨 보기 `#draw-12`, 당첨자 확인 `#check-12-1`). 뒤로가기는 바로 전 화면, 새로고침은 그 화면에 머문다. 응모를 마치면 응모 화면 기록을 영수증으로 바꿔 뒤로가기가 응모 화면으로 돌아가지 않는다. 데모는 한 페이지다.
- 응모권 공유(2026-10-30 사용자): 영수증의 「응모권 공유」가 공유 시트(Web Share)로, 없으면 링크 복사로 "하늘의 별 따기 {n}회에 응모했어요. 추첨은 {오후 h시}!"와 `/stardraw/ticket#{회차}-{일련번호}`를 보낸다. 그 주소는 읽기 전용 영수증이다: 추첨이 끝난 회차는 공개 장부에서 찾아 맞힌 별과 등수까지, 추첨 전에는 이 기기에서 낸 응모권만 "추첨까지 n분"과 함께 보이고 다른 기기에서는 "마감 뒤에 보여요"(마감~추첨 사이는 "추첨 뒤에 보여요"). 없으면 "이 응모권을 찾을 수 없어요". 아래에 「나도 응모하기」. 서버에 따로 찾기 API를 두지 않는다(추첨 전 응모권은 장부에 아직 없다).
- **브라우저 열쇠는 패스키.** 사용자가 사람들에게 패스키를 권하고 싶어 해, 하늘의 별 따기가 재미로 해 보는 패스키 연습장도 겸한다(만들기 → 다른 기기·브라우저에서 내 응모권 보기).

**고른 기본값**
- 판: 6/45, 보너스 1개(실제 로또와 같게). 한 열쇠는 회차당 한 줄(실제 용지의 A줄만 쓴다).

- 회차 id는 시각 문자열 대신 **차례 번호**(1, 2, 3, …)다. 회차 길이가 바뀌어도 이어진다.

### 11-1. 회차 길이 바꾸기와 마감 여유

- **일정표**를 장부에 기록한다: `{ fromRound, length, closeMargin }` 목록. 바꿀 때는 새 줄을 더하고, 효력은 **24시간 뒤에 시작하는 회차부터**다. 이미 응모받는 회차의 시각은 바꿀 수 없다.
- 회차 k의 시각은 일정표만으로 계산된다: `opensAt`(앞 회차 마감), `closesAt`. 검사기도 같은 계산을 한다. epoch는 추첨이 정각에 오게 맞춘다(3절).

| 회차 길이 | 마감 | 추첨(drand) | 응모 창 | 화면 마감 |
|---|---|---|---|---|
| 1시간(정식) | 매시 x:55:00 | 정각 x:00:00 직후 | x:00 ~ x:55 | x:54:55 |
| 10분(시험 기본) | x:05·x:15·…·x:55 | x:10·x:20·…·x:00 직후 | 추첨 직후 ~ 다음 마감(5분) | 마감 5초 전 |
- **시계 오차 흡수**
  - 응모 마감은 서버가 **받은 시각**으로 정하고 영수증에 적는다.
  - 화면과 터미널은 `closesAt - closeMargin`(기본 5초)부터 응모를 막는다. 사용자 기기 시계가 틀려도 서버 시각(응답 헤더)과 차이를 재서 보정하므로 여유는 시계 차이·전송 시간만 덮으면 된다(처음 60초 → 2026-10-29 5초로 줄임: 마감 시각이 x:55로 분명해져 1분 일찍 막으면 오히려 헷갈린다).
  - 마감 뒤 도착한 응모(앞 회차 응모권이거나 이미 봉인한 회차)는 "마감됐어요(서버 시각 hh:mm:ss)"로 분명히 알린다(`closedMessage`, 한국 시각).
  - 마감 뒤 **처리 기한**(기본 3분) 안에 봉인 값(응모권 루트 + 등록 루트, 4절)의 시각 인증 토큰을 공개 기관에서 받는다. 서로 다른 기관 1곳 이상의 맞는 토큰이 있어야 봉인 성공이고, 봉인 시각(`rootLoggedAt`)은 그중 가장 이른 시각이다(11-7). 기한 안에 한 곳도 못 받으면 그 회차는 무효다.
  - drand 회차는 `closesAt + 5분` 이후 첫 회차다. drand 시각은 drand 체인의 시작 시각과 주기로 계산되므로 우리 서버 시계와 상관없다.
  - 봉인 시각이 drand 시각보다 늦으면 그 회차는 **무효**(당첨 없음, 기록은 남김)다. 운영자가 일부러 늦춰도 그때는 결과를 모르므로 결과를 고를 수 없다.

### 11-2. 당첨을 알고 증명하기

**열쇠: 브라우저는 패스키, 터미널은 열쇠 파일**
- 패스키(WebAuthn, ES256 = P-256)는 iCloud 키체인·Google 비밀번호 관리자·1Password에 저장되어 기기를 바꿔도 따라온다. 비밀 열쇠는 사용자도 서버도 볼 수 없어 복사당하지 않는다.
- 응모와 증명 때마다 Face ID·지문 한 번. 사람이 직접 눌러야 해 브라우저 자동 응모가 막힌다(5절 사용자 의도와 같다).
- 서버는 **패스키 번호(credential id)와 공개 열쇠만** 저장한다. 패스키는 만들 때만 공개 열쇠를 알려 주므로 등록 기록을 장부에 남긴다. 이름·이메일·비밀번호·로그인 세션은 없다. 패스키 "사용자 이름" 칸은 "하늘의 별 따기"다. 응모자를 부르는 표시(코드·별명)는 두지 않는다(사용자).
- 새 기기에서는 따라온 패스키로 Face ID만 하면 브라우저가 패스키 번호를 알려 주고, 서버가 그 번호로 공개 열쇠를 찾는다.
- 서명은 WebAuthn 형식(authenticatorData ‖ clientDataJSON 해시에 서명, clientDataJSON의 challenge = 서명할 내용의 해시)이라 검사기가 이 형식을 읽는다.
- **브라우저 응모는 패스키로만**(2026-10-29 사용자). 기기 안 열쇠(IndexedDB)로 응모하는 길은 없앴다. 패스키를 쓸 수 없는 환경은 응모 대신 안내한다: 앱 안 브라우저(카카오톡·네이버 앱·인스타그램 등) → "Safari·Chrome으로 열어 주세요"와 주소 복사, WebAuthn이 없는 브라우저 → 업데이트 안내, 이 기기 잠금을 못 씀 → "화면 잠금을 켜면 이 기기에서 바로, 지금은 휴대폰(QR)·보안 키로", 만들기·서명 취소 → "응모되지 않았어요" + 「패스키가 뭐예요?」 문답, ES256을 못 만드는 인증기(일부 오래된 Windows Hello) → "다른 기기 사용(휴대폰 QR)". 터미널은 열쇠 파일(백업은 파일 복사).
- 만들기 옵션: ES256(-7)만, attestation `none`, residentKey `required`(새 기기에서 이름 없이 찾기), userVerification `required`, 기기 종류(authenticatorAttachment)는 정하지 않는다(iCloud·Google 비밀번호 관리자·1Password·Bitwarden·Windows Hello·보안 키·휴대폰 QR 모두). 서명도 userVerification `required`. 검사기는 서명마다 UV 표시를 요구하고, 화면은 만들 때 받은 authenticatorData에 UV가 없으면 미리 "본인 확인을 하지 못합니다"로 막는다(11-10).

**패스키 자연스럽게 쓰게 하기(사용자: 이 게임의 목적 중 하나, 2026-10-29)**
- 원칙: 등록을 따로 시키지 않고 응모 자체가 패스키 만들기다. 이득을 쉬운 말로, 조르지 않는다. 패스키에 응모권·확률 혜택은 주지 않는다(공정성).
- 패스키 등록과 서명을 나눈다(2026-10-30 사용자, 같은 날 화면 이름은 「우주인 등록」·「이미 우주인 등록증이 있어요」로 바뀜, 11-9): ① 패스키가 없으면 별을 고르기 전에 "응모하려면 패스키가 필요해요 · 패스키 만들기"(등록만, 확인 한 번). 다른 기기에서 만든 패스키가 따라왔으면 「이미 패스키가 있어요」(이름 없이 찾기). ② 「이 별 6개로 응모하기」가 서명한다(확인 한 번). 두 번째 응모부터는 ②만. 데모도 같은 두 단계로 흉내 시트("패스키를 만들까요?", "패스키로 서명할까요?")를 띄운다. 게임 화면에는 덧붙이는 설명 문장을 두지 않는다(2026-10-30 사용자: "쓸데없는 문구들은 추가하지 마"). 무엇을 하면 되는지, 왜 막혔는지만 짧게.
- 「패스키가 뭐예요?」는 사람들이 실제로 걱정하는 질문에 존댓말로 답하는 문답이다: 얼굴·지문이 서버로 가나요, 서버가 해킹되면요, 가짜 사이트에 속으면요, 휴대폰을 잃어버리면요, 비밀번호보다 왜 나아요, 저를 추적하나요, 어디에 저장되나요, 아이폰과 안드로이드를 같이 쓰면요. 솔직한 한계 한 줄("휴대폰 잠금 비밀번호를 아는 사람은 지문 대신 그 비밀번호로 패스키를 쓸 수 있어요". 패스키는 지문·Face ID가 안 되면 기기 잠금 PIN·패턴·암호로도 열린다)과 "다른 기기에서 열어 보기" 연습을 붙인다. 문답은 설명 페이지 "패스키와 보안"(/stardraw/about#passkey)에만 두고, 게임 화면은 「패스키가 뭐예요?」 링크로 잇는다.
- 내 응모 화면에는 열쇠 칩·"서버가 가진 것" 비교를 두지 않는다(설명 페이지 "패스키와 보안"으로 옮김, 2026-10-30). 패스키 기억이 없는 기기에서는 「다른 기기에서 내 응모권 찾기」: 따라온 패스키로 한 번 확인하고(이름 없이 찾기), 장부에서 그 패스키 번호의 공개 열쇠를 찾아 닫힌 회차의 내 응모권을 모은다(서버 `GET /api/passkeys/:id`).
- 패스키로 서명한 응모권은 영수증에 작은 열쇠 표시("서명: 패스키")가 붙는다. 꾸밈일 뿐 혜택이 아니다.
- 버린 안: 기기 열쇠 응모자에게 "패스키로 바꾸기"를 띄우기, 기기 열쇠로 낸 응모권이 당첨되면 패스키 만들기를 권하기(브라우저는 패스키로만 응모하게 되어 필요 없어졌다).
- 패스키는 주소(game.byb.kr)에 묶인다. 주소를 옮기면 옛 패스키 응모권 증명이 어려워진다.
- 버린 안: 영수증의 QR·코드를 보여 주면 당첨으로 보기(무기명이라 스크린숏으로 복사된다), 영수증의 "긁는 칸"에 열쇠 백업 넣기(긁는 칸도 같은 저장소에 있어 열쇠와 함께 사라진다).

**내가 알기**
- 추첨 때 보고 있으면: 공이 나올 때마다 하늘의 그 별이 켜지고(금빛), 내 별(하늘색)과 겹치면 초록으로 강조한다. 등수에 맞는 연출(1등은 화면이 빛난다).
- 나중에 오면: 지난 응모권이 **봉한 봉투**로 쌓여 있고, 누르면 그 회차 추첨을 다시 돌리며 맞춰 본다.
- 터미널: `stardraw status`(자동 응모와 함께 돌리면 당첨 때 알림).
- 내 응모 이력은 내 공개 열쇠로 장부에서 찾는다. 기기 알림(Web Push)은 나중에 본다.

**당첨자 확인(2026-10-30 다시 설계: 당첨자가 먼저 한 번 쓰는 확인 링크를 보낸다)**
1. 당첨자 기기는 공개 장부로 스스로 당첨을 안다. 내 응모(·첫 화면)에 **카노푸스 우주국 당첨 안내** "시험 n회 k등입니다. 당첨을 알리고 싶은 사람에게 확인 링크를 보내세요"가 뜬다(서버 메시지가 아니라 장부 계산이라 위조할 수 없다, 카드 아래 "공개 장부로 이 기기가 계산한 안내입니다").
2. 「확인 링크 만들기」 → 등록증(패스키)으로 서명 한 번. 기기가 무작위 토큰(18바이트 = 144비트)을 만들고 `토큰 해시 ‖ 회차 ‖ 응모권 id`에 응모권 열쇠로 서명해 서버에 초대를 올린다. 서버는 장부의 그 응모권 공개 열쇠로 서명이 맞아야 받는다 → **응모권 주인만 링크를 만든다**. 서버는 토큰 해시만 둔다. 링크는 `game.byb.kr/stardraw/check#토큰`(토큰은 `#` 뒤라 서버 로그·Referer에 남지 않는다). 공유(Web Share)·복사 단추. 링크는 7일, 응모권당 열린 링크 10개. 「다른 사람에게 보낼 새 링크」로 사람마다 따로 만든다.
3. 확인하는 사람: 링크를 열면 서버가 회차·응모권 id를 알려 주고, 기기가 공개 장부로 그 회차 당첨 응모권인지 확인해 "n회 k등 당첨자가 보낸 확인 링크입니다"를 띄운다. 「확인 시작」 → 임시 ECDH 열쇠를 만들어 그 링크에 요청을 붙이고, 링크는 이때 닫힌다(한 번만). 이미 쓰인 링크면 "이미 사용된 링크입니다. 당첨자에게 새 링크를 받으세요", 없거나 기한이 지났으면 "없는 링크이거나 기한(7일)이 지났습니다". 같은 기기에서 같은 링크를 다시 열면 이어서 확인한다.
4. 당첨자 기기: 그 한 건의 요청을 스스로 찾아(열 때·열려 있는 동안) "보낸 확인 링크로 n회 k등 당첨 확인 요청이 왔습니다", 작게 "○시에 만든 링크 · 전달: 카노푸스 우주국", "링크를 보낸 적이 없으면 거절하세요". 「등록증으로 승인」 → 패스키 서명과 자기 임시 ECDH 공개 열쇠를 올린다. [거절]도 알린다. **24시간** 안에.
5. 당첨자 화면: 네모 하늘에서 **별 세 개**가 ①②③ 차례로 빛난다. "링크를 보낸 사람에게, 당첨을 알렸던 그 메신저·메일로 이 세 별 이름을 차례대로 보내 주세요", "별 세 개는 내가 당첨을 알린 그 사람에게만 보내세요." 보낼 별은 화면을 닫아도 남는다.
6. 확인하는 사람 화면: 브라우저가 장부의 응모권 열쇠로 서명을 직접 검사하고, 통과하면 "당첨자가 보낸 별 세 개를 하늘에서 차례로 눌러 주세요". 맞으면 초록불이 하늘 전체로 번지며 "n회 k등 당첨자 본인이 맞습니다". 틀리면 다시, **세 번 틀리면 닫는다**(새 링크를 받는다). 별 누르기에는 기한이 없다. 당첨자 화면에는 "확인하는 분의 화면에 초록불이 켜졌습니다". 실패면 빨간 "본인 확인에 실패했습니다"와 이유.
- **판정은 늘 확인하는 사람의 기기에서** 한다. 당첨자 화면이나 그 스크린숏은 증거가 아니다.
- **별 세 개를 ECDH로 뽑는 이유**: 요청 문구와 서명만으로 뽑으면 둘 다 서버를 거치므로, 서버(나 응답을 엿본 누구든)가 별을 알아 가짜 당첨자에게 넘길 수 있다. 양쪽 기기가 요청마다 임시 P-256 ECDH 열쇠를 만들어 공개 열쇠만 주고받으면 공유 비밀은 두 기기만 계산할 수 있어 서버는 별을 모른다. 당첨자는 서명할 문구에 양쪽 임시 공개 열쇠를 묶어(`sasChallenge`) 가운데서 열쇠를 바꿔치기할 수 없게 한다. 별 = taggedHash("stardraw/sas/v1", 공유 비밀 ‖ 요청 id)에서 당첨 번호와 같은 거절 표본으로 1~45 중 서로 다른 3개(차례 있음). 규칙 패키지 `sas.ts`, 시험 값은 Node·파이썬으로 따로 맞췄다.
- 확인 요청의 요청자 칸(`claim` 형식은 그대로)은 이름 대신 늘 "확인 링크"(`CHECK_LINK_REQUESTER`)다. 확인 문구 증명 형식과 공개 장부·기록 형식은 바꾸지 않았다.
- 확인하는 사람 기기는 확인 기록(링크 토큰 해시, 임시 ECDH 비밀 열쇠는 꺼낼 수 없는 CryptoKey로 IndexedDB 2판, 1판 묶음 기록은 버린다)을 저장해 화면을 닫았다 열어도 이어서 확인한다. 지난 회차 화면에 "확인 중인 당첨자 N건 · 별 세 개를 기다리는 중".
- **확인함 표시**: 초록불이 켜진 응모권은 확인한 날짜와 함께 확인하는 사람 기기(IndexedDB)에만 남고, 그 기기의 지난 회차 화면에서 그 응모권 옆에 "확인함 · 10/30"이 보인다. 메모 칸·「상품 드림」·메모 내보내기/들여오기는 두지 않는다(2026-10-30 사용자: "메모를 옮길 일은 없고, 어차피 패스키에 응모/당첨 모두 귀속된다").
- 전달 서버(`apps/stardraw-server` relay.ts): `POST /api/confirm/invites`(서명한 초대) · `/peek`(토큰 → 회차·응모권, 쓰였는지) · `/start`(토큰 + 확인자 임시 공개 열쇠 → 요청, 초대를 닫는다) · `/open`(응모권 id들로 열린 요청) · `/:id/answer`(서명이 맞아야 받는다) · `/:id/report`(요청을 붙인 기기의 결과 열쇠). 토큰은 주소가 아니라 본문으로만 보낸다. 요청·응답·결과 보관 **7일**. 연습 장부·데모는 같은 기기 안(localStorage) 전달로 흉내 낸다(`ConfirmRelay` 인터페이스, 초대 서명은 검사하지 않는다).
- 지난 방식(2026-10-29~30): 지난 회차의 등수 줄에서 누구나 「당첨자 확인」을 눌러 그 등수 응모권 모두에 요청(묶음)을 보내고 "확인하는 사람 이름"을 적었다. 요청 폭탄·칸 채우기·이름 사칭(8-1 P7·P8) 때문에 버렸다. 서버는 옛 경로를 없애고 옛 요청 행을 처음 한 번 지운다(응모 0장일 때라 호환이 필요 없었다).
- 「당첨 알리기」 공유(Web Share, 없으면 링크 복사)는 확인과 따로 두는 선택 기능이다(아직 만들지 않음).
- 터미널: `stardraw confirm`(나중).
- 받는 사람이 정해진 한 번에 보내는 증명(`makeDirectClaim`)도 규칙 패키지에 남긴다. 화면은 쓰지 않는다.
- 버린 안: 바로 보내는 증명 링크, 6자리 확인 번호·QR(사용자: 복잡하다), 열쇠 별자리 지문(별자리가 여러 개면 헷갈린다), 확인 10분 제한(별 이름을 메일·DM으로 받는 데 시간이 걸린다).

**별명 남기기(선택)**: 당첨자가 원하면 지난 회차 화면에 "12회 1등: 철수"를 남긴다. 그 응모권 열쇠의 서명으로만 남길 수 있다.

### 11-4. 나중에: 게임 한 판 = 응모권 한 장

- 혼자 하는 게임은 기기 안에서 돌아 "했다"는 것을 증명할 수 없다. 화면을 고치면 판을 안 해도 응모권을 받는다.
- 온라인 대전은 두 사람이 서명한 기록이 있어 조금 낫지만, 둘이 짜면 똑같다.
- 그래서 "게임 한 판 = 작업 증명 대신 쓰는 비용"으로 보되, 응모권 상한(열쇠당 회차 1장)은 그대로 둔다. 그때 다시 설계한다.

### 11-6. 시험 운영과 정식 시작: 이어지는 장부(2026-10-30 사용자: 장부를 새로 만들지 않고 하나의 사슬을 끝까지 잇는다)

처음에는 "시험 장부를 지우고 정식 장부를 새로 만든다(패스키 등록만 옮김, `start-live`)"로 정했다가 2026-10-30 바꿨다. 시험 회차도 영원히 남고, 정식 시작은 장부 안의 일정 바꾸기다. `start-live`와 등록 옮기기(`carried`)는 코드·시험·문서에서 지웠다.

**단계(phase)**
- 일정표 한 줄(`ScheduleEntry`)에 `phase: "trial" | "live"`를 둔다. 줄 바이트 끝에 u8(0 없음, 1 시험, 2 정식)로 실려 genesis 해시와 기록 해시에 묶인다.
- 서버의 새 장부는 시험 단계 한 줄로 시작한다(`STARDRAW_ROUND_SECONDS`, 기본 10분. `STARDRAW_EPOCH`을 비우면 띄운 뒤 첫 맞춘 마감이 1회차 마감).
- 정식 시작 = 일정 바꾸기 한 줄 추가(`fromRound`, length 3600, closeMargin 5, 작업 증명 목표값, `phase: "live"`). 기존 "그 기록 마감 + 24시간 뒤에 시작하는 회차부터" 규칙을 그대로 따라 하루 전에 장부에 예고된다.
- 규칙(`checkSchedule`·`checkScheduleChange`): 단계는 모든 줄에 있거나(서버 장부) 모두 없다(기기 안 연습 장부). 정식 단계 뒤로 시험 단계를 둘 수 없다.
- 서버는 `STARDRAW_MODE` 없이 장부의 지금 단계를 따른다. `/api/state`의 `mode`(지금 회차 단계)로 화면이 시험 띠를 띄우고, `liveFrom`(정식 첫 사슬 회차, 없으면 null)을 함께 준다. 시각 인증은 단계와 상관없이 켠다.

**보이는 회차 번호**
- core `displayRound(schedule, round)` 하나로 화면·검사기·검증 페이지가 같이 쓴다: 정식 단계 첫 회차가 "정식 1회", 그 앞은 "시험 n회", 단계가 없으면 "n회". 화면은 연습 장부에서 예전처럼 "제 n회"를 보인다(`round-label.ts`).
- 데이터의 기준은 늘 사슬 회차 번호(`round`)다: 기록, 공유 주소(`/stardraw/ticket#<회차>-…`), 앵커 경로.
- 화면의 원격 장부(`RemoteLedger.schedule`)는 처음 일정표에 닫힌 기록의 일정 바꾸기를 모두 반영한 일정표다(정식 단계부터 회차 길이가 1시간으로 바뀐다).

**다시 시작 막기**
- 서버는 장부를 처음 만들 때 앵커 저장소 main 브랜치에 `genesis.txt`(장부 id, genesis 해시, epoch)를 한 번 커밋한다. 이미 다른 내용이 있으면 덮어쓰지 않고 1분마다 다시 시도하며 기록을 남긴다(사람이 봐야 한다).
- 검사기(`verifyLedger`의 `genesisAnchorVerifier`, anchor.ts `githubGenesisVerifier`)는 장부의 처음 일정표가 그 파일과 같은지 본다. 다르면 "장부를 다시 시작했다"로 실패, 없으면 건너뜀. 규칙 "이 장부는 다시 시작하지 않는다"는 검증 페이지에도 적었다.
- 회차 앵커 브랜치는 그 회차의 단계로 정한다(시험 `trial`, 정식 `main`, `anchorBranch`). 검사기도 같은 규칙으로 읽는다.

**정식 예약 명령**
- `node server.mjs schedule-live --from <ISO, x:55> [--round-seconds 3600]`: 돌고 있는 서버의 데이터 폴더에 예약만 넣는다(`pendingChange`). 명령은 먼저 규칙을 확인한다: 시험 단계 장부인지, 이미 정식 단계가 있거나 예약이 있는지, 시작이 정각 추첨에 맞는지(1시간이면 x:55), 시험 회차가 열리는 시각인지, 다음에 닫히는 기록(지금 닫힌 기록 수 + 1)의 마감 + 24시간보다 뒤인지.
- 서버는 다음 회차 기록을 닫을 때 예약을 기록의 `scheduleChanges`에 싣고 지운다. 그사이 늦어져 24시간 규칙에 맞지 않으면 싣지 않고 지운 뒤 기록을 남긴다(다시 예약해야 한다).
- 절차는 `deploy/stardraw/README.md`.

### 11-7. 봉인 시각 증명과 앵커(2026-10-30)

**공개 시각 인증 기관(RFC 3161 TSA) 여러 곳**(사용자 결정: Rekor 대신. Rekor 공개 인스턴스는 공급망 서명용 공공 서비스라 이 쓰임이 애매하고, 시험용 로그는 보장이 없다)
- 서버(`TsaRootLog`): 마감 직후 `SHA-256(봉인 값)`을 담은 TimeStampReq(인증서 함께, nonce 없음)를 기관들에 동시에 보낸다(10초 제한). 받은 토큰은 검사기와 같은 규칙(`verifyTimestampToken`)으로 먼저 확인해 맞는 것만 싣는다. 서로 다른 기관 `STARDRAW_TSA_MIN`곳 이상이면 봉인 성공, 모자라면 다음 진행 때 모두에게 다시 묻는다. 마감 + 3분까지 모자라면 무효 회차.
- 기본 기관: **DigiCert**(`http://timestamp.digicert.com`), **Sectigo**(`http://timestamp.sectigo.com`). 둘 다 2026-10-30 실제로 SHA-256 요청에 응답(Granted)하는 것을 확인했다. FreeTSA(`https://freetsa.org/tsr`)도 응답하지만 개인 운영이라 검사기 목록에만 두고 서버 기본에서는 뺐다.
- **최소 기관 수 기본 1**: 기관 한 곳이 멈추거나 느려도 회차가 무효가 되지 않게 하는 쪽(가용성)을 골랐다. 서버는 늘 두 곳에 묻고 받은 것을 모두 싣기 때문에, 평소에는 두 기관 토큰이 함께 남아 두 기관이 함께 거짓말하지 않는 한 시각을 바꿀 수 없다. 커피 규모에서 한 기관과 운영자가 짜는 위험은 감수한다. 더 엄격히 하려면 `STARDRAW_TSA_MIN=2`(검사기 규칙의 기본은 1이라 화면 판정은 그대로다).
- 장부 형식(`seals/N.json`의 `log`): `{ kind: "tsa", tokens: [{ tsa, genTime, token }] }`. `token`은 ContentInfo DER의 표준 base64, `genTime`은 토큰 안 시각(초, 소수점 아래 버림)을 사람이 읽기 쉽게 함께 적은 것이다. `rootLoggedAt` = 가장 이른 `genTime`.
- 검사(`packages/stardraw-core/src/tsa.ts`, 브라우저에서도 WebCrypto): 토큰마다 ① messageImprint가 SHA-256이고 값이 `SHA-256(봉인 값)` ② 서명된 속성의 messageDigest·contentType ③ 서명(RSA PKCS#1 v1.5 SHA-256/384/512, ECDSA P-256/384/521) ④ 서명 인증서에서 올라가며 서명을 확인해 고정한 공개 열쇠(인증서 SPKI DER의 SHA-256)에 닿는지 ⑤ 그 아래 인증서가 `genTime`에 유효한지 ⑥ 서명 인증서가 시각 인증용(EKU timeStamping)인지 ⑦ 적어 둔 `genTime`이 토큰과 같은지. 실린 토큰은 모두 맞아야 하고 서로 다른 기관 `DEFAULT_TSA_MIN`(1)곳 이상, 가장 이른 시각이 기록의 `rootLoggedAt`과 같아야 한다. drand 시각과의 앞뒤는 무효 회차 규칙(`isVoidRound`)이 본다.
- 고정한 열쇠(루트 SPKI SHA-256): DigiCert Trusted Root G4 `59df317bfa9f4f0ab7ca514d7772296aa2c765b87664d08b96e57399e364729c`, Sectigo Public Time Stamping Root R46 `a4db8668c6796ebf476ddc5ace453a9260dbd4dbb09f51ecec9a839003824795`, FreeTSA Root CA `52c54ba340885605314daa1857c8763b94087d05c636092938d4e2d1818e99b5`. 기관이 루트를 바꾸면 core에 새 열쇠를 더한다(옛 열쇠는 지난 회차 검사를 위해 남긴다).
- 묶음 크기 때문에 pkijs/asn1js를 들이지 않고 필요한 만큼의 DER 읽기를 직접 썼다(`der.ts`). 시험은 세 기관에서 실제로 받아 둔 토큰(`tsa.fixtures.ts`)으로 네트워크 없이 돌고, 회차 봉인 값을 담은 토큰은 시험용 가짜 기관(`@mighty/stardraw-core/testing`의 `FakeTsa`)이 만든다.
- Rekor(`rekor.ts`, `RekorRootLog`)는 꺼 둔 선택지로 남긴다: `STARDRAW_TSA=off`이고 `STARDRAW_REKOR_URL`이 있을 때만 쓴다(시험 운영은 rekor.sigstage.dev만, 정식은 rekor.sigstore.dev만). 2026-10-30 시험용 로그에 실제로 한 번 올려(uuid `71d46696…0e3`, integratedTime 1793324413) 검사기가 맞는 것을 확인했다.

**GitHub 앵커**(사용자 승인, 저장소 `ybbarng/stardraw-ledger` 공개)
- 회차가 닫힐 때마다 파일 하나를 Contents API로 커밋한다: `ledgers/{장부 id}/{회차 6자리}.txt`. 장부 id는 genesis 해시 앞 16자리라 시험 장부를 새로 시작해도 섞이지 않는다.

- 브랜치는 회차의 단계로 정한다: 시험 단계 `trial`, 정식 단계 `main`(`anchorBranch`). 처음 일정표 파일 `genesis.txt`는 늘 `main`(11-6 "다시 시작 막기").

- 검사기(`githubAnchorVerifier`, `verifyLedger`의 `anchorVerifier`): raw.githubusercontent.com에서 회차 파일을 읽어 기록 해시가 같은지 본다. 파일이 없으면 건너뜀.

### 11-8. 화면 코드를 덜 믿게: 터미널 검사기, 재현 빌드, 화면 코드 해시(2026-10-30)

"막지 못하는 것" 가운데 "화면 코드는 운영자가 내준다"(8-1 O5)를 줄인다. 화면 코드를 바꿔 패스키로 몰래 서명하게 하는 일 자체는 여전히 막지 못하지만, 사이트가 내준 코드가 공개 저장소의 어느 커밋인지 누구나 비교할 수 있고, 장부 검사는 화면 없이 할 수 있다.

**터미널 검사기 `stardraw-verify`**(`packages/stardraw-cli`)
- 계산은 core의 `checkPublicLedger` 하나로 검증 페이지와 같다(`verifyLedger`, quicknet BLS, TSA `verifyTsaProof`, 앵커 `githubAnchorVerifier`·`githubGenesisVerifier`). 페이지에 있던 공개 장부 검사 코드를 core로 옮겼다.
- 앵커는 서버를 거치지 않고 raw.githubusercontent.com에서 `ybbarng/stardraw-ledger`를 직접 읽는다(처음 일정표 main, 시험 회차 trial, 정식 회차 main).
- 명령
  - `stardraw-verify [서버 주소]`(기본 `https://game.byb.kr/stardraw-api`): 회차별 한 줄(보이는 회차, 마감, 응모 수, 당첨 번호 또는 무효, 그 회차의 문제·건너뜀)과 항목별 통과·실패·건너뜀. `--pow-sample n`, `--pow-all`, `--anchor-repo`, `--no-anchor`, `--json`.
  - `--ticket <회차-일련번호>`(여러 번): 영수증 앞 12자리나 공유 주소를 그대로 받는다. 장부에서 찾아 머클 증명, 등수, 작업 증명(전부)을 본다.
  - `stardraw-verify site [사이트]`(기본 `https://game.byb.kr`): 아래 해시 목록과 사이트 파일, `--build <out>`이면 직접 빌드한 파일을 비교한다. 기본 범위는 하늘의 별 따기 페이지(HTML·화면 전환용 .txt), 모든 화면 코드(`_next/`), 서비스 워커. `--all`은 목록 전부(그림 포함).
  - 끝 상태: 0 통과(건너뜀 포함), 1 어긋남, 2 사용법·네트워크 오류.
- 실행: 저장소를 받아 `pnpm install` 뒤 맨 위 폴더에서 `pnpm stardraw-verify [인자]`(묶고 바로 돈다). 묶은 파일 `dist/stardraw-verify.mjs` 하나만 있으면 Node 24로 저장소 없이도 돈다.
- 시험은 2026-10-30 시험 서버에서 받아 둔 실제 장부·앵커 파일(`src/fixtures/`)로 네트워크 없이 돈다. 진짜 drand 서명과 DigiCert·Sectigo 토큰이라 실제 검사 경로 그대로다.
- npm 발행은 준비만 했다(바깥 발행이라 사용자 확인 뒤): `package.json`에 `bin`·`files`·`engines`를 두었다. 발행하려면 이름을 정하고(예: `stardraw-verify`, `@mighty/*`는 npm에 없는 범위), `private`을 빼고, `pnpm -C packages/stardraw-cli build` 뒤 `npm publish --provenance`(GitHub Actions에서 하면 어느 커밋에서 묶었는지 npm에 남는다). core가 작업 공간 패키지라 묶은 파일만 올린다.

**재현 빌드**
- 흔들리던 것은 Next 빌드 id 하나였다(빌드마다 무작위, HTML·화면 전환 파일·`_next/static/<id>/`에 들어간다). `next.config.ts`의 `generateBuildId`를 빌드한 커밋으로 바꿨다(`SOURCE_COMMIT`, 없으면 `git rev-parse HEAD`). 커밋이 바뀌면 `_next/static/<id>/` 주소도 바뀌어 오래 두는 캐시와 섞이지 않는다.
- 확인: 같은 폴더에서 두 번(캐시 지우고), 다른 경로(worktree)에서 한 번 빌드해 `out/` 전체가 같았다. 배포된 사이트(Linux Docker 빌드, c8ea466)를 이 맥에서 같은 빌드 id로 다시 빌드하니 295개 가운데 293개가 같았고, 다른 둘은 공유 미리보기 그림(`opengraph-image/share.png`, `gostop/opengraph-image/share.png`)이었다. 그림 그리기가 운영체제에 따라 조금 다른 것으로 보고, 코드가 아니어서 검사기 기본 범위에서는 뺀다(하늘의 별 따기 공유 그림은 같았다).
- 같은 파일을 얻는 조건: 같은 커밋, 같은 빌드 변수(`NEXT_PUBLIC_*`, 해시 목록 `env`에 적힌다), 깨끗한 작업 트리(`apps/web/public/cards-local/`처럼 저장소에 없는 파일이 있으면 그만큼 더 생긴다), lockfile대로 설치. Node 판은 목록에 참고로 적는다.

**화면 코드 해시 목록**
- 빌드 끝에 `apps/web/scripts/build-hashes.mjs`가 `out/`의 모든 파일 SHA-256을 `out/build-hashes.json`에 적는다: `commit`, `dirty`, `env`, `node`, `files`(경로 → 해시, 바이트 순), `digest`(files를 sha256sum 형식 `"<hex>  <경로>\n"`으로 적은 글의 SHA-256). 우리 도구 없이도 `out/` 안에서 `jq -r '.files|to_entries[]|"\(.value)  \(.key)"' build-hashes.json | sha256sum -c`로 확인할 수 있다.
- 어디에 두나(되돌리기 쉬운 쪽부터)
  1. **사이트 `/build-hashes.json`**(켬): 빌드 결과에 들어가 배포와 함께 바뀐다. 사이트가 "지금 어느 커밋을 내주는지" 밝히는 곳이고, 검사기가 여기서 시작한다. 운영자가 내주는 파일이라 그 자체로는 증거가 아니다. 직접 빌드한 해시와 맞아야 의미가 있다.
  2. **Image 워크플로 기록**(켬): Docker 빌드에서 같은 파일을 꺼내(`hashes` 단계) 실행 요약에 digest를 적고 기록 파일(90일)로 남긴다. 이 저장소 안의 일이라 새로 바깥에 공개하는 것이 아니다.
  3. **재현 확인 작업 `reproduce`**(켬): 배포마다 Docker 밖(러너의 Node + pnpm)에서 같은 커밋·같은 빌드 변수로 다시 빌드해 이미지의 목록과 `--all`로 비교한다. 배포는 막지 않고 어긋나면 이 작업만 실패로 남는다.
  4. **GitHub 릴리스 `site-<커밋 앞 12자리>`**(준비만, 꺼 둠): `publish-hashes` 작업이 목록을 릴리스 파일로 올린다. 사이트 밖에 배포 기록이 남아, 운영자가 잠깐 다른 코드를 내줬다가 되돌리는 것을 나중에도 비교할 수 있다. 저장소 변수 `STARDRAW_PUBLISH_HASHES=true`로 켠다. 릴리스는 지우면 그만이라 되돌리기 쉽다.
  - 버린 안: 앵커 저장소(`ybbarng/stardraw-ledger`)에 남기기. 장부 기록과 섞이고, Actions에 다른 저장소 쓰기 토큰을 새로 넣어야 한다.
- 확인하는 순서: ① `stardraw-verify site`로 사이트 파일이 목록과 같은지 ② 목록의 커밋을 받아 같은 빌드 변수로 `pnpm --filter @mighty/web build` ③ `stardraw-verify site --build apps/web/out`. ①②③이 맞으면 사이트가 내준 하늘의 별 따기 화면 코드는 공개 저장소의 그 커밋에서 나온 것이다.

**아직 남는 한계**
- 내 브라우저가 받은 파일이 검사기가 받은 파일과 같다는 보장은 없다. 운영자가 사람마다·때마다 다른 파일을 내주면 검사기로는 그때 받은 것만 비교된다. 서비스 워커가 저장해 둔 옛 파일을 쓰는 동안에도 마찬가지다.
- 패스키 서명은 여전히 브라우저 화면 코드가 시킨다. 큰 상품이면 응모·증명을 터미널로 하는 길이 필요하다(터미널 응모·`claim` 명령은 아직 없다).
- 검사기도 이 저장소 코드다. 가장 독립적인 것은 4절 규칙대로 직접 짠 검사기다.


### 11-9. 우주인 등록과 우주인 등록증, 카노푸스 우주국(2026-10-30)

사용자 아이디어. 입구 문구 "하늘의 별 따기는 등록한 우주인만 응모할 수 있습니다". 패스키 만들기 단계를 **우주인 등록**이라 부르고(등록 = 패스키 만들기), 등록 직후 **우주인 등록증**을 발급해 보여 준다. 장부·기록 형식은 바꾸지 않았다(시험 운영 중인 장부를 이어 가므로). 등록증은 이미 공개된 정보(공개 열쇠, 등록 회차)에서 화면이 계산한다.

**말 고르기**
- 게임 흐름에서는 패스키 대신 우주인 말을 쓴다: 「우주인 등록」, 「이미 우주인 등록증이 있어요」, 「등록증으로 승인」, 영수증 "서명: 우주인 등록증". "패스키"는 등록 단계의 한 줄("우주인 등록증은 이 기기의 패스키로 만들어집니다 · 자세히")과 카드 구석의 패스키 마크에만 남긴다(운영체제 창에는 "패스키"라고 나오고, 패스키 홍보도 목적이다). 기술 설명은 /stardraw/about 패스키 문답과 /stardraw/learn으로 보낸다.
- 패스키 마크는 직접 그렸다(열쇠 머리에 지문 물결). FIDO Alliance 패스키 아이콘은 상표 사용 계약 조건이 분명하지 않아 쓰지 않았다.

**등록증 계산**(`apps/web/src/stardraw/astronaut/identity.ts`, 모두 공개 열쇠에서 결정적)
- 씨앗 s = taggedHash("stardraw/astronaut/v2", 공개 열쇠 65바이트). 같은 공개 열쇠면 어느 기기에서든 같은 등록증이고, 「이미 우주인 등록증이 있어요」로 들어와도 같다. (v1은 "해시 % 목록 길이"로 골라 목록에 하나만 더해도 거의 모두의 주소가 바뀌었다. 실제 응모자가 없을 때 v2로 바꿔 아무도 이사하지 않았다, 2026-10-30.)
- **등록번호** `SD-XXXX-XXXX`: s 앞 40비트를 Crockford base32 8자로. 사람이 눈으로 가르는 값이다.
- **이름**: 별·하늘 느낌의 3음절 이름 117개에서 고른다(`names.ts`). 앞말·끝말을 곱하면 "가람람"처럼 어색한 이름이 섞여 손으로 고른 목록으로 두었다. 동명이인처럼 겹칠 수 있고 등록번호로 가른다(사용자). 이름이 곧 id라 이미 있는 이름의 글자는 고치지 않는다.
- **주소**: 실제 천체의 실제 위계(`places.ts`). **주소의 끝은 늘 천체다**(행성·위성·왜소행성·소행성·혜성·외계 행성·다른 은하와 그 안의 천체). 충돌구·바다 같은 천체 위 지명은 두지 않는다(2026-10-30 사용자, 40곳을 뺐다). **지구만 대륙까지**: 지구가 나오면 아시아·유럽·아프리카·북아메리카·남아메리카·오세아니아·남극 가운데 하나를 한 번 더 고른다. 나라는 민감해서 쓰지 않는다. 앞부분은 우리 우주 › 라니아케아 초은하단 › 처녀자리 초은하단 › 국부은하군 › 우리 은하 › 오리온 팔. 우리 은하는 처녀자리 은하단이 아니라 국부은하군에 속해 그 경로에 "처녀자리 은하단"을 넣지 않았다. 고르는 곳은 오리온 팔 안 290곳과 다른 은하 21곳: 태양계 93곳(태양·행성·위성·왜소행성·소행성·혜성), 확인된 외계 행성 197곳(NASA Exoplanet Archive 확인 행성 표로 맞춤, 1,000광년 이하, 1,000~3,000광년은 오리온 팔을 따라 보는 케플러 탐사 영역만), 다른 은하 21곳(국부은하군·처녀자리 은하단·M81 은하군의 실제 천체). 지구 대륙 일곱 곳까지 치면 나올 수 있는 주소는 317가지다. 후보·논쟁 중인 행성(포말하우트 b, 프록시마 c 등)은 뺐다. 카드에는 우리 은하부터(다른 은하는 끝 세 단계) 보이고 누르면 전체와 거리.
- **사진**: 외계인 얼굴 SVG(피부 8 × 머리 5 × 눈 6 × 더듬이 5 × 입 6 × 무늬 4 × 헬멧 유무). 부위마다 그림 번호가 id다. **드문 사진**은 65536분의 32 = **1/2048**(셋이라 하나하나는 약 1/6144): 우주견, 작은 별의 아이와 장미(오마주), 절구 찧는 달토끼. 카드에 "★ 드문 사진".
- **확률**: 다른 은하는 따로 굴리는 주사위(65536분의 128 = **1/512**)라 목록 크기가 바뀌어도 흔들리지 않는다. 다른 은하 한 곳은 약 1/10,752. 나머지(511/512)는 오리온 팔 290곳에서 고르게 골라 한 곳이 약 1/291이다. 그래서 지구는 약 1/291, 지구의 대륙 하나(예: 지구 남극)는 약 1/2,034. 이름 하나는 1/117.
- **고르는 법: 랑데부 해싱**(`rendezvous`). 이름·주소·지구 대륙·드문 사진 종류·얼굴 부위 모두 같다. 항목마다 바뀌지 않는 고유 id(`earth`, `earth/antarctica`, `jupiter/europa`, `trappist-1e` 등)를 두고, u = sha256(s ‖ 종류 ‖ 0 ‖ id)에서 만든 (0,1) 값으로 점수 = -가중치 / ln(u)를 매겨 가장 높은 항목을 고른다(가중 HRW, 지금 가중치는 모두 1). 한 명 계산은 해시 약 450번, 0.3ms쯤이다. 목록을 고칠 때 규칙:
  - **목록에 더해도 기존 우주인은 그대로다.** 새 항목이 이긴 사람(약 1/(n+1))만 그리로 옮긴다. 주소 290곳에 하나를 더한 시험에서 5,000명 가운데 11명(0.22%, 기댓값 0.34%)만 새 곳으로 옮기고 다른 곳으로 옮긴 사람은 없었다. 이름 117개에 하나를 더하면 43명(0.86%, 기댓값 0.85%).
  - **빼면 그곳 주민만 옮겨 간다.** 나머지는 그대로다.
  - **id는 한 번 정하면 바꾸지 않는다.** 같은 id를 다른 곳에 다시 쓰지도 않는다. id를 바꾸면 그곳 주민이 모두 흩어진다.
  - **화면 이름은 고쳐도 된다.** 목록 차례를 바꿔도 된다. 아무도 옮기지 않는다.
- **등록일**: 장부의 등록 회차(첫 응모 회차, 서버 `GET /api/keys/:pub`가 `{ registered, round }`로 돌려준다. 닫힌 회차는 공개 장부 파일의 등록 목록에도 있다)의 마감 날짜. 응모 전이면 "첫 응모 때 기록". 열쇠 등록은 지금처럼 첫 응모와 함께 장부에 오른다.
- **문장**: 카드는 실제 신분증처럼 칸(성명·등록번호·주소·등록일)을 나눈다. "OOO에 거주하는 OOO"는 등록 직후 인사와 공유 문구에만, 주소의 끝 이름 하나로 쓴다(예: "트라피스트-1 e에 거주하는 노을별 님, 우주인으로 등록되었습니다"). 지구 대륙이면 대륙만으로는 어색해 천체 이름을 앞에 붙인다("지구 남극에 거주하는 별나래 님"). 내 응모 머리에는 이름만.
- **발급 기관**: **카노푸스 우주국장**(지어낸 기관). 직인은 용골자리 별과 선으로 이룬 붉은 네모 인장. 하늘의 별 따기는 카노푸스 우주국이 정해진 시각마다 여는 추첨이라는 설정이고, 설정을 쓰는 곳은 등록증, 영수증 아래 "발행 · 카노푸스 우주국", 추첨 화면의 "카노푸스 우주국 정시 추첨", 설명 페이지 첫머리 한 줄과 고른 이유(서울에서는 지평선 위로 오르지 않는 두 번째로 밝은 별, 노인성, 매리너 4호·보이저의 기준 별)뿐이다. 우주국장은 운영자지만 평범한 우주인이다(특별한 등록증·배지·권한 없음).
- **3D 카드**: 마우스를 올리거나 가로로 끌면 좌우로 기울고 홀로그램 빛이 지난다. 움직임 줄이기면 기울지 않는다. 휴대폰 기울기 센서는 쓰지 않는다(iOS 권한 창).

**본인 확인(모바일 신분증 검사처럼)**(`owner-check.ts`)
- 카드를 누르면 그 자리에서 만든 문제 값(태그 ‖ 공개 열쇠 ‖ 무작위 32바이트 ‖ 시각)에 패스키로 서명하고(내 등록증이면 그 패스키 번호를 지정), 기기 안에서 `verifyEntrantSignature`로 등록증의 공개 열쇠와 맞는지 본다. 서버에 묻지 않는다. 통과하면 "이 기기에서 확인됨"과 지금 시각이 초 단위로 흐르고 홀로그램이 움직인다(캡처와 구분). 30초 뒤 원래대로. 실패·취소면 조용히 "확인하지 못했습니다". 데모는 흉내 시트("패스키로 본인 확인할까요?").
- **범위**: 내 패스키가 이 카드 열쇠와 맞는다는 것을 **나에게** 보여 주는 체험이다. 남에게 보여 주는 증명이 아니다(가짜 페이지도 같은 표시와 흐르는 시계를 흉내 낼 수 있다). 남에게 당첨을 증명할 때는 당첨자 확인(별 세 개)을 쓴다. 이 구분을 카드 아래 한 줄, 설명 페이지 문답, 배우기 "막지 못하는 것"에 적었다.

**판정은 공개 열쇠 전체와 서명으로만**
- 이름·주소·사진은 재미로 붙인 것이다. 열쇠 파일로 열쇠를 많이 만들면 이름·주소·사진이 같은 등록증은 쉽게 나오고, 40비트 등록번호도 약 1조(2^40) 번이면 맞출 수 있다. 그래서 응모·당첨자 확인 판정은 언제나 공개 열쇠 전체와 서명으로 하고, 등록번호로 무언가를 판정하는 코드는 두지 않는다.
- **효력은 서명에서 나온다**: 진짜 "우주국 관인"은 서버 서명 열쇠의 서명이다(영수증 등). 등록증의 붉은 직인은 꾸밈이다. 앞으로 우주국이 직접 보내는 것(공지, 정식 시작 예고 등)은 서버 서명 열쇠로 서명하고, 화면이 장부 genesis의 서버 공개 열쇠로 확인했을 때만 관인 표시를 붙인다. 지금 있는 것 가운데 그런 것은 없고, **당첨자 확인 요청에는 관인이 붙지 않는다**(우주국은 전달만 한다). 당첨 안내는 서버가 보내지 않고 기기가 장부로 계산한다.

**남의 등록증은 그리지 않는다**
- 등록증은 공개 열쇠에서 누구나 계산할 수 있다(공개 가명의 성질, 이더리움 주소 아이콘처럼). 이 방식은 유지한다. 대신 **우리 화면은 남의 등록증(얼굴·이름·주소)을 그려 주지 않는다**: 지난 회차, 당첨자 목록, 검증 페이지, 당첨자 확인 화면 어디에도 띄우지 않고, 이 기기의 내 등록증만 보인다(데모는 가짜 우주인). 기존 "응모자 신원 표시 없음" 결정을 등록증에도 적용한 것이다. 그래서 공유도 공개 열쇠 주소 대신 인사 문구와 첫 화면 주소만 보낸다.
- 버린 안: WebAuthn PRF 확장으로 기기만 아는 값에서 등록증을 만들어 예측을 막기. 지원이 브라우저·인증기마다 고르지 않고, 공개 열쇠를 그대로 보여 주는 의도와 부딪힌다.

**개인정보**
- 등록증 아래 한 줄: "공개 열쇠는 원래 공개하는 값이라 보여 줘도 안전합니다. 다만 등록증을 보여 주면 장부 속 응모가 내 것인 줄 알 수 있습니다."
- 공개 열쇠는 가명이다. 가명도 사람과 이어지면 개인정보가 된다. 우리는 장부 밖에서 가명을 사람과 잇는 정보(이름·이메일·전화번호)를 받지 않는다. 응모 제한용 IP는 앞부분(IPv4 /24, IPv6 /48)만 메모리에서 센다. 장부는 고칠 수 없어 지울 수 없다는 한계가 있다. 이어지지 않게 하려면 새 우주인으로 다시 등록하면 그때부터 이어지지 않는다. 설명 페이지 "우리가 저장하는 것"(/stardraw/about#privacy)에 쉬운 말로 적었다.

**당첨자 확인 승인과 장난 요청**
- 당첨자 기기: "보낸 확인 링크로 n회 k등 당첨 확인 요청이 왔습니다", 작게 "○시에 만든 링크 · 전달: 카노푸스 우주국". 우주국은 배달한 곳으로만 적고 요청 주체처럼 쓰지 않는다. 「등록증으로 승인」을 누르면 내 등록증 카드가 나타나 확인을 받고(본인 확인과 같은 움직임), 별 세 개가 빛난다. "별 세 개는 내가 당첨을 알린 그 사람에게만 보내세요" 한 줄과 "우주국은 전달만 하고 별 세 개는 모릅니다"(임시 ECDH).
- 2026-10-30 확인 링크로 다시 설계(11-2): 요청은 당첨자가 만든 링크로만 붙어 요청 폭탄·칸 채우기가 없다(8-1 P7). 이름 칸과 이름 사칭 검사(core `requesterProblem`, "우주국·국장·카노푸스·운영")는 이름 칸과 함께 없앴다(P8). 상한: IP 앞부분마다 하루 링크 만들기 30번(`STARDRAW_INVITES_PER_PREFIX`, 옛 `STARDRAW_CONFIRMS_PER_PREFIX`는 없앴다), 없는 링크 조회 60번, 응모권당 열린 링크 10개. 링크를 받은 사람이 다른 확인자에게 별을 넘겨 당첨자인 척하는 것은 "별 세 개는 알린 그 사람에게만" 한 줄로 막는다. 판정(서명·별 세 개)은 그대로다.

**나중에(아이디어, 만들지 않음)**: 우주국 창구·관인 공지·명예의 전당. 행사·상품이 생기면 본다(map.json next-lotto의 아이디어).

### 11-10. 본인 확인 표시, IP 상한, 터미널 도구의 범위(2026-10-30)

시험 서버가 돌고 있지만 응모가 0장일 때 정했다. 그래서 응모 검사 규칙을 바꿔도 지난 기록이 걸리지 않는다(장부는 다시 시작하지 않았다).

**패스키 서명마다 UV 표시를 요구한다**
- 규칙: 패스키 서명의 authenticatorData flags에 UP(0x01)와 UV(0x04)가 모두 켜져야 한다(core `checkAuthenticatorData`, `FLAG_UP`·`FLAG_UV`). 다른 비트(BE·BS·AT·ED)는 보지 않는다. 응모권, 별명, 당첨자 확인 승인, 확인 링크 만들기 등 `verifyEntrantSignature`를 거치는 모든 서명에 같이 걸리고, 서버·검증 페이지·터미널 검사기(`verifyLedger`·`checkPublicLedger`)가 같은 코드라 규칙도 같다. 시험 값에 "패스키 authenticatorData" 묶음을 더했다.
- 이유: 화면은 늘 `userVerification: "required"`로 부르는데 검사는 UP만 봐서, 장부만 보고는 본인 확인을 거쳤는지 알 수 없었다. 이제 진짜 패스키로 낸 응모는 매번 지문·얼굴·PIN을 거쳤다고 장부가 보장한다.
- 한계: 개발자용 가상 인증기(브라우저 개발 도구, 소프트웨어 인증기)는 UV 표시도 꾸밀 수 있다. 그래서 이 규칙은 자동화를 막지 못한다. 진짜 인증기로 낸 서명의 뜻을 분명히 할 뿐이다.
- 등록에는 서명이 없어 장부가 UV를 볼 수 없다. 첫 응모권 서명이 UV를 요구하므로 UV 없이 만든 패스키는 응모할 수 없다. 화면은 만들 때 받은 authenticatorData에 UV가 없으면 미리 막는다(`hasUserVerification`).
- 시험용 가짜 인증기(core `testing.ts` `fakePasskey`, 기본 0x05)와 배우기의 흉내 패스키(`lab.ts` `demoAssertion`)는 UP·UV를 함께 켠다. 배우기 패스키 흉내에서 "지문·얼굴·PIN 없이 서명"을 고르면 UP만 켜져 검사기가 거절한다. 데모 지갑은 원시 서명이라 flags가 없다.
- 원시 열쇠(kind 1)는 규칙에 남아 있다(연습 장부·데모·시험). 서버도 원시 열쇠 등록·서명을 받으므로, 스스로 프로그램을 짜는 사람은 UV 없이도 원시 열쇠로 응모할 수 있다. 가상 인증기와 마찬가지로 작업 증명 비용만 든다.
