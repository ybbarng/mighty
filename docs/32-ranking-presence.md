# 32. 공유 랭킹과 접속·인기 현황 (2026-10-29, 장기 계획)

사용자 요청(2026-10-29): "공유하는 랭킹 시스템 같은 것을 만들어볼까 싶기도 하거든. 아니면 다른 사람들은 현재 몇 명이 어느 게임을 하고 있는지 같은 것도 있으면 좋을 것 같고. 현재 인기 있는 게임이 무엇인지 알 수도 있으니까."
덧붙인 요청: "여기서도 중요한 건 어뷰징 및 해킹 방지야."

**당장 만들지 않는다.** 나중에 만들 때 방향이 어긋나지 않게, 또 지금 다른 기능을 만들면서 이 두 기능의 길을 막지 않게 하려고 쓴다. [18](./18-game-center-plan.md)과 같은 성격의 문서다.

두 기능:

1. **공유 랭킹**: 게임별 순위와 점수(레이팅)
2. **접속·인기 현황**: 지금 몇 명이 어느 게임을 하는지, 요즘 인기 있는 게임

## 사용자와 정한 것 (2026-10-29)

**랭킹은 보류한다.** 사용자: "나중에 정말 만들고 싶어질 때 다시 생각해보자. 컴퓨터가 들어가 있는 게임을 랭킹에 넣는 게 애매하긴 해서, 많이들 사용할 때야 의미가 있는 것 같아." 사람끼리 하는 판이 많아질 때 다시 연다. 아래 4절 이후의 랭킹 설계는 그때의 출발점이다.

이야기하며 정리한 것(다시 열 때 이것부터 본다):

- **결과를 믿는 방식(G1)은 ② "참가자 서명을 믿는다"를 기본으로 기운다.** 서버가 모든 판을 다시 돌리면(①) 부하가 생긴다. 다만 서명만으로 막지 못하는 두 경우에만 서버가 그 판을 다시 돌리는 섞은 방식을 추천했다(아직 정하지 않음).
  - 끝 서명이 빠진 판(지고 결과를 보지 않고 나가 버리기): 남은 사람이 판 기록을 내면 그 판만 다시 돌려 정한다. 가벼운 대안은 "끝나지 않은 판"으로 두고 끝까지 안 한 비율을 보이며 높으면 랭킹 판을 잠시 막는 것.
  - 무작위 표본 몇 %: 지어낸 기록은 다시 돌리면 맞지 않으니 위조를 꺼리게 한다.
- **랭킹 서버는 ①·② 모두 따로 하나 있다.** 순위를 모아 보여 줄 곳이 필요하다. ②의 서버는 서명 확인과 점수 계산만 한다.
- **"랭킹 판"은 따로 도는 게임이나 새 방 종류가 아니다.** 지금 온라인 방에 "랭킹에 넣는다" 표시 하나다. 사람만 있는 온라인 판을 기본으로 넣으면 표시도 거의 보이지 않는다. 컴퓨터가 앉은 판은 넣지 않는다(G6).
- **②에서 서명으로 막는 것**: 결과 위조(참가자마다 기기 열쇠로 결과 + 판 기록 지문에 서명), 같은 결과 두 번 보내기(판 고유 번호), 남의 행세. 판을 시작할 때 모두 서명한 "시작표"를 먼저 내 판이 있었다는 것을 남긴다.
- **서명으로 못 막는 것(짜고 치기·져 주기·여러 계정·봇)은 영향을 줄인다**: 친구 리그부터, 같은 상대 반복 판의 반영 줄이기, 새 계정 임시 등급, IP 앞부분당 하루 판 수 한도, 표본 검사. 봇은 어떤 구조로도 못 막고 판 뒤 통계로 찾는 정도다.

접속·인기 현황(정함):

- **G10 혼자 하기도 센다.** 1분마다 게임 이름과 무작위 번호만 보내고, 끄기 스위치를 두고 GPC를 존중한다.
- **G11 1분마다 모은 값(캐시 파일) 방식에 "실시간 느낌"을 더한다.**
  - 들어오면 첫 알림으로 바로 센다.
  - 떠날 때 `sendBeacon`으로 "나감"을 보내 바로 뺀다. 한마디를 못 보낸 경우(배터리·망 끊김)만 마지막 알림 뒤 75초에 뺀다.
  - 서버는 숫자가 바뀔 때 `presence.json`을 다시 쓰되 5초에 한 번까지만 쓴다.
  - 화면은 보고 있을 때만 10~15초마다 ETag로 확인한다(바뀌지 않았으면 304). 다른 앱으로 가 있으면 확인하지 않는다.
  - 내가 들어온 순간 내 몫을 화면 숫자에 먼저 더하고, 숫자가 바뀔 때 부드럽게 굴린다.
  - 그래서 숫자는 늦어도 10~20초 안에 바뀌고, 읽기는 nginx 캐시 파일만 닿아 튼튼함은 그대로다. SSE는 쓰지 않는다.
- **G12 인기 게임은 보류.** 사용자: 인기는 "사람 수"가 되어야 한다. 다만 사람을 세려면 같은 사람을 알아봐야 해서 개인정보와 맞바꾸는 지점이 생겨, 사람이 많이 쓸 때 다시 본다. 그때의 출발점:
  - 기기마다 오래 가는 무작위 번호: "7일 동안 몇 명"을 정확히 세지만 한 기기를 7일 동안 잇는 값이 서버에 생긴다(추적에 가깝다).
  - 날마다 바뀌는 무작위 번호(추천했던 것): 그날 안에서만 같은 사람을 알아보고 "최근 7일 하루 평균 사람 수"로 센다. 날짜를 넘어 잇는 값이 없고, 서버는 날마다 더한 숫자만 남긴다. 같은 수면 논 시간으로 가린다.
  - 어느 쪽이든 사람이 아니라 기기를 세고, 번호를 새로 만들어 부풀릴 수 있어 IP 앞부분당 하루 몇 명까지만 센다.
  - umami를 붙이면(docs/33) 주인이 보는 인기 통계는 그쪽으로 먼저 볼 수 있다.
- **G13 0명이면 감추고, 1명부터 보인다.** 사용자: "0명일 때는 보이지 않는 게 낫고, 1명부터는 보여도 된다." 숫자 대신 "지금 누군가 하는 중" 점 하나를 켜는 방식도 좋다고 해, 만들 때 화면을 보고 숫자·점 가운데 고른다.

## 0. 한 줄 결론

- **접속·인기 현황은 작게 바로 할 수 있다.** 서버가 1분마다 숫자만 모아 두고, 사람을 가리키는 값은 남기지 않는다. 부풀리기는 "근사값 + IP 앞부분당 상한"으로 막는다. 막지 못해도 잃는 것이 거의 없다.
- **랭킹은 "서버가 게임을 모른다"는 지금 원칙을 처음으로 넘는 일이다.** 서버가 판 기록을 받아 같은 엔진으로 다시 계산해야 믿을 수 있다. 그래도 **혼자 여러 열쇠로 자기와 두기·친구끼리 져 주기·봇으로 두기는 어떤 구조로도 완전히 막지 못한다.** 그래서 처음에는 전체 공개 순위가 아니라 **같이 둔 사람끼리의 순위(친구 리그)**부터 시작하기를 추천한다. 지인끼리 쓰는 사이트라는 목표([18](./18-game-center-plan.md))와도 맞는다.
- 어뷰징·해킹 방지는 3절에 모았다. 항목마다 막는 방법·남는 위험·탐지 방법·포기하는 것을 적었다.

## 3. 어뷰징·해킹 방지 (이 문서의 중심)

[07](./07-security.md)·[12](./12-redteam-2026-10-21.md)와 같은 방식으로 정리한다. 아직 만들지 않은 기능이라 "확인"은 실제 시험이 아니라 **설계 단계의 판단**이다. 만들 때는 12처럼 항목마다 공격을 실제로 해 보는 시험을 먼저 쓰고(시험 실패 = 공격이 통함), 고친 뒤 통과를 본다.

### 3-1. 위협 모델: 누가, 무엇을 노리나

| 공격자 | 할 수 있는 것 | 노리는 것 |
|---|---|---|
| T1. 점수를 올리고 싶은 보통 사용자 | 탭 여러 개, 기기 여러 대, 개발자 도구 | 내 순위 올리기, 지는 판 숨기기 |
| T2. 고친 프로그램을 가진 사람 | **저장소가 공개라 소스를 모두 가진다.** 서버 API를 직접 부를 수 있다 | 결과 위조, 남의 행세, 대량 판 만들기 |
| T3. 짜고 치는 친구 무리 | 여러 사람이 실제로 함께 둔다 | 한 사람 몰아주기, 남 끌어내리기 |
| T4. 방해꾼 | 스크립트, 여러 IP | 숫자 부풀리기, 서버 넘어뜨리기 |
| T5. 남을 캐려는 사람 | 공개된 순위·현황을 지켜보기 | 특정인이 언제 무엇을 하는지 알아내기 |
| T6. 서버 운영자(우리) 또는 서버를 뚫은 사람 | 저장소를 마음대로 고치기 | 순위 조작, 기록 들여다보기 |

지킬 것: ① 순위가 실제 실력을 따라가는 것 ② 내 선수 열쇠 ③ 서버가 계속 도는 것 ④ 사용자의 활동 정보 ⑤ "방장도 서버도 속이지 못한다"는 지금 정체성.

### 3-2. 어디서든 못 막는 것 (먼저 받아들일 것)

- **혼자 여러 신원 만들기.** 계정이 없으면 신원은 공짜다. 계정이 있어도 이메일·전화번호를 더 만들면 된다. 막는 것이 아니라 **비용을 올리고, 새 신원이 순위를 흔들지 못하게** 하는 것이 목표다.
- **봇으로 두기, 옆에 엔진을 띄워 수 묻기.** 규칙에 맞는 수만 보내므로 증명으로 잡을 수 없다([18](./18-game-center-plan.md) "어디서든 못 막는 것", [07](./07-security.md) E). 큰 사이트도 사람이 신고를 받고 통계로 의심을 좁혀 계정을 닫는다(6절 chess.com).
- **게임 밖 짜고 치기**(음성 채팅으로 패 알려 주기, 일부러 지기). 07의 F와 같다.

그래서 랭킹의 공정성 목표는 "**규칙과 운을 속이지 못한다** + **조작이 순위에 주는 영향을 작게** + **이상한 것은 눈에 띄게**"까지로 둔다.

### 3-3. 랭킹 쪽 공격

| 항목 | 공격 | 막는 방법 | 남는 위험 | 탐지 |
|---|---|---|---|---|
| R1 | 여러 열쇠(두 탭·두 기기)로 자기와 두어 한쪽 점수 올리기 | ① 새 열쇠는 **임시 등급**: 판 수와 서로 다른 상대 수가 기준(예: 20판, 상대 5명)을 넘기 전에는 순위표에 없다. ② 임시 등급 상대를 이겨서 얻는 점수는 0이나 아주 작게. ③ 같은 상대와 하루 몇 판을 넘으면 그 뒤 판은 레이팅에 넣지 않는다. ④ 친구 리그는 초대받은 사람만 들어온다 | 임시 열쇠 여럿이 서로 두어 모두 확정 등급이 되면, 그 무리 안에서는 통한다. 다만 무리 밖 확정 선수를 이겨야 순위가 오른다 | 상대 그래프에서 **밖과 거의 두지 않는 닫힌 무리**, 같은 IP 앞부분에서 같은 시간대에 이어지는 판, 판 길이가 아주 짧은 판 |
| R2 | 친구끼리 져 주기·몰아주기 | R1의 ③(같은 쌍 반복 제한). 몇 수 만에 기권한 판은 레이팅에 넣지 않는다(게임별 최소 수). 3인 이상 카드 게임은 "몰아주기"가 순위에 주는 영향을 줄이려고 **판이 아니라 게임(여러 판 묶음) 결과로만** 레이팅을 바꾼다 | 실제로 끝까지 두며 져 주면 구별할 수 없다. 카드 게임 담합은 07 F와 같이 막지 못한다 | 쌍별 승패 치우침(같은 상대에게만 이상하게 많이 짐), 기권 비율 |
| R3 | 방장이 고친 프로그램으로 엔진·섞기를 조작해 이기기 | 지금도 참가자 판 끝 검증이 잡는다([07](./07-security.md), [13](./13-mental-poker.md)). 랭킹에서는 **서버도 같은 기록을 다시 계산**해 통과한 판만 넣는다 | 모든 참가자가 공모하면 R1·R2가 된다 | 서버 재계산 실패 기록(누가 올렸는지) |
| R4 | 판을 두지 않고 서버에 결과만 지어내 보내기 | 서버는 결과가 아니라 **판 기록(규칙·시드 재료·행동 목록)**을 받아 스스로 결과를 계산한다. 결과 칸은 받지 않는다. 참가자 모두가 판 시작 때 서명한 "랭킹 판 시작 약속"(3-5)이 없는 기록은 받지 않는다 | 공모자끼리는 기록을 기계로 빨리 만들어 낼 수 있다(R11) | 행동마다 쓴 시간의 합과 실제 걸린 시간(시작표 발급~제출)이 크게 다름 |
| R5 | 같은 결과를 여러 번 보내기(재전송), 옛 판을 다시 보내기 | 서버가 판 시작 때 **한 번만 쓰는 시작표**(무작위 id + 발급 시각)를 준다. 판 id = 시작표, 한 번 받으면 다시 받지 않는다. 시작표는 몇 시간 안에만 쓸 수 있다 | 없음(서버 저장소가 지켜지는 한) | 같은 시작표로 다시 온 요청 수 |
| R6 | 남의 열쇠로 서명해 남의 행세하기 | 선수 열쇠는 Web Crypto의 **내보낼 수 없는 열쇠**(`extractable: false`)로 만들어 IndexedDB에 둔다. 페이지 스크립트도 열쇠 값을 꺼내지 못하고 서명만 부탁할 수 있다. 서명 문장 맨 앞에 용도 이름(`game-result-v1` 같은)을 넣어 다른 용도의 서명을 옮겨 쓰지 못하게 한다(`welcomeStatement`의 `mighty-welcome-v2`와 같은 방식) | 그 기기에서 우리 페이지에 남의 스크립트가 돌면(XSS, 나쁜 확장 프로그램) 서명을 부탁할 수 있다. 기기를 잃어버리면 그 기기를 가진 사람이 나다 | 한 열쇠가 짧은 시간에 멀리 떨어진 IP 앞부분 여럿에서 쓰임 |
| R6b | 남과 같은(또는 비슷한) 이름으로 행세 | 이름은 겹쳐도 되게 두고, 순위표에 **열쇠 지문에서 만든 짧은 표식**(색·글자 4개)을 함께 보인다 | 사람들이 표식을 보지 않을 수 있다 | 같은 이름, 다른 지문 |
| R7 | 원하지 않는 판 결과를 남 이름으로 올려 끌어내리기 | 시작 약속에 **모든 사람의 서명**이 있어야 판을 받는다. 내가 서명하지 않은 판은 내 기록이 될 수 없다 | 없음 | — |
| R8 | 지는 판을 숨기기: 지기 직전 서명·제출을 하지 않거나 그냥 나가기 | 시작 약속은 판 **시작 때** 받는다. 끝 결과는 서명이 아니라 기록으로 정해지므로, **누구든 한 사람이 기록을 올리면** 서버가 계산해 확정한다. 이긴 사람이 올리면 된다 | 멘탈 포커 게임은 판 끝에 모두가 열쇠를 공개해야 기록이 완성된다. 열쇠 공개를 하지 않고 나가면 R9로 처리 | 시작표를 받고 끝내 기록이 오지 않은 판의 비율(사람별) |
| R9 | 끊기 악용: 질 것 같으면 나가기 | 시작 약속이 있는 판에서 기록이 중간에 끝나면, 남은 사람들이 서명한 "○○ 자리가 나갔다" 진술(지금의 끊긴 사람 끝내기 투표 결과, [13](./13-mental-poker.md) 4절)을 함께 올린다. 서버는 **나간 사람을 진 것으로** 친다. 판 끝에 열쇠를 공개하지 않은 사람도 같다 | 진짜로 망이 끊긴 사람도 진다. lichess도 끊김·지연으로 잃은 점수는 돌려주지 않는다(6절). 남은 사람들이 짜고 멀쩡한 사람을 "나갔다"고 할 수 있다(2인 판은 상대 혼자 진술) → 진술에 기록 끝부분의 차례·시각을 붙이고, 2인 판은 차례가 나간 사람에게 있었고 시간 규칙이 있을 때만 인정 | 사람별 나가기 비율. lichess처럼 자주 나가는 사람은 잠시 랭킹 판을 막는다 |
| R10 | 봇(체스 엔진, 우리 고수 컴퓨터)으로 대신 두기 | 막지 못한다(3-2). 신고 버튼, 의심 판은 운영자가 무효로 할 수 있게 레이팅을 **기록에서 언제든 다시 계산**하는 구조로 둔다 | 남는다 | 판 게임은 엔진과 같은 수 비율, 수마다 쓴 시간이 너무 고르게 짧음. 서버 한 대로 모든 판을 엔진에 돌리기는 무겁다 → 신고된 판만 |
| R11 | 대량 판 만들기로 점수 쌓기(공모자·여러 열쇠가 기계로 빠르게) | 열쇠당·IP 앞부분당 **하루 시작표 수 상한**, 게임별 최소 판 시간(수 × 최소 시간), 레이팅은 판 수가 많아도 잘 오르지 않게(같은 쌍 제한, 임시 상대 제한) | 상한 안에서는 통한다 | 시작표 발급 수, 상한에 닿는 열쇠 |
| R12 | 카드 게임에서 좋은 패가 나오게 시드 고르기 | 사람끼리는 commit-reveal·멘탈 포커가 이미 막는다([07](./07-security.md) B). 시작 약속에 각자의 약속 해시를 넣으면 서버도 나중에 확인할 수 있다 | 공모자끼리는 시드를 고를 수 있다 → R1·R2 | — |
| R13 | 방장이 남의 쓴 시간(`spent`)을 부풀려 시간패를 만들기 | 참가자 기기도 자기 차례 시간을 따로 재 두었다가, 판 끝 검증에서 방장 기록과 크게 다르면 실패로 알린다. 그 알림을 결과에 붙여 올린다. 서버는 **시간패로 끝났고 이의가 붙은 판은 레이팅에 넣지 않는다** | 차이가 작은 조작(몇 초)은 망 지연과 구별되지 않는다 | 사람별 "시간패 이의" 수 |
| R14 | 방장이 컴퓨터 자리를 조종해 한 사람 돕기 | 지금도 참가자가 컴퓨터 수를 다시 계산해 잡는다([12](./12-redteam-2026-10-21.md) A4). 랭킹에서는 **컴퓨터 자리가 있는 판은 넣지 않는다**(처음 단계) | — | — |
| R15 | 일부러 레이팅을 내린 뒤 약한 상대 사냥 | 지인끼리 쓰는 곳이라 영향이 작다. 순위는 "최고점"이 아니라 지금의 보수적 점수(4-4)로 정한다 | 남는다 | 짧은 기간 큰 하락 뒤 큰 상승 |
| R16 | 공개 소스를 보고 서버 API를 직접 부르기 | 정상으로 본다. **서버는 앱을 믿지 않는다**: 모든 값을 다시 확인하고, 계산은 서버가 한다 | — | — |

### 3-4. 접속·인기 현황 쪽 공격

| 항목 | 공격 | 막는 방법 | 남는 위험 | 탐지 |
|---|---|---|---|---|
| P1 | 숫자 부풀리기: 탭 여러 개, 스크립트로 "지금 여기" 알림 대량 보내기 | ① 숫자는 근사값으로 보인다("약 10명"). ② **IP 앞부분 하나가 더하는 사람 수에 상한**(예: 20). 회사 와이파이처럼 한 IP에 여러 사람이 있는 경우를 생각해 1이 아니라 넉넉하게. ③ 알림은 1분에 한 번만 센다(같은 세션 id가 자주 와도 한 번) | IP를 많이 가진 사람(VPN·클라우드)은 상한을 피한다 | IP 앞부분별 세션 수, 갑자기 뛴 숫자 |
| P2 | 특정 게임을 인기 1위로 만들기 | 인기 = 최근 7일 **끝난 판** 수(또는 서로 다른 기기 수, 5절). 끝난 판은 판 끝 알림이 와야 센다. 랭킹 서버가 있으면 **검증된 온라인 판**만 따로 센다(지어내기 어렵다) | 혼자 하기 판 수는 지어낼 수 있다(서버가 확인할 방법이 없다) | 게임별 판 수가 IP 앞부분 하나에 몰림 |
| P3 | 가짜 방 열기로 "지금 열린 방" 부풀리기(신호 서버 구독) | 신호 서버 한도(전체 2000·IP 200·주제 32)가 이미 있다. 방 수는 "구독자가 둘 이상인 주제"만 센다 | 두 탭으로 방 하나를 여는 것은 진짜 방과 같다 | — |
| P4 | 요청 폭주로 서버 넘어뜨리기 | Traefik 횟수 제한(신호·진단과 같은 방식), 본문 크기 상한(1KB), 현황 읽기는 **1분마다 만든 작은 JSON을 nginx가 캐시**해 내준다(읽기가 많아도 서버 앱에 닿지 않는다). 실시간 SSE를 쓰지 않으면 열린 연결 수 걱정도 없다 | 큰 분산 공격은 서버 한 대로 못 막는다(지금 신호 서버도 같다) | Traefik 거절 수 |
| P5 | 숫자에서 개인 알아내기("새벽 3시 바둑 1명 = 그 사람") | 작은 수는 보이지 않는다: 게임별로 **3명 미만이면 "조금"**, 7일 판 수도 작은 값은 묶어 보인다. 시각별 그래프는 만들지 않는다. 이름은 어디에도 없다 | 사람이 아주 적은 동안은 "조금"만 보일 수 있다 | — |
| P6 | 신호 서버가 방마다 어느 게임인지 알게 되어 추적이 쉬워짐 | 게임 이름을 신호 주제에 넣지 않는다. 현황 알림은 신호와 **따로**(방 코드·주제 없이) 보낸다 | — | — |

### 3-5. 서버 API 쪽

랭킹 서버(가칭 `game-rank`)가 받는 요청은 셋이다. 모두 같은 원칙: **앱을 믿지 않고, 서버가 확인하고 계산한다.**

| 요청 | 하는 일 |
|---|---|
| `POST /rank/ticket` | 판 시작 때. 참가자 전원의 공개 열쇠, 게임, 규칙 코드, 각자의 "이 판을 랭킹 판으로 둔다" 서명(서버가 직전에 준 무작위 값 포함)을 보내면 시작표를 준다 |
| `POST /rank/result` | 판 끝. 시작표 + 판 기록(약속·공개 값·행동 목록, 멘탈 포커면 공개된 열쇠) + (있으면) 나간 사람 진술·시간 이의. 누구든 참가자 한 사람이 보내면 된다 |
| `GET /rank/...` | 순위표·내 기록. 정적 JSON으로 만들어 캐시 |

| 항목 | 위험 | 대책 |
|---|---|---|
| S1 인증 | 열쇠 없이, 또는 남의 열쇠로 요청 | 쓰기 요청은 모두 선수 열쇠 서명. 서명 문장 = 용도 이름 + 서버가 준 무작위 값 + 내용 해시. 무작위 값은 한 번만, 몇 분 안에만 유효 |
| S2 요청 한도 | 폭주, 대량 판 | Traefik 횟수 제한(IP) + 서버 안에서 열쇠별·IP 앞부분별 하루 시작표 수 |
| S3 입력 검증 | 큰 본문, 이상한 값으로 엔진을 오래 돌리게 하기 | 본문 크기 상한(게임별, 예: 판 게임 64KB, 멘탈 포커 판 수백 KB), 형식 검사(zod), 규칙 코드는 아는 것만, 엔진은 지금처럼 모르는 행동을 거절([12](./12-redteam-2026-10-21.md) B7). **다시 계산은 따로 일하는 스레드(worker)에서, 판마다 시간 상한**(넘으면 거절) |
| S4 재전송 | 같은 결과·같은 서명 다시 쓰기 | 시작표 한 번만(R5), 서명 문장에 시작표 id를 넣는다 |
| S5 재계산 검증 | 서버가 엔진과 다른 결과를 냄, 엔진이 바뀜 | 서버가 판 기록을 **같은 엔진 패키지**로 다시 돌린다. 결과에 엔진 판(커밋 해시)을 적는다. 규칙이 바뀌면 판 기록에 적힌 판의 엔진으로 계산해야 하므로, 서버 이미지는 게임 센터와 **같은 커밋**으로 만든다(같은 저장소, 같은 워크플로) |
| S6 저장소 | 디스크 손상, 실수로 지움 | SQLite 파일 하나 + 하루 한 번 백업(서버의 다른 앱처럼) |
| S7 운영자 정정 | 봇 판·부정 판을 나중에 무효로 할 때 | 레이팅을 저장값이 아니라 **판 기록에서 다시 계산**할 수 있게 둔다. 무효 표시 후 전체 다시 계산 |
| S8 운영자 믿음(T6) | 우리가(또는 서버를 뚫은 사람이) 순위를 고침 | 각 판의 서명된 시작 약속과 기록을 **누구나 내려받게** 하면, 누구든 레이팅을 다시 계산해 서버 표와 맞춰 볼 수 있다. 지금 "방장도 속이지 못한다"를 서버로 넓힌 것. 대신 판 기록이 공개된다(개인정보와 부딪친다, 4-5) |

### 3-6. 방어마다 포기하는 것

| 방어 | 얻는 것 | 포기하는 것 |
|---|---|---|
| 서버가 판 기록을 받아 다시 계산 | 결과 위조·엔진 조작이 순위에 못 들어감 | **"서버는 게임을 모른다"는 원칙**([18](./18-game-center-plan.md) 5절). 서버 코드·CPU·저장소. 판 기록(누가 무엇을 냈는지)이 서버에 남는다 |
| 판 시작 때 모두의 서명 + 시작표 | 지는 판 숨기기·남 끌어내리기·재전송 막기 | 랭킹 판은 **서버가 살아 있어야 시작**된다(지금은 서버가 없어도 방장끼리 둔다). 시작이 조금 늦어진다 |
| 나간 사람 패배 | 끊기 악용 막기 | 진짜로 끊긴 사람이 억울하다 |
| 새 열쇠 임시 등급, 같은 쌍 반복 제한 | 자기와 두기·몰아주기의 효과를 줄임 | 새로 온 친구는 한동안 순위에 없다. 같은 친구와만 자주 두는 사람은 레이팅이 잘 안 움직인다 |
| 친구 리그(초대받은 사람만) | 여러 신원 문제를 거의 없앰 | "전국 순위"의 재미 |
| OAuth(구글·카카오) 로그인 | 신원 만드는 비용이 오름, 기기 바꿔도 이어짐 | 계정 정보(이메일 등)를 받게 되어 개인정보 처리 책임이 생김, 로그인 화면, 외부 서비스 의존 |
| 기록 공개(누구나 다시 계산) | 운영자도 못 속임 | 누가 언제 누구와 무엇을 두었는지 공개 |
| 컴퓨터 자리 있는 판 제외 | 컴퓨터 조종·봇 기준점 조작을 없앰 | 사람이 모자라 컴퓨터를 넣은 판은 랭킹이 안 된다 |
| 현황 숫자 근사·작은 수 숨김 | 부풀리기 효과·개인 알아내기를 줄임 | 정확한 숫자, 사람 적을 때 "살아 있는 사이트" 느낌 |
| IP 앞부분당 상한 | 스크립트 부풀리기를 줄임 | 회사 와이파이처럼 한 IP의 여러 사람은 덜 셀 수 있다 |

## 4. 공유 랭킹

### 4-1. 신원

| 방법 | 어떻게 | 기기 바꾸면 | 여러 신원 비용 | 서버 부담 | 개인정보 |
|---|---|---|---|---|---|
| A. 이름만 | 지금처럼 입력 | — | 0 | 없음 | 없음 |
| B. 기기 열쇠 | 처음 랭킹 판에 들어갈 때 ECDSA P-256 열쇠를 내보낼 수 없게 만들어 IndexedDB에 둔다. 공개 열쇠가 곧 신원 | 새 사람이 된다. 옮기려면 ①옛 기기에서 "새 기기 열쇠를 나로 인정" 서명(QR로 새 기기 공개 열쇠를 읽어 옛 기기가 서명, 서버가 둘을 묶음) ②또는 처음부터 내보낼 수 있는 열쇠로 만들어 암호 문장으로 감싸 내보내기 | 0(탭마다 만들 수 있다) | 서명 확인만 | 공개 열쇠뿐 |
| C. 패스키(WebAuthn) | 서버가 계정(무작위 id)을 만들고 패스키를 묶는다. 이메일 없이도 된다 | 동기화 패스키(iCloud 키체인, 구글 비밀번호 관리자 등)면 같은 계정 회사의 기기끼리 이어진다(6절 passkeys.dev) | 낮음(패스키도 여러 개 만들 수 있다) | 등록·로그인 흐름, 챌린지 | 계정 id |
| D. OAuth(구글·카카오·GitHub) | 외부 로그인 | 이어진다 | 중간(외부 계정 필요) | 로그인 흐름, 비밀 값 관리 | 이메일·이름을 받는다 |

**추천: B로 시작하고, 필요해지면 C를 "열쇠 묶기 수단"으로 더한다.**

- 패스키는 쓸 때마다 사용자 확인(지문·얼굴)을 띄우므로 **판마다 서명하는 데는 맞지 않는다.** 패스키는 "이 계정에 새 기기 열쇠를 등록"할 때만 쓰고, 판 서명은 B의 기기 열쇠가 한다.
- D는 여러 신원 비용을 올리는 효과는 있지만 개인정보 처리 책임과 외부 의존이 생긴다. 지인 대상 사이트에 비해 무겁다.
- B의 약점(여러 신원이 공짜)은 신원 쪽이 아니라 레이팅 쪽(임시 등급, 친구 리그)에서 다룬다(3-3 R1).
- 방장 열쇠(`identity.ts`)는 방마다 새로 만드는 것이라 그대로 둔다. 선수 열쇠는 따로 둔다. 방장이 선수 열쇠로 방 열쇠를 서명해 두면 "이 방장은 ○○ 선수"를 이을 수 있다.

### 4-2. 결과를 서버가 어떻게 믿나

지금은 참가자마다 판 끝에 기록을 다시 돌려 확인하고, 그 결과를 서명 없이 알린다. 랭킹 서버가 믿을 길은 둘이다.

| 방법 | 서버가 하는 일 | 막는 것 | 못 막는 것 | 비용 |
|---|---|---|---|---|
| ① 참가자 서명 모으기 | 판 끝에 각자 "이 판 결과는 X이고 내 검증을 통과했다"에 선수 열쇠로 서명. 서버는 **모든 사람 서명**이 모이면 받는다 | 방장 혼자 위조, 남 끌어내리기 | 공모자끼리 아무 결과나 서명. 진 사람이 서명 안 하기(R8) | 아주 작다 |
| ② 서버가 다시 계산 | 판 기록(규칙·약속·공개 값·행동 목록, 멘탈 포커는 판 끝에 공개된 열쇠)을 받아 같은 엔진으로 돌려 결과를 스스로 낸다 | 결과 위조, 규칙 위반, 엔진 조작. 진 사람의 서명이 필요 없다 | 공모자끼리 실제로 둔 판(R1·R2) | 서버 CPU, 판 기록 저장 |

**추천: 시작 서명 + ②.** 판 시작 때 모두가 "이 사람들과 이 규칙으로 랭킹 판을 둔다"에 서명해 시작표를 받고(3-5), 끝 결과는 기록으로 서버가 계산한다. 끝에 서명을 모으는 ①은 필요 없다. 그러면 지는 사람이 서명을 거부해 판을 숨길 수 없다.

②가 되는 근거:

- 엔진이 모두 순수 함수이고, 판 끝 검증(`guest-room.ts`의 `verify`, `fair-verify.ts`의 `verifyFairLog`)이 이미 같은 재료로 같은 계산을 한다. 단위 시험이 Node에서 이것을 돌리고 있다.
- 키트(`apps/web/src/*/kit.ts`)가 `apps/web` 안에 있다. 서버가 쓰려면 화면과 상관없는 부분(규칙 풀기, `createMatch`, `step`, 결과 내기)을 키트에서 떼어 패키지로 옮기거나, 서버 빌드가 그 파일만 가져가게 해야 한다. 화면 코드에 기대는 곳이 있는지는 만들 때 확인한다.
- 판 게임(오목·장기·체스·바둑)은 계산이 가볍다. 멘탈 포커 판은 판 끝에 공개된 열쇠로 카드를 풀고 다시 돌리는 계산이 든다. 섞기 증명([15](./15-shuffle-proof.md))까지 서버가 다시 확인할 필요는 없다(판 끝에 열쇠가 모두 공개되면 실제 카드로 다시 계산되므로 조작은 드러난다, [13](./13-mental-poker.md) 8절).
- 컴퓨터 수를 다시 계산하려면 고수 컴퓨터의 탐색을 서버가 돌려야 해 무겁다. 처음에는 컴퓨터 자리가 있는 판을 넣지 않는다(R14).

### 4-3. 레이팅

게임이 두 무리다.

| 무리 | 게임 | 결과 모양 |
|---|---|---|
| 2인 판 게임 | 오목, 장기, 체스, 바둑 | 이김·짐·비김 |
| 카드·화투(여러 명) | 하트(4인, 점수 순위), 고스톱(2~3), 민화투(2~4), 나이롱뽕(2~5) | 여러 명의 순위 |
| 팀이 판마다 바뀌는 카드 | 마이티(주공+프렌드 대 야당, 판마다 바뀜) | 판마다 팀 승패, 게임 끝 돈 순위 |

| 방식 | 특징 | 여러 명 | 판 수가 적을 때 | 비고 |
|---|---|---|---|---|
| Elo | 가장 단순. 점수 하나 | 원래 2인. BGA는 여러 명 판을 "나보다 아래 사람을 다 이기고 위 사람에게 다 진" 2인 판 묶음으로 바꾼다(6절) | 확신 정도가 없어 처음 몇 판에 크게 흔들린다(BGA는 처음 30판 K를 크게) | |
| Glicko-2 | 점수 + 확신 정도(RD) + 변동성. 오래 안 두면 확신이 줄어든다 | 2인 | "임시 등급"을 RD로 자연스럽게 정한다(lichess는 RD 110 넘으면 임시, 6절) | lichess 사용. 판을 일정 기간씩 묶어 계산하는 것이 원래 방식 |
| TrueSkill | 점수 평균·불확실성. 팀·여러 명 순위를 바로 다룬다 | 됨 | 됨 | Microsoft 상표: Xbox 게임이나 비상업 프로젝트만 이름을 쓸 수 있다고 라이브러리 문서가 적는다(6절) |
| OpenSkill(Weng–Lin) | TrueSkill과 같은 문제(여러 팀·여러 명)를 푸는 공개 방법. JS 라이브러리(`openskill`, npm)가 있다 | 됨 | 됨 | 논문·라이브러리 저자 측정으로 TrueSkill보다 빠르고 정확도는 조금 낮다(6절) |

**추천: OpenSkill 하나로 모든 게임을 계산한다.**

- 2인 판 게임도 "두 명의 순위"로 넣으면 같은 코드로 된다. 계산 코드가 한 곳이라 고칠 곳이 적다.
- 마이티는 **게임(여러 판 묶음) 끝의 돈 순위**만 넣는다. 판마다 바뀌는 팀까지 넣으면 몰아주기(프렌드 짜기)에 민감하고 계산이 복잡하다. 하트·화투도 게임 끝 순위로 넣는다.
- 보이는 점수는 "평균 − 몇 배 불확실성"(보수적 점수)에 보기 좋은 배율을 곱한다. 순위도 이것으로 정한다. 새 사람은 불확실성이 커서 자연히 아래에 있다.
- 체스·바둑처럼 "Glicko-2 점수"가 익숙한 게임만 따로 Glicko-2로 보이자는 의견이 있을 수 있다. 갈림길(8절)에 둔다.
- 운이 큰 카드 게임은 점수가 천천히 모인다. 숫자보다 **단·급 같은 구간**으로 보이는 편이 오해가 적다.

규칙 차이:

- 게임 안 규칙(오목 일반·렌주, 바둑 9·13·19줄, 마이티 인원·규칙 묶음, 시간 규칙)마다 레이팅을 나누면 판이 너무 흩어진다. **처음에는 게임마다 하나**, 바둑만 줄 수(9 / 13·19)로 나누기를 추천한다. 데이터는 판마다 규칙 코드를 남겨 두므로 나중에 나눠 다시 계산할 수 있다.

컴퓨터 상대 판:

| 방법 | 장점 | 문제 |
|---|---|---|
| 넣지 않는다 | 단순, 조작 없음 | 혼자 하는 사람은 랭킹이 없다 |
| 컴퓨터 단계를 고정 점수 기준으로 넣는다 | 혼자서도 점수, 점수 기준점 | 혼자 하기 판은 서버를 거치지 않아 **시드를 내가 고를 수 있다**(좋은 패가 나올 때까지 다시 시작). 판 게임은 컴퓨터가 결정적이면 **이기는 수순을 외워 되풀이**할 수 있다. 서버가 시드를 주고 기록을 다시 계산하면 줄지만, 고수 컴퓨터를 서버에서 다시 돌리는 비용이 크다 |
| 따로 둔다: "컴퓨터 상대 기록"(고수를 이긴 횟수, 업적) | 사람 순위와 섞이지 않는다 | — |

**추천: 사람 순위에는 넣지 않고, 컴퓨터 상대는 따로 "도전 기록"으로 둔다.** lichess도 컴퓨터(Stockfish) 상대 판이 레이팅에 들어가는지 FAQ에 적혀 있지 않아 확인하지 못했다(6절).

### 4-4. 순위표

- 확정 등급 조건: lichess처럼 판 수·최근 활동·불확실성 기준을 둔다(lichess: 30판 이상, 최근 1주 안에 한 판, RD 75 미만, 6절). 우리는 사람이 적어 예를 들어 **10판 이상, 서로 다른 상대 3명 이상, 최근 30일 안에 한 판**으로 시작한다.
- **친구 리그**: 판을 같이 둔 사람끼리만 보이는 순위. 리그는 "초대 링크로 만든 모임"이고, 모임 안의 판만 센다. 전체 순위가 없을 때도 이것만으로 재미가 있다. 여러 신원 문제(R1)가 거의 사라진다.
- 전체 순위(공개): 친구 리그가 돌아간 뒤에 연다.

| 것 | 정할 것 | 추천 |
|---|---|---|
| 이름 공개 | 순위표에 보이는 이름 | 랭킹용 이름을 따로 정하게 하고, 기본은 "이름 숨김(지문 표식만)". 친구 리그에서는 이름, 전체 순위에서는 사용자가 고른 것 |

| 지우기 요청 | 내 기록을 지워 달라 | 앱에서 선수 열쇠로 서명한 "지워 줘" 요청 → 서버가 그 열쇠의 이름과 순위를 지우고, 판 기록의 내 자리는 "지워진 선수"로 바꾼다. 상대의 레이팅은 **이미 계산된 값 그대로 둔다**(다시 계산하면 남의 점수가 흔들린다). 열쇠를 잃은 사람은 지울 수단이 없다 → 운영자 연락처 안내 |
| 미성년자 | 한국은 만 14세 미만의 개인정보를 처리하려면 보호자 동의가 필요하다(개인정보 보호법 제22조의2). 이 규정은 **개인정보를 받을 때** 걸린다 | **별명과 공개 열쇠만 받고 실명·연락처·생년월일은 받지 않는다.** 그러면 나이를 물을 필요도, 보호자 동의 화면도 없다. 공개 열쇠는 무작위 값이라 그것만으로 사람을 알아보기 어렵다. 별명에 실명을 쓰지 말라는 안내 한 줄을 두고, 기본은 지문 표식만 보이게 한다. **OAuth(이메일)나 연락처를 받기 시작하면** 나이 확인과 보호자 동의 절차가 함께 따라온다. 이것도 G3에서 OAuth를 피하는 이유다 |
| 남기는 기간 | | 판 기록은 레이팅 다시 계산에 필요해 오래 둔다. IP 앞부분은 한도 계산용으로 메모리에만, 아니면 며칠 |

### 4-6. 서버 저장소와 비용

| 방법 | 장점 | 단점 |
|---|---|---|
| 개인 서버에 Node 앱 + SQLite 파일 | 지금 신호·진단 서버와 같은 방식(compose, Traefik, 백업). 엔진 패키지를 그대로 쓴다. 추가 비용 없음 | 서버 한 대가 멈추면 랭킹도 멈춘다(게임은 계속 된다). 운영자 믿음(S8) |
| Cloudflare Workers + D1 / Durable Objects 같은 서버리스 | 서버 관리 없음, 무료 한도 | 새 플랫폼 계정·배포·비밀 값. 실행 시간 제한이 있어 멘탈 포커 판 다시 계산이 걸릴 수 있다. 판 기록이 외부 회사에 있다 |
| Supabase 같은 BaaS | 로그인·DB가 함께 | 외부 의존, 개인정보 처리 위탁, 이 프로젝트 원칙(우리 서버는 내용 모름)과 멀다 |

**추천: 개인 서버에 SQLite.** 크기 짐작: 판 게임 기록 한 판 수 KB, 멘탈 포커 판 수십~수백 KB. 한 달 1,000판이면 많아야 수백 MB 안쪽이다. 실제 크기는 만들 때 재서 고친다. 다시 계산은 판이 올 때 한 번, 큐 하나에 하나씩. 메모리는 128MB 안쪽으로 시작한다.

### 4-7. 다섯 질문 (랭킹)

1. **데이터의 뜻·연결·책임**
   - `Player`: 공개 열쇠(신원), 랭킹용 이름, 만든 때. 묶인 열쇠 목록(기기 옮기기).
   - `Ticket`: 판 시작표. 게임, 규칙 코드, 자리별 공개 열쇠, 각자의 시작 서명, 발급 시각, 엔진 커밋. 서버가 만든다.
   - `Match`: 시작표 하나에 하나. 판 기록, 서버가 계산한 결과(자리별 순위), 나간 사람·시간 이의, 상태(받음·통과·거절·무효).
   - `Rating`: 선수 × 게임(× 줄 수). **저장값이 아니라 `Match` 목록에서 계산한 결과를 캐시한 것**이다. 책임: 결과를 정하는 것은 서버의 다시 계산 하나뿐이다.
   - `League`: 초대로 만든 모임과 구성원. 순위표는 리그별로 같은 `Match`를 걸러 만든다.
2. **꼭 지킬 규칙을 어떻게 보장하나**
   - 모든 사람의 시작 서명이 없는 판은 없다: `Match`는 `Ticket` 없이 만들 수 없게 DB 제약으로 둔다.
   - 결과는 서버 계산으로만: API에 결과 칸이 없다.
   - 한 판은 한 번: 시작표 id가 기본 키.
   - 시험: 12처럼 R·P·S 항목마다 "공격이 막히는지" 시험을 먼저 쓴다. 다시 계산은 지금의 판 끝 검증 시험 재료(정직한 판·조작한 판)를 그대로 서버 쪽에 돌린다.
3. **사람과 AI가 데이터를 어떻게 찾아 쓰나**
   - 사람: 순위표 화면, 내 기록 화면에 "랭킹" 탭. 판마다 "기록 내려받기"(복기 형식과 같게 하면 지금 복기 화면으로 열린다, [14](./14-review-replay.md)).
   - AI·운영: SQLite 파일을 읽는 작은 스크립트(`read.sh`처럼). 이 문서의 표 이름을 그대로 쓴다.
4. **요구사항이 바뀌면 어디까지 고치나**
   - 레이팅 방식 바꾸기: 계산 함수 하나 + 전체 다시 계산. 판 기록이 남아 있어 옛 판에도 새 방식이 적용된다.
   - 규칙별로 나누기: `Match`에 규칙 코드가 있어 거르기만 바꾼다.
   - 새 게임: 키트의 서버용 부분(규칙 풀기·진행·결과)만 있으면 된다. 지금 새 게임 체크리스트([21](./21-new-game-checklist.md))에 "서버 다시 계산" 한 줄을 더한다.
   - 신원 방법 바꾸기(패스키·OAuth): `Player`에 열쇠를 묶는 방법만 늘어난다. 판 서명은 계속 기기 열쇠.
5. **다른 대안과 고른 근거**: 4-1(신원), 4-2(결과 믿기), 4-3(레이팅), 4-6(저장소) 표에 적었다. 공통 근거는 "가장 적은 서버 + 지금 있는 판 끝 검증 재료 재사용 + 개인정보 받지 않기"다.

## 5. 접속·인기 현황

### 5-1. 무엇으로 셀 수 있나

| 재료 | 알 수 있는 것 | 모르는 것 | 바꿀 것 |
|---|---|---|---|
| 신호 서버(지금 그대로) | 구독이 열린 주제 수, 구독 수, IP. 구독자가 둘 이상인 방 공용 주제 ≈ 사람이 모인 방 | **어느 게임인지**(주제는 방 코드 해시뿐), 실제로 연결됐는지·판이 시작됐는지, 혼자 하기 | 신호 서버가 1분마다 "열린 방 수"를 메모리 숫자로 내놓기만 하면 된다. 앱은 고치지 않는다. 사람 한 명이 통로 셋(`LANES`)으로 구독 여러 개를 열어 사람 수는 대략이다 |
| 앱의 "지금 여기" 알림(새로) | 게임별·방식별(혼자·온라인·배우기) 지금 하는 사람 수 | — | 앱이 화면이 보이는 동안 1분마다 `{game, mode, 세션 id}`를 보낸다. 세션 id는 **탭을 열 때마다 새로 만든 무작위 값**, 저장하지 않는다. 화면을 숨기면 보내지 않는다 |
| 판 끝 알림(새로) | 게임별 끝난 판 수 → 인기 | — | 판이 끝날 때 `{game, mode}` 하나. 서버는 **날짜·게임·방식별 숫자만 더하고 요청 자체는 남기지 않는다** |
| 랭킹 서버(있다면) | 검증된 온라인 판 수 | 혼자 하기 | 따로 할 일 없음 |

혼자 하기(컴퓨터 상대)는 지금 서버를 전혀 거치지 않는다. 세려면 위의 "지금 여기"·판 끝 알림을 보내야 한다.

- **세는 쪽 추천**: 혼자 하기도 센다. 인기 게임을 알고 싶다는 목적에 혼자 하기가 큰 몫이다. 단, 설정에 "현황에 세지 않기"를 두고 브라우저의 추적 거부 신호(GPC)가 켜져 있으면 보내지 않는다.
- 혼자 하기 숫자는 지어낼 수 있다(P2). 그래서 화면에는 "지금 하는 사람(근사)"만 보이고, 순위처럼 무게 있는 곳에 쓰지 않는다.

### 5-2. 개인정보와 추적에 대한 반감

이 사이트의 정체성은 "서버가 내용을 모른다"다([07](./07-security.md), [18](./18-game-center-plan.md) 5절). 현황 기능이 이것을 흐리지 않게 한다.

- 보내는 값은 게임 이름·방식·탭마다 새 무작위 값뿐. 이름·방 코드·기기 정보(진단처럼 UA·코어 수)를 보내지 않는다.
- 서버는 IP를 한도 계산에만 메모리에서 쓰고 디스크에 남기지 않는다.
- 저장하는 것은 "날짜·게임·방식별 판 수" 같은 **더한 숫자뿐**이다. 사람 하나하나의 행이 없으니 지울 것도 없다.
- 무엇을 보내는지 /security(또는 새 "현황" 설명)에 그대로 적는다. 진단 기록(`/diag`)을 설명하는 방식과 같다.
- 쿠키·지문 추적(브라우저 특징 모으기)을 쓰지 않는다.

### 5-3. 실시간(SSE)인가, 몇 분마다 모은 값인가

| 방법 | 장점 | 단점 |
|---|---|---|
| SSE로 바로바로 | 숫자가 살아 움직인다 | 보는 사람 수만큼 연결이 열린다(신호 서버 한도와 같은 자원). 사람이 적으면 움직일 숫자도 없다 |
| 1분마다 JSON 만들기, 화면은 열 때·1분마다 읽기 | 서버 부담이 거의 없다(nginx 캐시). 부풀리기를 1분 단위로 거른다 | 1분 늦다 |

**추천: 1분마다 모은 값.** 첫 화면 게임 카드에 "지금 약 n명"을 작게 보인다. "지금"은 최근 2분 안에 알림이 온 세션으로 정한다(lichess는 페이지를 떠나면 바로, 열어 둔 채 10분 쉬면 목록에서 뺀다고 포럼에 적었다, 6절).

### 5-4. "인기 게임"의 뜻

| 정의 | 장점 | 단점 |
|---|---|---|
| 최근 7일 끝난 판 수 | 단순 | 짧은 게임(오목 몇 분)이 긴 게임(마이티 한 게임 수십 분)보다 늘 유리 |
| 최근 7일 서로 다른 기기 수 | "몇 명이 해 봤나"에 가깝다 | 기기를 구별하려면 오래 가는 기기 id가 필요하다 = 추적 |
| 최근 7일 논 시간(분) | 게임 길이 차이를 덜 탄다 | "지금 여기" 알림 수를 더하면 되지만, 화면만 켜 둔 것도 센다 |
| 최근 7일 **온라인** 판 수 | 사람끼리 함께 한 것, 랭킹 서버가 있으면 검증됨 | 혼자 하기가 빠진다 |

**추천: "최근 7일 논 시간"을 기본으로**, 판 수를 함께 보인다. 기기 수는 추적 없이 세기 어려워 쓰지 않는다. 사람이 적은 동안에는 순위보다 "요즘 많이 하는 게임" 표시(위 몇 개에 작은 표)만 한다.

### 5-5. 다섯 질문 (접속·인기 현황)

1. **데이터의 뜻·연결·책임**
   - `live`(메모리): 세션 id → `{game, mode, 마지막 알림 시각}`. 2분 지나면 사라진다. 책임: 현황 서버.
   - `daily`(디스크): `(날짜, game, mode) → {판 수, 논 분}`. 사람을 가리키는 값이 없다.
   - `presence.json`: 1분마다 `live`·`daily`에서 만든 공개 숫자(근사·작은 수 숨김 적용 뒤). 화면은 이것만 읽는다.
   - 신호 서버의 "열린 방 수"는 따로 하나 더할 수 있다.
2. **꼭 지킬 규칙을 어떻게 보장하나**
   - 개인을 남기지 않는다: 디스크에 쓰는 함수가 `daily` 더하기 하나뿐이게 둔다. 시험으로 "알림 본문의 다른 칸은 버린다"를 확인한다.
   - 작은 수 숨김: `presence.json`을 만드는 함수 한 곳에서. 시험으로 경계값을 본다.
   - 부풀리기 상한: IP 앞부분별 세션 수 상한을 같은 함수에서. 시간은 `Clock`으로 넣어 시험한다(flaky 금지 규칙).
3. **사람과 AI가 데이터를 어떻게 찾아 쓰나**
   - 사람: 첫 화면 카드의 숫자, (나중에) 작은 "현황" 화면.
   - 운영·AI: `daily` 파일(JSONL이나 SQLite)을 읽는 스크립트. 진단 기록의 `read.sh`와 같은 방식.
4. **요구사항이 바뀌면 어디까지 고치나**
   - 인기 정의 바꾸기: `daily`에 판 수와 논 분이 둘 다 있어 화면 계산만 바꾼다.
   - 실시간으로 바꾸기: `presence.json`을 SSE로 내보내는 길 하나만 더한다.
   - 기기 수가 필요해지면: 그때 추적 문제를 다시 정해야 한다(지금 구조로는 못 센다. 일부러 그렇게 둔다).
5. **다른 대안과 고른 근거**
   - 신호 서버만 쓰기: 앱을 안 고쳐도 되지만 게임별로 못 센다. 첫 단계로는 좋다(7절 1단계).
   - umami 같은 방문 통계 도구 붙이기: 페이지 방문은 세지만 "판이 끝났다"·"화면을 보고 있다"를 직접 정해야 하고, 방문 기록을 사람 단위로 남긴다. 이 기능 하나에 비해 무겁다.
   - SSE 실시간: 5-3.

배울 점:

- 큰 사이트도 여러 계정·져 주기를 **증명으로 막지 않는다.** 규칙으로 금지하고, 자동 탐지 + 신고 + 계정 닫기로 대응한다. 우리는 계정을 닫을 수단이 약하므로(열쇠는 공짜) 영향을 줄이는 쪽(임시 등급, 친구 리그)이 맞다.
- 나가기는 모두 불리하게 처리한다(BGA: 꼴찌 + 10점, lichess: 끊김 점수 돌려주지 않음, 자주 나가면 일시 금지).
- 여러 명 판을 2인 판 묶음으로 바꾸는 BGA 방식은 단순하지만, 순위 맨 아래 한 사람이 여러 판을 진 것처럼 계산된다. OpenSkill은 순위를 그대로 받는다.

## 7. 단계별 추천

| 단계 | 할 일 | 얻는 것 | 드는 것(서버 한 대 기준) |
|---|---|---|---|
| 0 | (지금 할 수 있는 준비) 판 끝 검증 재료(규칙·약속·공개 값·기록)를 한 묶음 형식으로 정리해 두기, 키트에서 화면과 상관없는 부분을 떼기 쉽게 두기 | 나중에 서버 재계산을 붙이기 쉬움 | 코드 정리만, 서버 없음 |
| 1 | 신호 서버가 "지금 열린 방 수"를 숫자로 내놓고 첫 화면에 "지금 친구와 하는 방 n개"(작은 수 숨김) | 가장 작은 현황. 앱 변경 거의 없음 | 신호 서버에 몇 줄. 개인정보 늘지 않음 |
| 2 | 현황 서버: "지금 여기"·판 끝 알림, 1분 `presence.json`, 7일 인기 | 게임별 현황, 인기 게임 | 작은 Node 앱 하나(메모리 수십 MB), 더한 숫자만 저장. Traefik 한도 |
| 3 | 선수 열쇠(기기 열쇠) + 내 기록 화면에 "랭킹 이름" | 신원 바탕 | 앱만. 서버 없음 |
| 4 | 랭킹 서버: 시작표, 판 기록 받아 다시 계산, OpenSkill, **친구 리그만**. 컴퓨터 자리 판·시간 이의 판 제외 | 친구끼리 순위. 결과 위조·지는 판 숨기기·끊기 악용을 막음 | Node + SQLite 앱, 엔진 패키지 서버 빌드, 백업. 랭킹 판은 서버가 살아 있어야 시작. 3절 시험을 먼저 |
| 5 | 전체 공개 순위(임시 등급·같은 쌍 제한·하루 상한), 신고, 운영자 무효 처리 | "전국" 순위 | 운영자가 신고를 보는 시간(가장 큰 부담). 이름 공개·지우기 요청 처리 |
| 6 | (선택) 패스키로 기기 열쇠 묶기, 판 기록 공개 내려받기(S8) | 기기 바꿔도 이어짐, 운영자도 못 속임 | 패스키 흐름, 공개 범위 결정 |

순서 이유: 1·2는 잃을 것이 거의 없고 사람 수가 늘었는지 먼저 알려 준다. 사람이 적으면 4 이후는 의미가 작다(순위표가 비어 있다). 4를 친구 리그로 시작하면 3절의 가장 어려운 문제(여러 신원)를 피해 간다.

## 9. 불확실한 점

- 서버 재계산 비용(특히 멘탈 포커 판)은 재 보지 않았다. 만들기 전에 지금 판 끝 검증을 Node에서 돌려 판당 시간·기록 크기를 잰다.
- 키트를 화면 코드 없이 서버에서 돌릴 수 있는지는 `omok/kit.ts`처럼 일부만 봤다(엔진·AI 패키지와 타입만 가져온다). 모든 키트를 확인해야 한다.
- R9의 "나간 사람 진술"을 남은 사람들이 짜고 지어낼 때(특히 2인 판)의 처리는 더 다듬어야 한다.
- R13(방장의 시간 부풀리기)은 지금도 남은 한계다([24](./24-time-control.md)). 랭킹이 생기면 무게가 커진다.
- 별명과 공개 열쇠만 받아도 개인정보로 보는 경우가 있는지는 깊이 조사하지 않았다. 이 문서는 "받지 않는 설계"로 위험을 줄이는 데까지만 다룬다.
- 6절의 BGA 문서는 옛 문서로 표시되어 있어 지금 방식과 다를 수 있다. chess.com의 Glicko 판은 확인 못 했다.
